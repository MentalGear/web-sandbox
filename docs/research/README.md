# Sandbox Security Research

This repository documents security research into the `iframe-sandbox` environment.

## Definition of "Breakout"

For the purposes of this research, a "Breakout" or "Vulnerability" is defined as any mechanism that allows code running within the sandbox to:

1.  **Bypass Network Restrictions**: Successfully establishing a connection (fetch, XHR, WebSocket) to a domain not explicitly allowed in the sandbox configuration.
2.  **Access Host Context**: Gaining access to the `window.parent` or `window.top` DOM or JavaScript objects in a way that violates the intended Same-Origin Policy isolation.
3.  **Compromise Infrastructure**: Tampering with the sandbox control mechanisms (e.g., Service Workers, Shared Storage) to degrade security for the current or future sessions.

## Findings

Each subdirectory documents one investigated attack vector. **Status** reflects the *current*
opaque-origin architecture — several findings describe the older shared-origin design and are
closed by construction rather than by a fix.

| # | Vector | Status |
| :-- | :--- | :--- |
| [01](01_csp_bypass/README.md) | Nested iframe with a manipulated CSP | Closed by construction — no `inner-frame.html`; a nested `srcdoc` frame inherits the sandbox policy (asserted by the spec) |
| [02](02_sw_tampering/README.md) | Unregistering the Service Worker | Closed by construction — an opaque origin cannot register one |
| [03](03_storage_sharing/README.md) | Data leaking between instances via `localStorage` | Closed by construction — an opaque origin has no storage |
| [04](04_websocket_bypass/README.md) | WebSockets bypass request logging | Bridge requests are logged — `fetch` events, `BL:B5`. **Remains:** a direct `WebSocket` or `fetch` to an origin in `origins.connect` is governed by the policy but not logged ([threat model](../THREAT-MODEL.md)) |
| [05](05_outer_frame_tampering/README.md) | Reaching the outer frame's DOM | Closed by construction — no `allow-same-origin`; guarded by the deny-list test (backlog T2) |
| [06](06_protocol_handlers/README.md) | `registerProtocolHandler` | Secure — browser refuses it in a sandboxed frame |
| [07](07_data_uri_navigation/README.md) | Top-level navigation to a `data:` URI | Secure — no `allow-top-navigation` |
| [08](08_session_exhaustion/README.md) | Unbounded server-side sessions | Not applicable — the local-first design has no server; see backlog E2 |
| [09](09_monkey_patch_bypass/README.md) | Undoing monkey-patched `fetch` | **Open** — why observability needs a bridge, backlog B5 |
| [10](10_base_tag_hijacking/README.md) | Injected `<base href>` | Fixed — `base-uri` now defaults to `'none'` (finding 12) |
| [11](11_meta_csp_delivery/README.md) | Limits of delivering CSP via `<meta>` | Partial — 11.3 fixed (security block is prepended, backlog S2); 11.1 and 11.4 remain inherent to `<meta>` delivery (S7, S8) |
| [12](12_non_fallback_directives/README.md) | Empty-array directives that do not fall back | Fixed — empty `base-uri` / `form-action` are emitted as `'none'` (backlog S9) |
| [13](13_popup_exfiltration/README.md) | Popup to an attacker URL | Fixed by default — `allow-popups` needs the explicit `unsafeCapabilities` opt-in (backlog S12) |
| [14](14_self_navigation/README.md) | Guest navigates itself; host re-sends the port | Fixed — wrapper frame with `frame-src 'none'`, one-shot channel (backlog S10, S11) |

Findings 11 and 12 include probe scripts and the environment they were measured in; see
[`11_meta_csp_delivery/probes/METHOD.md`](11_meta_csp_delivery/probes/METHOD.md).

## Design probes

| Probe | Question | Result |
| :--- | :--- | :--- |
| [Blob-URL file delivery (δ)](../archive/research/blob-delivery-probe.md) | Can guest-created blob: URLs plus an import map replace the virtual-files Service Worker? | Viable with changes: `blob:` in five directives, rewrite relative specifiers, one import map before any module. | [Strict mode (15)](15_strict_mode/README.md) | Does the strict-mode design hold, measured before building it (P1–P8)? | Holds with nine amendments (A1–A9): no nested frames, move never clone, hash the parsed text, render flow control, a view liveness check, worker hardening. | [View isolation (16)](16_view_isolation/README.md) | Where does the strict view run, and what can it cost the host page that its time budget does not see? | On the host page's thread everywhere but desktop Chromium 127+; CSS animations and transitions keep it 75–92% busy, outside the budget. A stylesheet in one anonymous layer plus inline-style stripping brings every vector back to idle (`allowAnimations: false`); a meter-and-actuator design was rejected; the budget's rendering measure became a gap meter. | [Relay worker (19)](19_relay_worker/README.md) | Should a library-only relay worker spawn the guest as a nested worker, so its events land off the host page's thread and are measured in a trusted realm (S66)? | Build it, with caveats: nested `blob:` workers start under the view's policy on all three engines; the guest's own `postMessage` (98% / 58–63% / 29% host busy) and its uncaught errors cost the host page 0–2% through a relay that cancels them; unhandled rejections are not closed (Firefox 96–98% busy in every layout); +1.9 MB and +14–21 ms to ready per sandbox; the relay needs a byte budget that ends the guest |
| [Served-document mode (20)](20_served_document_mode/README.md) | If the host serves one static `frame.html` with its own headers instead of `srcdoc` frames, does it survive the host's Service Worker, a COEP host, `frame-ancestors` with sandboxed ancestors, and Chromium's process grouping? | Nothing blocks it, and it gains no availability. A sandboxed frame is out of the host SW's reach on all three engines (the iframe `sandbox` attribute, not the header, keeps it out). Under a COEP host `frame.html` needs COEP, and in Firefox CORP too, or it does not load. `frame-ancestors 'self'` refuses cross-site framing and every opaque ancestor (a sandboxed host, a served frame inside a served frame), and no source list fixes that in Chromium or WebKit. The served frame shares a renderer with the `srcdoc` frames in every Chromium configuration: a loop delays the host timer 1200 ms of 1200 where they share the host's renderer, and not at all where they do not. The header is a ceiling every guest inherits (a hash-only `script-src` stops a cooperative guest). Six amendments to the proposal |
| [Forced crossorigin (21)](21_crossorigin_loads/README.md) | If the strict view's renderer forced `crossorigin="anonymous"` on every element that loads a URL, would Chromium, Firefox and WebKit omit the cookies of those loads, and what breaks? | On elements, yes on all three, any SameSite kind, same-site or cross-site: a CORS request (`Origin: null`, no preflight) without a cookie, Range and seeking still stream, the view's own `blob:` files still load; the listed origin must answer ACAO, and a miss is silent (no violation). Set last in a live document it is too late; in the renderer's inert template it is not. Four other loads (`td background`, `input type=image`, SVG `image`, `feImage`) have no attribute: keep them off the allowlists |
| [Review trajectory (22)](22_review_trajectory/README.md) | Is the finding curve of the review rounds bending, and when should the approach change? | Data findings reaching strict went 2, 3, 4 over the board passes, all from the host page's context, and BD3's highs sit in code BD2's fixes added: delete the predictors rather than patch them; re-evaluated after every pass. |
| [View input (23)](23_view_input/README.md) | Can strict mode's inert view give a guest pointer, wheel, scroll and focus input for drag-and-drop, gestures, sliders and virtual scrolling, with no guest code in the view and no guarantee weaker? | Yes: trusted events only, coordinates clamped to the view's box (a press that began in it goes on delivering over the host page in every engine), continuous events coalesced per frame with one frame unacknowledged, their time charged to the view's budget; the worker answers with `set({ css, scroll })` from closed lists. | [Sealed mode (24)](24_sealed_mode/README.md) | If the default mode had no network at all, what leaves its code, what are its policies, and can it run an app the host drives from outside, with WebAssembly? | Decided, not built: `mode: 'sealed'` is strict with no network (every fetch directive `blob:` or `'none'`, `connect-src 'none'`), becomes the default, and refuses a config that names `origins` or `fetchBridge` without `mode: 'strict'`. | [Guest styles under the host page's `style-src` (25)](25_cssom_styles/README.md) | Which ways of styling a document does a `style-src` it inherits from its host page not check, on every engine, and can the strict view apply every guest style through them? | The CSSOM: an element's declaration and a constructed stylesheet raise no violation and no report on all three engines; every inline style does, and Chromium and WebKit check a `style` attribute already as they parse it, in an inert template too (Firefox on insertion). So the view's parser never sees one (`styleMarkup` renames them first), a style attribute becomes the element's declaration and a `<style>` an adopted constructed stylesheet. But the interrupt handler is polled every 5,000 loop turns, and WebKit ends the worker only when the running native operation returns (3.8 s seen for one), so the stop bound is not a constant of the library: the residual that keeps WebAssembly out of sealed mode ([research 24](24_sealed_mode/README.md), D2). | [Served document, no headers (27)](27_served_document_headerless/README.md) | If D8's served document is a static file with no response headers and its policy in a `<meta>` tag, does the host page's policy still reach it, can it stay inert when opened the wrong way, and which hosts can serve it? | It starts a policy of its own on all three engines: the host's policy refused nothing in the frame, its `srcdoc` child or their workers, and no violation reached the host's endpoint; the host's `frame-src` must admit the file. `self.origin` is opaque exactly when the file is framed with `sandbox` and without `allow-same-origin`, so a file that does nothing otherwise is inert wherever it would hold the embedder's origin; an opaque origin does not say who the embedder is (`ancestorOrigins` names it on Chromium and WebKit; on Firefox it is `null` once the frame sets `no-referrer`). Not closed: permission state (Chromium's documents and WebKit's worker read the host page's grants), the secure-context bit, the shared thread; the referrer is the host's full URL unless the frame sets `referrerpolicy="no-referrer"`. A COEP host needs headers on the file. Measured on Chromium 159, Firefox 159, WebKit 27.2, 2026-11-15 (and before on 145, 146, 26.0, with the same answers) |
| [Served topology (28)](28_served_topology/README.md) | Before D8 is built: can the served file be built so that guest code never runs with an origin's authority however the file is opened, with a constant policy, a channel the file cannot relay on, and start-up gates that fail closed? A second hostname changes the file's authority, not the thread: a loop in it stalled the host's timer on the headless shell, Firefox and WebKit as today's view does. The default build ran `examples/sealed-app` with its wrapper served as a file, also under a host policy that refuses today's `srcdoc` build. Measured on Chromium 159, Firefox 159, WebKit 27.2, 2026-11-15; not on Safari, Android or shipping third-party storage settings. |
| [Autofill (29)](29_autofill/README.md) | Does a browser's autofill (saved passwords, addresses, cards, the history of what the user typed) put the user's data into a sealed guest's fields, today and in the served topology? | Measured with a seeded profile on Chromium 159 (Chrome for Testing) and Firefox 159, each with a positive control. **History: yes, on both, with the renderer as it was**, after the user picks the browser's suggestion: both key it by the field's `name` on every site, the guest chooses the name, and the worker received the value. WebKit raises the events but reports only F's and the view's code-from-string refusals. The host page's own fetch tells the failure modes apart, and an SPA shell's frame received the hello's port. A file without its guard passes every gate. With `allow-forms` on the file, `submit` works and the twelve ways give research 28's cells; extra flags give the view nothing. A second, refused canary per directive (`http:` and `https:`) sees every header Q3 missed that would report a guest's URL, except `form-action` on Chromium (the refused form ends the view) and a header naming the canaries' own host; `manifest-src` has no canary and nothing to report. Firefox's refused clean starts came from the twin canary counting the worker's script refusals, which Firefox files in the view's document; a check that attributes events by their URL, with no fixed wait, refused none on Chromium and Firefox and saw every header tried, but its one kept cut (600 ms on a worker canary) refused 5 of 200 loaded WebKit starts. Measured on Chromium 159, Firefox 159, WebKit 27.2, 2026-11-18 and -19 |
