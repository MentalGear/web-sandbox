#### <a id="bd2-chl-1"></a>BD2:CHL-1: Firefox runs embedder code inside the teardown effect (the host window's `focus`, when the removed wrapper held focus); a rebuild from there is then torn down by the rest of the outer `_teardown`, and its guest outlives the next `terminate()` and `reset()`

- **Severity:** high. A documented security property does not hold: "`terminate()` or removing the element ends
  everything of the environment" (THREAT-MODEL, lifecycle integrity, L1/LM-1) and "Embedder code that runs inside the
  element's own calls cannot corrupt it" (same table, LM-2). The precondition is embedder code of an ordinary shape (a
  `window` `focus` listener that rebuilds a sandbox it finds `terminated`: an auto-restart when the user comes back) and
  the guest frame holding focus at a teardown (the user is typing in it). The guest can start the teardown itself (a
  forged second announcement, BR:PD8; the uncaught budget). Firefox only; cooperative mode for a running orphan (strict
  mode leaves an orphan view frame that never runs the worker). If the board does not count that listener as a realistic
  precondition, this is medium (embedder-triggered, as BD1:CHL-1), but with a worse effect than BD1:CHL-1: a running
  guest, not a config undone.
- **Leaks data?** No data crosses the policy: the orphan guest keeps its own policy, and its port is closed. What it
  breaks is termination: the host is told `terminated` while the guest keeps running, stays visible and interactive (its
  frame is still in the shadow root, before the next wrapper), keeps every egress its policy allows (and posts to the
  host window, S36), and receives whatever the user types into it.
- **Class:** L (LM-1 teardown completeness, LM-2/AR:B5 re-entrancy: "an actor of an old environment cannot act").
- **Where:**
  - `src/host.ts:1776-1808` (`_teardown`): line 1794 `this._iframe.remove()` is where Firefox fires `focus` on the host
    `window` and `document` synchronously (the wrapper, or a frame in it, held focus); every line after it runs after
    that embedder code, and writes fields by name: `this._iframe = null` (1794), `_port`, `_viewPort`, `_viewWrites`,

  - `src/lib/lifecycle.ts:660-673` (`runEffects`): the generation is compared before each effect, so nothing after the
    `teardown` effect runs, but the `teardown` effect itself is not one atomic step.
  - `src/host.ts:2190` (`_frameLoadHandler`): `stillOurs = iframe === this._iframe` is then false for the new build, so

     `window.addEventListener('focus', () => { if (el.state === 'terminated') el.reset(); })`.
  2. `el.terminate()`: the reducer stores `terminated` (gen n+1); the executor runs `teardown`.
  3. Inside `this._iframe.remove()` Firefox fires `focus` on the window; the listener sees `terminated` and calls

#### <a id="bd2-chl-2"></a>BD2:CHL-2: On desktop Chromium every sandbox on the page shares one sandboxed-frame process; one sandbox's guest stalls another's frames, and the other's view watchdog ends it

- **Severity:** medium. The library's own limit (the view liveness watchdog, `VIEW_LIVENESS_TIMEOUT_MS`) ends a
  healthy sandbox B because of what sandbox A's guest did: CONTRIBUTING "Availability findings", exception 2 (a
  correctness bug), the S79 mechanism, but across sandboxes. It is worse than S79 documents: S79 says one documented
  stall ends the sandbox that rendered it; here a plain loop in any cooperative sandbox, or one documented stall in any
  strict view, ends every strict sandbox on the page, in the default configuration of the victim. B fails closed
  (terminated, rebuildable), so no security property is broken beyond availability; the docs' "a process of its own"
  is wrong in a way that matters to an embedder that puts several sandboxes, of different trust, on one page.
- **Leaks data?** No (availability and a docs claim). Note for the Spectre residual (THREAT-MODEL "Side channels"): the
  process is shared with every other sandbox of the page (their views, their workers' owners, their bridge frames and
  the bodies those fetch), so "a process of its own" does not separate one sandbox from another.
- **Class:** B (a liveness bound that assumes a stall of the view is a stall of the host page; S79's class), plus a
  docs claim (THREAT-MODEL "Where the view runs", API.md "Chromium on the desktop: a process of its own").
- **Where:** `src/host.ts:2159-2166` (`_startViewWatchdog`, host ticks only), `VIEW_LIVENESS_TIMEOUT_MS`
  (`src/host.ts:534`); docs: `docs/THREAT-MODEL.md:210`, `:240`; `docs/API.md:270`, `:1368`; ADR-005:414 ("Desktop Chromium
  127+ runs it in a process of its own").
- **Path:**
  1. Desktop Chromium groups the sandboxed frames of one site in one renderer process (IsolateSandboxedIframes,
     per-site): A's cooperative guest frame, B's strict view, both bridge frames.

#### <a id="bd2-lim-2"></a>BD2:LIM-2: a bodiless response (HEAD, which is a default method) with a large `Content-Length` is refused `FETCH_TOO_LARGE`

- Severity: medium by the rubric ("a correctness bug with no security effect"); availability of a documented feature only.

- Class: E-net (the bridge's size limit), a case the limit's definition ("most bytes of one response body") does not cover.
- Where: `src/lib/fetch-bridge.ts:464-470` (`readBody`): the declared-length check

#### <a id="bd2-lim-3"></a>BD2:LIM-3: the fetch result's non-body size can exceed the 1 MiB the config invariant allows; the invariant "a response the bridge admits is never refused as a result" is false

- Severity: low, availability only (a response from an allow-listed origin that the bridge read in full is then refused
  on its way to the guest; the embedder's record says `ok`).
- Class: P (a budget that counts a proxy: the head is capped in characters, the result is measured in structured-clone bytes).
- Where: `src/lib/config-schema.ts:434` (`FETCH_RESULT_OVERHEAD = 1024 * 1024`, "Chromium at 256 KiB, measured twice

- Path: the result measures 2 bytes per character plus 8 per string and 16 per array, i.e. about 40 bytes of overhead

  budgets. With `maxBytes` near its largest (32 MiB) and a body above `RPC_MAX_BYTES` minus that head, the host reads the

- Reproduction: `test/unit/probe-p2-lim-size.test.ts`. Output: `HEADERS 46656 head bytes 3633132 RPC_MAX 34603008 overhead

  blocked by `img-src`, reported as a `violation`), so the renderer's "relative URL fails closed" assumption is false there;
  the strict guest (a worker) cannot read the base, so I rate the confirmed data leak as cooperative mode only.
- **Reproduction**: `test/e2e/p2-host-base-uri.probe.spec.ts` (served through the existing `/__host-policy` harness):


- **Why the existing tests miss it**: `test/e2e/host-policy.spec.ts` covers `script-src`, `worker-src`, `style-src`, Trusted Types and

  only the library's own guest policy). `host-url.spec.ts` runs with no host policy.
- **Suggested fix**: class C, one chokepoint: a table of the host-policy directives the library's own elements depend on
  (`script-src`, `worker-src`, `style-src`, `require-trusted-types-for`/`trusted-types`, **`base-uri`**), each with a startup

#### BD2:ISO-1: the hashed bootstrap is a script gadget on the host page — CONFIRMED-DIFFERENT-SEVERITY (medium; fix it anyway, one line, by construction)

##### Reproduction (unchanged src, `p2-iso-gadget.spec.ts` and `v2-iso-variants.spec.ts`)

Victim page `https://victim.test` with exactly the policy API.md prescribes (`default-src 'self'; script-src 'self' <viewScriptHash()>; worker-src blob:`),

| :--- | :--- | :--- | :--- |

The bridge role's gain is small: uncredentialed reads in the victim origin, and the victim's Service Worker/fetch wrappers do
not apply to it either (the injected copy calls the platform `fetch` it captured; a cross-site-framed context gets a
partitioned SW in Chromium). The view role is the real one: arbitrary attacker code in a worker of the host origin.

##### Threat model

- Not "a compromised host page": THREAT-MODEL.md:235 defines that as *a script injected into the host page*. Here no script
  of the attacker's runs until the library's hash admits one; the host has a markup injection that its CSP would neutralise.
- The library *requires* the hash on the host page (srcdoc inherits the policy; THREAT-MODEL.md:248, API.md "Host page
  policy"), so the embedder cannot avoid it in strict mode. The library therefore turns a CSP-neutralised markup injection into
  attacker-chosen code execution in the host origin: it weakens a control the embedder relies on, though no row of the
  library's own property table promises "the hash does not weaken your policy". THREAT-MODEL.md:83–84 and :138 ("the view
  takes INIT_VIEW only from parent.parent", "Strict mode's ports reach only the library's code") are stated for the library's
  frames and do hold there.
- Cooperative and worker mode need `'unsafe-inline'` on the host page anyway (API.md table), so there the injection is already
  code execution and the gadget adds nothing. The gadget matters for strict mode (default) and for `fetchBridge` on a
  hash-only page.

##### Severity: medium (from high)

Preconditions, all on the host page: (1) a markup injection in which a verbatim ~78.5 KB `<script>` survives (the server's
filtering keeps `<script>` and the size); (2) the page is frameable cross-origin (no `frame-ancestors` / `X-Frame-Options`;
helmet's default `X-Frame-Options: SAMEORIGIN` already stops it); (3) for the credentialed read, the browser sends the host's
cookies to the page as a cross-site frame: Chrome with third-party cookies on (its default), not release Firefox (Total
Cookie Protection partitions the framed page's cookies; not measured for the gadget, by the TCP result of BD2:ISO-2 below), not
Safari. This is a CSP script-gadget, a defence-in-depth bypass behind a host-page vulnerability: medium on the board's
scale (a leak needing an unusual configuration: an injectable *and* frameable page), plus a false security comment. Not high:
the attacker is not the guest, and two independent host-page weaknesses are needed. A board that weighs "the library
silently weakens the embedder's CSP" more heavily could keep high; the fix is cheap either way.

- Same-site (BD2:NEW-2): **high**. The common layout (`app.` host, `api.` listed, `Domain=` cookie) gets no warning; on Chrome

#### BD2:CHL-1: CONFIRMED, high

##### (1) Reproduction

**Host-triggered, Firefox** (load 9.4; `zz-p2chl-focus-reentry`). The run matches the report line for line.

- Cooperative mode:
  - `after terminate(): state=loading frames=1 _iframe=null _bridgeFrame=null _fetchBridge=null`
  - `settled: state=ready _iframe=null`
  - fetch: `FETCH_FAILED: the sandbox was torn down`
  - after the 2nd `terminate()`: `frames=1`, 14 guest messages in 1.5 s
  - after `reset()`: `frames=3`
- Strict mode:
  - the new environment ends by the load deadline
  - an orphan view frame stays
  - `frames=3` after `reset()`

**Guest-triggered** (load 12; `zz-p2chl-focus-guest`):
- Firefox: an orphan, 20 pings in 2 s after `terminate()`.
- Chromium and WebKit: clean (`frames=0`, 0 pings).

**New: the guest needs no user interaction on Firefox** (load 5.4; `zz-v2chl-pagehide`, `PROBE_SELFFOCUS=1`). The guest
calls `window.focus(); input.focus()` itself, which README "Focus and the clipboard" documents as possible, and then
forges the second announcement. Result: `now: state=ready _iframe=null`, then 20 pings after the host's `terminate()`.
The precondition "the user is typing in it" is not needed.

**New: the re-entry also happens on Chromium and WebKit.** The reviewer's "clean" is luck, not a property.
- Mechanism: a focused cooperative guest's `pagehide`/`unload` handler runs synchronously inside the host's
  `iframe.remove()` (same-process frames). There it calls `parent.parent.blur(); parent.parent.focus()`, and the host
  window's `focus`/`blur` listeners fire inside `_teardown`.
- Seen in `zz-v2chl-orphan` "sync events": `win:focus:inside=true`, `win:blur:inside=true` on Chromium and WebKit
  (cooperative mode). The stack in `zz-v2chl-pagehide` shows `WebSandbox._teardown → teardown → runEffect → … → onMessage`
  on all three engines.
- Why there is no orphan there: Chromium and WebKit run the `pagehide` before the node leaves the tree (`frames=1`).
  The nested `reset()`'s own teardown removes the old wrapper, so the outer `remove()` then throws `NotFoundError`
  ("The node to be removed is no longer a child of this node…", and WebKit's "The object can not be found here.").
  That throw aborts the rest of the outer `_teardown` before `this._iframe = null`.
- Side effect: an uncaught `NotFoundError` on the host page. In the host-triggered form, the throw comes out of the
  embedder's own `terminate()` call (low on its own).

**Without the guest's `focus()` call**, nothing fires on any engine: the host window already had focus.

**Other synchronous events looked for inside `terminate()`.** Tested together on all three engines, both modes:
`DOMNodeRemoved`, `DOMNodeRemovedFromDocument`, `DOMSubtreeModified`, `resize`, `visibilitychange`, `selectionchange`,
`pagehide`, `focusin`/`focusout`, on the element, its shadow root, the window and the document.
- None fired, apart from the `focus`/`blur` above.
- Strict mode, Chromium and WebKit: nothing fires (the view runs no guest JavaScript).
- Code review of the other release points:
  - `rejectAllPending` and `lost()` reject promises, so their handlers run asynchronously.
  - `abortAll()` calls `controller.abort()`. Its `onAbort` settles through promises, and the `fetch` record is
    asynchronous.
  - `bridgeFrame.close()` removes a host-made frame that the guest cannot focus.
  - So the only synchronous embedder-code point is the wrapper's `remove()`. In a unit test, every release point
    (wrapper `remove()`, bridge frame `remove()`, port `close()`) is still exploitable: see (4).

##### (2) What the orphan can do

Probe `zz-v2chl-orphan`, Firefox, load 7.

**While the host thinks the orphaned environment is current** (`ready`, `_iframe=null`):
- its RPC works (10 host-method hits per second);
- its fetch bridge is dead.

**After the host's next `terminate()`:**
- `hostHits=0`: its port and broker are closed, because the outer `_port` field held its port and the next teardown
  closed it;
- no announcement listener, no bridge, no `violation` channel;
- it keeps running: 15 pings in 1.5 s by `postMessage` to the host window, which reaches the embedder's own `message`
  listeners (S36);
- it stays visible and interactive in the shadow root, so it receives the user's input;
- it keeps whatever egress its own CSP allows (the policy is baked into its srcdoc);
- `state` reads `terminated`.

**Next to a new environment:**
- `reset()` builds a 3rd environment beside it. The new one works normally (14 hits per 1.5 s, its own port only).
- The orphan cannot forge into the new listener, which checks `event.source` against its own frame.

**What ends it:**
- the next `terminate()` does not (10 pings after a 3rd `terminate()`);
- **removing the element** does (0 pings), and so does navigating the page;
- the frame can also be removed by hand: the shadow root is open, but no API does it.

So it is a running guest past `terminate()`, with its own policy and no channel. No data crosses the policy. The
embedder's kill switch fails silently, and the element reports `terminated`.

**Strict mode (the default):** no guest code runs in the orphan. The worker source travels only in `INIT_VIEW`
(`host.ts:1467`), which the orphan's view never receives (its load is not `stillOurs`), and the view is inert without it
(unit test `in-sandbox-view.test.ts:205`). The effect in strict mode is LM-2 corruption that fails closed:
- the rebuilt environment's bridge is closed;
- the load deadline ends it with a startup reason, though nothing refused anything;
- an inert frame stays in the shadow root and stacks at the next `reset()`.

##### (3) How realistic the precondition is

- README, docs/API.md and `playground/` contain no `focus`/`blur`/`visibilitychange` handler that calls `reset()`,
  `load()` or `setConfig()`. The only listener examples log `terminated`.
- The shape (resume a stopped widget when the user comes back to the tab) is plausible and uses only public methods,
  which LM-2 explicitly promises are safe from embedder code ("Embedder code that runs inside the element's own calls
  cannot corrupt it").
- The guest can supply the rest itself on Firefox: it takes focus and ends its own environment.

##### (4) Fix tested

The fix is the reviewer's first option: detach, then release.
- `_teardown` copies `_stopListening`, `_loadDeadline`, `_iframe`, `_port`, `_viewPort`, `_viewWrites`, the timers,
  the probes, the watchdogs, `_resizer`, `_fetchBridge` and `_bridgeFrame` into a local record.
- It clears all those fields, then releases from the record only.
- The wrapper's `remove()` and the bridge frame's `close()` come last.
- Diff: `teardown-fix.diff`.

Results:
- **Unit test** `zz-v2chl-teardown-reentry` (9 cases: wrapper `remove()`, bridge `remove()` and port `close()`, each

- A reducer state that refuses `build` while tearing down would silently swallow (or have to queue) a public `reset()`,

- The record makes the teardown commute with any nested step: whatever runs during the release finds an element with no

1. The release-point re-entry matrix above, kept in `test/unit/lifecycle-reentry.test.ts`.
2. A source scan: `_teardown` writes no `this._…` field after its first call on a platform object.
3. A model listener plan "focus during teardown" (`test/model/generator.ts`).
4. E2E on Firefox (the focus) and Chromium/WebKit (guest `pagehide` with `parent.parent.focus()`): L1 with the guest

- **The property that fails:** a documented security property, "`terminate()` … ends everything of the environment"

- **Why not critical:**
  - default strict mode runs no orphan guest (there it is fail-closed corruption, medium on its own);

  - removing the element ends it.
- **Medium if** the board does not count the listener as realistic (the BD1:CHL-1 precedent).

then remains the bound for B's own stalls.

##### Evidence per engine

The reviewer's probe (`p2-host-base-uri.probe.spec.ts`, copied in), run on chromium, firefox and webkit:

- **Control (no `base-uri`):** passes in all three engines.
- **`base-uri 'none'` and `base-uri 'self'`:** both fail in all three engines. The guest logs
  `BASE http://localhost:24380/__host-policy?...&code=HOST-URL-SECRET | http://localhost:24380/x`.
- **`base-uri 'self' about:`:** passes in **all three** engines. The reviewer verified this remedy on Chromium only.

My probe opens the host at `...&code=HOST-URL-SECRET#frag`. With `base-uri 'none'`, unfixed, the guest's
`document.baseURI` is the full host URL **including `#frag`** in Chromium, Firefox and WebKit. The state is `ready`
and there is no warning. The reviewer's "fragment excluded" is wrong. A fragment can hold an OAuth implicit-flow
`access_token` or an SPA route.

##### Already-documented channels (they change the picture only on WebKit)

- **WebKit, S17 (documented):** a frame the guest creates, with `referrerpolicy="unsafe-url"`, reads the host URL
  **without the fragment** as `document.referrer`. I re-measured this with no host `base-uri`:
  `R:http://localhost:24380/__host-policy?...&code=HOST-URL-SECRET`. So on WebKit, BD2:NEW-1 adds the fragment and a
  no-effort read (`document.baseURI`, every relative URL, `import.meta.url`). On Chromium and Firefox it is new: the
  whole URL.
- **`ancestorOrigins` (Chromium, WebKit):** shows the origin only.
- **`document.referrer`:** empty, because both frames are `no-referrer`.
- **Firefox:** no documented channel at all.

##### Strict (the default) and worker mode

- **What the worker sees:** the strict worker's `location` is `blob:null/<uuid>` in all three engines.
- **The view:** its `baseURI` is the full host URL including the fragment, in all three. Relative URLs in rendered
  markup and CSS resolve against the host origin: `<img src="rel.png">`, `<img src="?q=1">` and `url(bg.png)` are
  requested from `localhost:24380/...`. The view's `img-src` blocks them.
- **Where the violations go:** they reach **the host** as `violation` events with `source: 'view'` (blockedURI
  `http://localhost:24380/__host-policy?q=1`). The host already knows its own URL.
- **Can the worker get any of it?** I checked by reading the view code and found no path:
  - Violations are posted only to the host (`toHost`, in-sandbox-view.ts:1367).
  - `VIEW_EVENT` carries raw `.value`, `name`, `id` and `FormData` strings, never a resolved URL. Forms are excluded
    from `.value`, and links are `INERT_HREF`.
  - `VIEW_ACK` carries only budget codes.
- **What does break in strict:** the renderer's assumption that "a relative URL resolves to nothing" (in-sandbox-view.ts
  near 795, and `loadOf`/`refusedUrl` treat relative URLs as non-loads) is false. If the embedder lists the host origin
  for a kind, relative URLs make real loads that the distinct-URL budget does not count. No new destination opens,
  because an absolute host URL would be admitted the same way. That is defence in depth: **low**.
- **Worker mode:** guest code runs in a `blob:` worker and saw nothing.

##### Severity reasons

It meets "a documented property that does not hold (#11 'Host URL Hidden', THREAT-MODEL row 104) under a realistic
precondition":

- The mode is non-default, but documented as supported.
- Any host CSP with `base-uri 'none'` or `'self'` triggers it. That is helmet's default line, kept when a host adds
  `'unsafe-inline'` to `script-src`, which cooperative mode needs.
- Nothing warns or terminates.

What it leaks is host page state: path, query and fragment. It is not rated critical because the default mode does
not leak to the guest. The realistic precondition is narrower than the reviewer implies: Google-style strict CSP
(nonce + `base-uri 'none'`) cannot run cooperative mode at all (BD2:NEW-6), so the exposed hosts are the ones with
`'unsafe-inline'` and a `base-uri` line.

##### Fix candidates

**(a) Set the base by another means: none exists. Not tested, rejected.**
- `base-uri` governs only `<base>`.
- A `srcdoc` or `about:blank` document's fallback base is its embedder's base URL, with nothing in between that the
  library controls.
- The guest's own `<base>` is refused by its own `base-uri 'none'`, and the host's would refuse it too.
- A `data:` wrapper would drop host-CSP inheritance and need host `frame-src data:`. A `blob:` wrapper would still
  expose the host origin as its base and need `frame-src blob:`. Both break the "every frame is srcdoc" design
  (THREAT-MODEL §1, the research-14 navigation argument).

**(c) The library's own policy: rejected.** Policies intersect, so a library policy can only add restrictions. The
wrapper's `WRAPPER_CSP` has no `base-uri`, and the binding one is the host's.

**(b) Detect the refusal and fail closed: TESTED, works on all three engines.** This is the recommendation. The patch
is `fix-b.diff`:

- **The check:** the first statement of `inSandboxScript`, in cooperative mode. If `document.baseURI !== 'about:blank'`,
  it posts `{ type: 'SANDBOX_PORT', refused: 'base-uri' }` with no port, calls `window.stop()` and throws.
- **Why `window.stop()`:** it aborts the parser, so no later guest script runs.
- **Host side:** accepts that portless refusal in cooperative mode only for `base-uri`. A forgery by the guest can only
  end its own sandbox, and after the real announcement it is a `secondAnnouncement`.
- **Results:**
  - `base-uri 'none'` and `base-uri 'self'`: terminated with the reason, and the guest's `<script>` never ran (no
    `GUEST RAN` line).
  - No `base-uri`, and `'self' about:`: `ready`, and the guest sees `about:blank`.
  - All of this held in Chromium, Firefox and WebKit.

**What to land:**

1. **A `reasons.ts` row.** For example `baseRefused`: "the host page's base-uri refuses the sandbox's base
   (about:; see docs/API.md#host-page-policy)", decided by `host`. Add it to `reasonCauses`.
2. **The same check in the strict view's bootstrap,** with a new view-port message. This keeps the renderer's
   relative-URL rule true and gives one uniform host requirement. For worker mode the check is optional, because it
   does not leak.
3. **Docs:**
   - a `base-uri` row in docs/API.md "Host page policy": absent, or listing `about:` (e.g. `base-uri 'self' about:`),
     verified on all three engines;
   - THREAT-MODEL "what the embedder must do";
   - README #11.
4. **A test:** a `host-policy.spec.ts` case per refusing value (`'none'`, `'self'`) asserting the reason, plus the
   `'self' about:` positive control, on all three engines.

**Residual:** cooperative mode without `allow-scripts` runs no bootstrap, so nothing checks there. No guest script runs
either, so there is nothing to read the base with. Relative markup URLs still resolve to the host origin and are
blocked by the guest policy. That is low, and should be stated.

### 1. Method

- Every finding the archive records is mapped to the **root cause**, meaning the property of the design that made the
  defect possible, not the invariant it broke. That is why this mapping differs from research 18's.
- The counts are all severities. Medium-or-higher is counted apart, by the verifier's rating where one exists.
- Where research 18 put a finding in E-net, B or G and the root cause is the host context, it moves to A, with the old
  class noted. A finding with two causes is counted under its first and listed under the second.
- **Recurring** means a new instance arrived after a fix of the same class. **Converged** means no medium since a
  change that enumerates the domain.
- The counts are one reviewer's judgement, like research 18's. A count can be disputed row by row in §2.

#### Class definitions

| Class | Root cause | Invariant that would make it impossible |
| :--- | :--- | :--- |
| **A** host context | The sandbox's documents, requests and library code run in or below the host page's context, and inherit its ambient state: the policy container (CSP incl. `base-uri`, Trusted Types, COEP and cross-origin isolation), base URL, referrer, the cookie jar and site for cookies, the Service Worker, host-realm globals and hooks (`fetch` wrappers, `console`, `Object.prototype`, a TT default policy), UA surfaces (focus, history, clipboard, the host window as a message target), and the thread and process. | Nothing reaches a guest from the host context except through a row that names the channel and its neutralisation, and is checked at run time or by construction. |
| **E** library in host trust | To run in `srcdoc` documents, the library's own scripts must be admitted by the host page's `script-src`, through a hash, or through `'unsafe-inline'` in cooperative and worker mode. That admission holds anywhere on the host page. | Library code carries no authority outside the context it was built for: it checks that context before it acts, or the host never has to admit it. |
| **V** value boundary | A budget, a measure or a decision is computed from a proxy of the value that crosses: own keys, a constant for a kind, the tag, a getter, the prototype chain, a part of the frame, a second read. | Library code measures and walks only values it built itself, from fields it read once. |

| **D** drift | A docs sentence, a warning's text or a code comment restates a fact: a per-engine measurement, a code path, a constant. Nothing derives it from the source or checks it against the source. | Each such fact has one source (code or a dated, per-engine measurement asserted by a test), and the text is generated from it. |

### 3. Probes run for this review

#### 3.1 What each kind of document inherits from the host

`class-probes/ctx.mjs`:
- The host page `https://host.test/app/secret-path?token=HOSTSECRET#frag` sends
  `default-src 'self' 'unsafe-inline' data: blob:; img-src 'none'; base-uri 'none'`.
- Each frame is `sandbox="allow-scripts"` and carries `<base href="about:blank">`.
- It loads an image from `https://img.test`, which its own policy (where it has one) allows.

| Document kind | Origin | Host `img-src 'none'` binds it | Host `base-uri 'none'` refuses its `<base>` | `document.baseURI` | Engines |
| :--- | :--- | :---: | :---: | :--- | :--- |
| `srcdoc` (today) | `null` | **yes** | **yes** | **`https://host.test/app/secret-path?token=HOSTSECRET#frag`** | Chromium, Firefox, WebKit: identical |
| `data:` | `null` | **yes** | **yes** | the `data:` URL (nothing of the host) | identical on all three |
| `blob:` (made by the host) | `null` | **yes** | **yes** | `blob:https://host.test/<uuid>` (the host origin, no path) | identical on all three |
| http(s), same origin as the host, served with its own CSP header | `null` | **no** (the image was requested) | **no** | `about:blank` (its `<base>` honoured) | identical on all three |
| `srcdoc` inside that served document | `null` | **no** | **no** | `about:blank` | identical on all three |
| `'credentialless' in HTMLIFrameElement.prototype` | — | — | — | — | Chromium `true`, Firefox `false`, WebKit `false` |

Conclusions:
1. **No local-scheme document escapes the host's policy container.** This is the HTML spec's "determine navigation
   params policy container": `about:srcdoc` clones the parent's, and a local URL clones the initiator's. It is now
   measured on all three engines.
   - This corrects v2-new's rejected option (a), which said "A `data:` wrapper would drop host-CSP inheritance". It
     does not.
   - `data:` changes only the base URL: there it is the `data:` URL even when the `<base>` is refused, so the host URL
     cannot leak through the base.
   - `blob:` leaks the host origin through its base.
2. **A network-fetched document starts a fresh policy container, and its `srcdoc` children inherit from it.** A
   same-origin static file in a sandboxed frame is enough. Its origin is opaque because of `sandbox`, not because of
   where it is served from.

#### 3.2 The host's Service Worker against a sandboxed frame

`class-probes/sw.mjs`, Chromium; Playwright's routing did not let the SW register on Firefox and WebKit:
- The host page is controlled (`controlled: true`) by a SW that answers `/frame.html` and `/sub.json` itself.
- A sandboxed frame navigated to the same-origin `/frame.html` got **the network's** document.
- A sandboxed `srcdoc` frame's `fetch` of a same-origin URL got **the network's** answer.

So the host SW neither substitutes the served frame document nor sees its subresources. This agrees with the SW spec's
opaque-origin rule and with P2-NEW's observations. One cost follows for an offline PWA: the frame document cannot come
from the SW's cache in Chromium, only from the HTTP cache.

**(ii) The context assertion: one chokepoint before any role runs.** `assertContext(role)` is the **first statement**
of the shared bootstrap text: the view, the bridge frame, the cooperative guest bootstrap, worker mode's frame and the
strict worker's prelude.
- It reads only unforgeable state, before any guest byte exists: `self.origin`, `location.href` (`location` is
  `[LegacyUnforgeable]`), `document.baseURI`, `crossOriginIsolated`, `document.referrer`, `parent !== self`.
- It compares each against `CONTEXT_EXPECTATIONS[role]`, which is generated from the inventory rows marked `assert`.
- On the first mismatch it:
  - posts `{ refused: <row id> }`, portless, which the host accepts only before the announcement (v2-new fix (b));
  - calls `window.stop()`, and throws.
- Outside a library-made document (row 10) it returns before reading `currentScript` or installing a listener. The
  gadget then has nothing to drive.

The approved pass-2 fixes become rows of this one function: the base-uri check is row 4, the origin and srcdoc guard
is row 10, and COI (row 8) and the referrer (row 9) come with them. They are not three patches. The unit harness needs
an injectable context (`globalThis.__sandboxContext` in test builds), because v2-iso saw 43 unit failures from
evaluating the bootstrap in the unit DOM.

**(iii) The structural tests that keep it complete.**
1. **Unit, enumeration.** Every directive name in a closed CSP3 directive list, every member of the HTML policy
   container (CSP list, embedder policy, referrer policy), and every document-inherited state (base URL, origin, sandbox
   flags, COI, storage key) maps to an inventory row. Every row has a neutralisation, a test that exists and engine
   facts for all three engines. Every `assert` row has a `CONTEXT_EXPECTATIONS` entry and a `reasons.ts` row, and every
   reason has a row. The docs tables are generated from the inventory: THREAT-MODEL "What the embedder must configure
   or do" and "Engine differences", and API.md "Host page policy". This is the `CHANNEL_BUDGETS` pattern.
2. **E2e, the directive matrix (nightly, sharded).** For each directive at its most restrictive value (`'none'`, or
   the narrowest legal one), on each engine, each mode ends in exactly one of two outcomes:
   - `ready`, with the property suite passing: host URL hidden, egress governed, `terminate()` ends everything;
   - `terminated`, with that row's reason.

   `ready` with a property broken fails. BD2:NEW-1 fails this test the day it is written. Cost: about 30 directives × 3
   modes × 3 engines; run strict on each PR and the rest nightly.
3. **E2e, the realistic-host fixture.** P2-NEW's `probe-host` becomes `test/e2e/realistic-host/`, the property suite
   run against it per engine:
   - a strict CSP with `base-uri 'self'`, `require-trusted-types-for` and `trusted-types`;
   - a cache-first SW and an auth `fetch` wrapper;
   - `Domain=` cookies with all three SameSite values;

   All four leaks of the board passes were found by building this host once. Over the real network it needs `/etc/hosts`
   entries or `--host-resolver-rules`, and a local TLS server (v2-iso: Chromium's TLS to a local server was reset in
   this container, so use the resolver flag plus HTTP for the same-site case).

What this cannot enumerate is a channel that no closed list names, as BD2:CHL-1's focus-on-removal was. The realistic
fixture and §4.R's yield-point matrix cover those as far as tests can.

##### 4.A.3 The cookie row: the one inherited channel no document kind removes

The mechanism by construction, in strict mode (the default):
1. **Refuse a same-site origin in `origins.*` in strict mode**, with a reason that names the bridge as the way to reach
   it. The bridge pins `credentials: 'omit'`, and it is the only by-construction remedy that works on every engine.
   Cooperative mode warns: it is a frozen-limits mode.
2. **Decide same-site with the browser's own public-suffix list.** Set `__ws_probe=1; Domain=<suffix>` on successively
   longer suffixes of the host name, then delete it. The shortest suffix the browser accepts is the registrable domain:
   the analytics "auto cookie domain" technique, a class-B delegation (ask the browser, do not re-derive it).
   - Where cookies are blocked or the page is opaque, fall back to a heuristic that errs toward same-site: the last two
     labels, plus a short list of multi-label suffixes. Its errors are refusals, a functional loss, never a leak.
   - This must be measured per engine first, including that the probe cookie never reaches the network: it is set and
     deleted synchronously.
   - Alternative: an explicit `hostSite` option.
3. **`credentialless` on the wrapper (Chromium).** It closes fetch, `no-cors`, rendered subresources and WebSocket for
   cross-site listed origins too. Its popups open `noopener`; document that.
4. **Defence in depth in the strict worker's prelude.** `fetch` and `Request` are pinned to `credentials: 'omit'`, and
   `XMLHttpRequest.withCredentials` to false, with the natives deleted from `WorkerGlobalScope.prototype` too (which
   closes BD1:ISO-2's shadowing). This stops the guest's opt-in channel on every engine. WebSocket handshakes and the
   view's `no-cors` subresources stay, which is why (1) is the primary mechanism.
5. The warning text and the docs are **generated from the cookie row's engine facts**: Chromium None; Firefox None,
   and none under TCP; WebKit None, Lax and Strict. The "on Firefox and WebKit" error then cannot recur.

##### 4.A.4 The opt-in served-document mode: the peak for A's policy-container rows and for E

`frameDocumentUrl: '/web-sandbox/frame.html'` (one static file the package ships, plus a header template):

```
Content-Security-Policy: sandbox allow-scripts; default-src 'none'; script-src 'sha256-<frame bootstrap>';
                         frame-src 'none'; base-uri 'self'; frame-ancestors 'self'
```

- The wrapper, the view and the bridge frame are this one document, with the role picked by the host's first message.
  The guest documents remain `srcdoc` children and inherit **the served document's** policy, not the host's (measured,
  §3.1).
- The `sandbox` header makes the document opaque even when an attacker frames it without `sandbox`. `frame-ancestors`
  stops cross-site framing entirely. The assertion's row 10 covers hosts that cannot set headers, and the document
  holds no other script.

**Rows that become construct (impossible) in this mode:**
- 1–4, 6 and 14: the host CSP no longer narrows the sandbox, no `viewScriptHash` is needed, cooperative mode needs no
  host `'unsafe-inline'`, and there is no TT policy;
- 9: WebKit's walk stops at the served document. Expected, not measured;
- the `<meta>` delivery limits ADR-001 lists: S2, S7, S8 and research 11.

**Rows unchanged:**
- 11 (cookies);
- 15–17 (UA surfaces, re-entry and thread);
- `ancestorOrigins`, which still lists the host origin.

**Costs:**
- a static file, plus header control for the best variant;
- the dev servers (Vite, Bun) need the file served with its headers;
- an offline PWA must not rely on its SW for the frame document (Chromium does not route it through the SW, §3.2);
- not `file://`;
- a second build of the bootstrap (a postMessage-configured role instead of literals).

**Breaks:** nothing for srcdoc-mode users; it is opt-in.

**To probe first** (a research note):
- whether Firefox's and WebKit's SWs intercept the navigation;
- the COEP and COI behaviour of a served frame under a COEP host;
- `frame-ancestors` with sandboxed ancestors;
- the Chromium process grouping of served versus `srcdoc` frames (it may change BD2:CHL-2).

#### 4.V The value boundary: canonicalise, don't measure a model

**The mechanism.** One module, `canonical.ts`, is stringified into the guest realms and imported on the host:
`canonicalize(value, budget) → { value: Canonical, bytes } | Refusal`.
- **It reads** only through captured intrinsics: `Reflect.getOwnPropertyDescriptor`, and brand checks through
  internal-slot getters (`Blob.prototype.size`, `ArrayBuffer.prototype.byteLength`, …). Each field is read once.
  Getters may run once, as structured clone runs them: the output does not depend on them being honest. It never
  branches on `Symbol.toStringTag`, `constructor`, `instanceof` or a prototype the guest can change.
- **It builds** the output entirely in library code, over a closed set of kinds:
  - primitives (BigInt capped by digits);
  - a plain object (its own enumerable string-keyed properties);
  - an array (charged `max(8·length, keys)` **before** the loop; the output array is built from the keys);
  - `Map`, `Set`, `Date`, `RegExp` (`source` and flags);
  - `ArrayBuffer`, typed arrays and `DataView` (the bytes counted once per buffer, kept transferable);
  - `Blob` → `new Blob([b], { type: capped })`;
  - `File` → `new File([b], cappedName, { type, lastModified })`;
  - an Error-like → `{ name, message, stack }` strings.

  Anything else is refused, with its kind.
- **`bytes` comes from what was built**, so the measure is of what is sent, by construction, not by a model of clone.
- **Every sink takes only `Canonical`,** a branded type: `port.postMessage`, the host's `dispatchEvent` details and
  `freezeDeep`. The host canonicalises received data again with the same function before any walk, so `freezeDeep`
  walks only what was counted (BD1:LIM-3's host half).
- **A budget for work the platform makes** (Firefox's report of a rejection on the host's thread) charges an **upper
  bound computed without guest-controlled branching**. It counts `name`, `message` and `stack` of every object reason,
  tagged or not (S78). Over-counting is allowed.
- **A `Foreign` type with no members** is the static half. Every value from the guest or the embedder enters as
  `Foreign`: listener parameters, `MessageEvent.data`, `setConfig()`'s argument, `sandboxFetch` init, call arguments.
  Only `reader.ts` (`canonicalize`, `readEvent`, `ownField`) accepts it. TypeScript then rejects `event.reason` or
  `source.headers` at compile time. This replaces S80's planned syntactic scan and generalises BD2:LIM-1's `ownField`.

**Cost.**
- Engineering: M–L, 5–8 days: the console relay, both brokers, `toLogDetail`, `handleRequest`, the bridge result, and
  the per-engine tests.
- Run time: one pass instead of today's two (a `structuredClone` snapshot, then the measure walk). Bytes are copied
  once, as the snapshot does today.

**Engines.** Plain JS on all three. The `File` constructor exists in workers on all three; check WebKit's `File` in
a dedicated worker.

**What it breaks for embedders.**
- Received values are the canonical kinds. That is already true in practice, since clone drops prototypes and
  functions.
- A sparse array arrives dense up to its counted keys, or is refused past the budget.
- An unknown platform kind (ImageData …) is refused with its kind, as it is today.

**Structural tests.**
1. `tsc`: `Foreign` has no members, and a scan forbids `as` casts from `Foreign` outside `reader.ts`.
2. A differential property test (fast-check plus adversarial generators):
   - generators: getters that answer differently, Proxies, sparse and holey arrays, Files and Blobs with long names and
     types, tagged and subclassed errors, a polluted `Object.prototype`;
   - check: `bytes ≥` an oracle size of the canonical value after a `MessageChannel` round trip, on each engine. The
     oracle walks every string-valued getter of each kind's prototype chain, as S77's verifier designed;
   - check: every library walk's steps `≤ k·bytes`.
3. Every `postMessage` call site takes a `Canonical` (compile time).

**Supersedes:**
- S77 (the measure's kind table);
- S78 (tag gating);
- S80 (the scan);
- BD1:LIM-5 (the prelude reads the view's frames through the reader);
- BD2:LIM-3 (the bridge head measured as built);
- BD2:LIM-1's `ownField` (generalised).

**S69 (the relay worker)** would make the guest-side copy functional rather than a security property, but it does not
cover the host-side walks. The canonical boundary is the cheaper, more complete step. The relay remains the
architectural answer for P-view's guest-generated share.

#### 4.R Re-entry: transactional state with registered yield points

**The mechanism.** `src/lib/foreign.ts` is the only module that may call a platform API that can run embedder or guest
code synchronously: a **yield point**.
- The closed list of such APIs:
  - frame insert and remove (load, unload, pagehide, focus and blur, custom-element reactions);
  - `focus()` and `blur()`;
  - `srcdoc` and `src` assignment (unload, a TT default policy);
  - `console.*` (embedder hooks);
  - `dispatchEvent` (listeners);
  - reads and coercions of `Foreign` values (getters, Proxies, `toString` and `valueOf`);
  - resolving an embedder thenable (`Promise.resolve(x)` reads `then` synchronously);
  - `structuredClone` of embedder values (getters);
  - `AbortController.abort()` where embedder listeners exist.
- **Each wrapper asserts the element is quiescent.** The executor sets `_tx` while it writes a reduce output's fields,
  and the wrapper throws in test builds if `_tx` is open. After the call it re-reads the generation (the existing
  executor rule).
- **Every effect is either pure field writes, or one yield point last.** `environment.ts`'s detach-then-release is the
  teardown's instance of this rule. The rule generalises it to builds, `applyConfig`, warnings and dispatch.
- **Library warnings go out at a quiescent point.** `warnLater()` queues them to a microtask (`setConfig()`'s returned
  `warnings` are unchanged), so a `console.warn` hook can never run inside an operation. That makes BD1:CHL-1 and
  CHL-1b impossible.

**Structural tests.**
1. A source scan, as `CAPTURE_POINT`'s: the raw yield-point APIs (`.remove()`, `appendChild` and `insertBefore` of a
   frame, `.focus(`, `console.`, `dispatchEvent`, `.srcdoc =`, `await` of a `Foreign`) appear only in `foreign.ts`.
2. **A re-entry matrix generated from the registry.** The model-based suite (`test/model/generator.ts`, `fc.commands`)
   gains one command: "at the next yield point of kind k, run public method m", for every m in reset, load, setConfig,
   terminate, remove, re-append and call. After each command sequence it checks L1:
   - at most one environment;
   - no orphan frame;
   - the state matches the frames;
   - the next `terminate()` leaves 0 frames and 0 guest messages.

   `test/unit/teardown-reentry.test.ts` (BD2:CHL-1's matrix) is the teardown's slice of this, generalised to every
   method.
3. Per-engine e2e for the yield points only the platform makes: Firefox's focus on removal; the guest's
   `pagehide` → `parent.parent.focus()` on all three.

**Cost:** M, 3–5 days. **Engines:** n/a (JS). **Breaks:** library console warnings appear one microtask later; the
documented synchronous `terminated` inside `terminate()` is kept.

**Supersedes** the per-method teardown scan, BD1:CHL-1 and CHL-1b (S82), and LM-2's case-by-case reasoning.

#### 4.D Drift: one source per fact

**The mechanism.**
- `ENGINE_FACTS`: rows of a fact id, a value per engine, the measurement date, and the e2e that asserts the measured
  value per engine (the `host-url.spec.ts` "asserts the measured value" pattern).
- The prose of README, THREAT-MODEL and API.md, and every warning string, interpolates facts through the docs
  generator (S76 already generates the API reference). A security-claim sentence carries a marker
  (`<!-- claim:id -->`) that links it to its test, extending THREAT-MODEL's 37 rows to the prose.
- `docs:check` fails on:
  - a fact without all three engines;
  - a claim marker without its test;
  - a hand-copied constant (BD1:DOC-11).

**What it cannot make impossible:** wrong prose that cites no fact. It stops the measured-once-and-copied drift, which
is the drift that hid a leak.

**Cost:** S–M, 2–3 days.

### 6. What cannot be made impossible, and the residual risk

**Without any network-fetched document (pure local-first, the default `srcdoc` mode):**
- **The policy container is always inherited** (measured, §3.1). The host's CSP, TT and COEP narrow or break the
  sandbox. After PR 1–3 every such case is either constructed away or **fail-closed with a named reason**, and the
  matrix checks each directive. The residual is availability or function (the sandbox refuses to run), not a leak.
- **The host must admit the library's text** (the view hash; cooperative and worker mode need `'unsafe-inline'` on the
  host page). With row 10 the admitted text is inert outside a library-made opaque `srcdoc`, so the gadget carries no
  authority.
  - The cooperative cost stays: the guest's own inline scripts inherit the host's `script-src`, so they need the host's
    `'unsafe-inline'` too.
  - Only the served mode removes it.
  - This is a weakening of the embedder's own XSS defence, not a sandbox leak. Document it as the price of cooperative
    mode (done in pass 2) and prefer strict mode.
- **`ancestorOrigins`** shows the host *origin* to a cooperative guest on Chromium and WebKit, in both modes. It is
  permanent: no page can change it.

**In every mode:**
- **Cookies.** No document kind changes them (they follow the top-level site), and a separate origin does not either.
  - After PR 2:
    - Chromium: none, through `credentialless`.
    - Firefox and WebKit: none to same-site origins, which are refused. The residual is a detection error, which the
      browser-PSL probe makes about 0 and the heuristic makes err toward refusing.
    - A listed cross-site origin's own third-party cookies remain where the browser sends them: release Firefox (TCP)
      and Safari do not; Chrome does only without `credentialless`. They remain only for WebSocket handshakes and the
      view's `no-cors` subresources, because the prelude pins fetch and XHR.
  - The residual is the third party's own session, sent to the third party the embedder listed. **Rated low, and
    documented.**
- **Thread and process** (P-view, BD1:LIM-2, BD2:CHL-2). These fall under the availability rule; no library mechanism
  removes them. The served mode may change Chromium's process grouping (to probe). S69's relay moves the guest-generated
  share off the host thread.
- **UA surfaces in cooperative mode** (focus, clipboard, history, modifier clicks) are frozen limits. Strict mode has no
  guest document.
- **Unknown future channels.**
  - The inventory's enumeration covers closed lists: CSP directives, policy-container members, document-inherited state.
    A new platform feature outside them (a new response header, a new synchronous event) is caught only by the
    realistic fixture or a review.
  - Rate estimate from the record: class A produced 5 findings in P2 with the fixture-like host, against 0 in R3–R5
    without one. With the fixture in CI, expect about 0–1 new A finding per board pass, mostly UA or platform surfaces,
    not the policy container.
