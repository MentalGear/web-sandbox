# S74 review board, pass 4 (2026-10-24)

The fourth pass of the final independent review board (backlog [S74](../../BACKLOG.md#s74)), on `main` at `46eb358`, after
the fixes of pass 3 ([BOARD-PASS-3-2026-10-23.md](BOARD-PASS-3-2026-10-23.md)) and the strict view's input (#74). The brief's
scope was strict mode first: strict at its default configuration, with its two opt-ins (`origins` and `fetchBridge`), and
the code that adapts to the host page, which the last three passes had found the data findings in. The changes since pass 3

that never answers "absent"), #72 (the BD3 docs and test batch), #73 (strict view loads carry no cookie: forced

## Decisions

How each finding was resolved. The first group is the findings that count against the board (they leak or can manipulate
data); the rest follows the "Pass 4" paragraph of backlog [S74](../../BACKLOG.md#s74).

- **Owner's board rule, 2026-10-21** (unchanged for this pass). A pass is clean when none of its confirmed findings leaks or
  can manipulate data, at any severity, a docs gap that leads an embedder into a leak included; DoS and availability-only
  findings are backlogged and do not count against a pass; strict mode (the default, with its opt-ins `origins` and
  `fetchBridge`) is the supported baseline.
- **Owner's decisions, 2026-10-24** ([research 24](../../research/24_sealed_mode/README.md)):
  - strict mode keeps its network, with two fixes that remove the predictors rather than patch them: it has no cookie
    carrier (no `WebSocket`, no `origins.withoutCors`), and the host page's policy comes only from
    `hostContentSecurityPolicy`, never from a read;
  - **sealed mode** (strict with no network at all) becomes the default and the board's scope. Data findings that reach only
    strict's network opt-ins no longer count against a clean pass (D5); they are fixed or documented. Pass 5 runs after
    sealed becomes the default, and it is the first pass of that scope.
- **[BD4:ISO-1](#bd4-iso-1) and [BD4:ISO-3](#bd4-iso-3)** (a host page with an opaque origin, or framed by a page of another
  site, keeps entries on a site the browser sends cookies to; on WebKit the guest's WebSocket and a `withoutCors` load carry
  Lax, Strict and host-only cookies) are fixed in two parts. Strict mode has no cookie carrier at all, so no strict request
  carries a cookie whatever the host page's site or its ancestors' are (#75). Cooperative and worker mode, which keep
  `wss://` entries, count the site of every ancestor the browser keys on, and where the host page's site cannot be decided
  (an opaque origin, a framed page whose ancestors cannot be read) drop the entries that a cookie-carrying request can reach:
  the `wss://` entries in worker mode, every entry in cooperative mode (#78).
  [BD4:DOC-1](#bd4-doc-1) is the same defect.
- **[BD4:CHL-2](#bd4-chl-2)** (a 2 s stall of the host page during the policy read caches "cannot be read", and every build
  keeps its connect lists) and **[BD4:CHL-1](#bd4-chl-1)** (a policy that admits the read's decoy is never read) are fixed by
  deleting the read: the host page's policy comes only from `hostContentSecurityPolicy`, and a build that lists a connect or
  bridge origin without it drops both lists with one warning (#76). `src/lib/host-csp.ts`, its frame, timer and page cache
  are gone, so no timing and no decoy decides anything. [BD4:ISO-2](#bd4-iso-2) (the read's frame throws on a sandboxed
  host page and the build stays `loading`) and its twin [BD4:DOC-4](#bd4-doc-4) are fixed by the same deletion.
- **[BD4:DOC-2](#bd4-doc-2) and [BD4:DOC-3](#bd4-doc-3)** (with `withoutCors`, the layout readback of #74 lets the guest read
  what the user's cookie shows at that origin, and a redirect or an imported stylesheet of that origin reaches every other
  listed origin with its cookies) are fixed by removing the exception (#75): every view load is a CORS request without
  credentials, and CSS keeps no network URL. Nothing is left to document for them.
- **[BD4:LIM-2](#bd4-lim-2)** is refuted after #75 ([the verdict](#verdict-on-bd4lim-2-after-75)): its route needed
  `withoutCors`, and strict mode now drops every string that is an absolute `http:` or `https:` URL wherever CSS holds it.
  The verifier's probes are permanent tests (a table of routes for the scan, a `set({ css })` test through the view, and an
  e2e with a positive control in both host worlds).
- **Verdict changes recorded.** [BD4:NEW-1](#bd4-new-1) is low, docs only (high as filed: the guest learns one bit that
  focus left the view and the modifier keys held during a press that began in the view, as any iframe does; no host data).
  [BD4:CHL-1](#bd4-chl-1) is medium (high as filed: no destination is reached that the guest could not already reach, a
  transport difference; the property "the same on every engine" did fail). [BD4:DOC-2](#bd4-doc-2) and

  (medium as filed: the user's display settings are not an asset of the threat model, and every iframe reads them).
  [BD4:DOC-1](#bd4-doc-1) is a duplicate of [BD4:ISO-1](#bd4-iso-1), and [BD4:DOC-4](#bd4-doc-4) of
  [BD4:ISO-2](#bd4-iso-2). The ISO verifier dropped the Firefox part of ISO-1: what Firefox sends is `SameSite=None` only,

- **Availability findings, backlogged** (they do not count against the pass): [BD4:LIM-3](#bd4-lim-3) (an `on()`/`off()`

#### <a id="bd4-iso-1"></a>BD4:ISO-1: a host page with an opaque origin keeps every `origins` entry, including its own origin and its siblings. On WebKit the guest's WebSocket (and a `withoutCors` view load) carries the host site's Lax, Strict and host-only cookies; on Firefox, its SameSite=None ones

- **Severity:** high. A documented security property does not hold in a documented, supported configuration (#71
  chose to keep the entries, with a warning). The reproduction was executed on all three engines.
- **Effect:** data. The guest sends credentialed handshakes to the user's own site, and to the host page's own origin.
- **Mode:** strict, at its default, with the `origins` opt-in (`connect` with the `wss://` twin; `withoutCors` for the
  view path). Every other mode is the same or worse.
- **Class:** B (a browser decision re-derived). The opaque branch errs toward admitting, but the class chokepoint
  requires that it errs only toward refusing. This is pass 3's high moved into the code that fixed it: the fallback was
  replaced, and the opaque branch still fails open.
- **Code:**
  - `src/lib/host-site.ts:21-23` and `:71`: `onHostSite` returns `false` for `hostOrigin === 'null'`, so "no entry is
    on its site".
  - `src/lib/config-schema.ts:270-271`, `:281`, `:304` and `:316`: `limitHostReach` keeps every entry of an opaque host
    page. Its warning says "a request there carries only that site's own cookies, as any cross-site request does".
  - `docs/API.md:240-241` and `docs/THREAT-MODEL.md:143` and `:325`: "its entries are kept … as a request from it
    carries only another site's own cookies".
  - `src/lib/cookie-facts.ts:16` and `COOKIE_CARRIERS.markup.why`: "`origins.withoutCors` … never the host site's: it is
    refused there as everywhere".

**Path.**
1. The embedder's page has an opaque origin. Either it is served with `Content-Security-Policy: sandbox allow-scripts`
   (a site of user content does this), or it is an `<iframe sandbox="allow-scripts">` of a page on its own site (the
   usual way to embed an untrusted widget or playground). Both are measured.
2. It lists its own API: `origins.connect: ['https://cdn.wsprobe.test', 'wss://cdn.wsprobe.test']`, or even its own
   origin `https://app.wsprobe.test`. `hostPageOrigin()` is `'null'`, so `onHostSite` returns false and every entry is
   kept. The embedder gets the warning above, which says this is safe.
3. The strict worker runs `new WebSocket('wss://cdn.wsprobe.test/…')`. The request gate admits it, because it is listed.
4. WebKit attaches the cookies by the top document's URL (`https://app.wsprobe.test`): S is same-site with it. Firefox
   attaches the target site's SameSite=None cookies, which here are the host site's.

**Reproduction.** `test/e2e/p4-iso-opaque.spec.ts`, tests `strict-default`, `withoutCors` and `nested`. These are the
Cookie headers the listener received. `img` is a view load, `ws` the worker's handshake, and `control` a plain sandboxed
frame of the host page:

| Engine | `S.ws` (sibling) | `H.ws` (the host page's own origin) | `S.img` default | `S.img` with `withoutCors: [S]` |
| :--- | :--- | :--- | :--- | :--- |
| WebKit (CSP-sandboxed page, and nested sandboxed iframe) | `s_none, s_lax, d_none, d_lax, d_strict` | `h_none, h_lax, d_none, d_lax, d_strict` | none (`cors`) | `s_none, s_lax, d_none, d_lax, d_strict` |
| Firefox (both layouts) | `d_none, s_none` | `d_none, h_none` | none | `d_none, s_none` |
| Chromium | none (credentialless wrapper) | none | none | none |

The guest logs show "strict Ready", and the warnings show every entry kept with the opaque-page sentence. WebKit was
rerun alone with the same result. To a page with a tuple origin, the same entries are dropped (`host-site.spec.ts`).

**Why the existing chokepoint and tests miss it.**
- `test/e2e/view-credentials.spec.ts`, the opaque-host world, lists S on purpose ("a sandboxed host page is the one
  through which a same-site target is listed at all"). It checks only the view's loads, which the forced `crossorigin`
  covers. Its listener destroys WebSocket upgrades unread (`server.on('upgrade', … socket.destroy())`), and it never
  uses `withoutCors` in that world.
- `test/unit/host-site.test.ts:62` and `:142` assert the design, "nothing is on the site". No test pairs an opaque host
  page with a carrier the library cannot strip.
- BD3's design premise ("an opaque `self.origin` … its requests carry only SameSite=None cookies, the documented
  cross-site residual", BOARD-PASS-3 §1585) was never measured. On WebKit it is false.

**Suggested fix (by construction).**
- An opaque host origin is **undecided**, not "no site". `onHostSite(_, 'null')` returns true, so every entry is
  refused with the reason "the host page's origin is opaque". The fetch bridge (no credentials) stays the way to reach an
  API. Optionally, admit an entry only when it is off the site of every URL the engines key on (the document's URL
  where it is a network URL, and each `location.ancestorOrigins` entry), and refuse every entry where any of them is
  unreadable. That is the same input as ISO-3.
- Structural test: an e2e over the cookie listener above, for each host-page layout (tuple top-level, CSP-sandboxed,
  sandboxed iframe, embedded cross-site). For each **kept** entry it makes a WebSocket handshake and a `withoutCors`
  load, and asserts that no cookie of the top document's site or of the host page's URL site arrives, on every engine.
  The carrier list should come from `COOKIE_CARRIERS`, so a carrier cannot be left out the way the WebSocket was here.

#### <a id="bd4-iso-2"></a>BD4:ISO-2: on a host page with an opaque origin, a build that lists a connect or bridge origin throws out of `setConfig()`/`reset()` and stays `loading` for ever. The host-policy read touches a cross-origin frame

- **Severity:** medium. This is availability-only with no data effect, and the embedder can end it by passing
  `hostContentSecurityPolicy`. But it hits a configuration the docs call supported (ISO-1's), and the host-policy read
  of #71 is documented to "never answer absent".
- **Mode:** strict at its default with `origins.connect` or `fetchBridge`, and every other mode.
- **Class:** L (a page resource the element holds) and A (the read frame inherits the host page's sandbox flags).
- **Code:**
  - `src/lib/host-csp.ts:164-185` and `:226-228`: the hidden `about:blank` frame inherits the page's sandbox flags, so
    its window is cross-origin. `canFetch()` reads `frame.contentWindow.fetch` outside any `try`, and throws a
    `SecurityError`.
  - `src/lib/host-csp.ts:95-103`: the waiter is pushed before `startRead()` throws. `reading` stays null, the frame
    stays in the shadow root, and the waiter never settles.
  - `src/host.ts:2087-2091` (`_buildGate`) and `src/lib/lifecycle.ts:742-755` (`runBuild`): the throw escapes the
    build effect, which is not guarded. `prepareBuild` and `startLoadDeadline` never run.

**Reproduction.** `test/e2e/p4-iso-opaque.spec.ts`, test "opaque host page: a strict build that lists a connect origin,
with no hostContentSecurityPolicy". The log is `p4iso-read.full.log`. Every engine gives the same outcome:
`setConfig()` throws (Chromium: "Failed to read a named property 'fetch' from 'Window'"; Firefox: "Permission denied to
access property 'fetch'"; WebKit: "Sandbox access violation"). After 12 s there is no `ready` and no `terminated`,
`state` is `"loading"`, and the shadow root holds 1 iframe. `reset()` throws the same, and the shadow root then holds 2
iframes.

**Why the existing chokepoint and tests miss it.** `host-policy-read-race.spec.ts` and `host-policy.spec.ts` run on
tuple-origin pages. The opaque-host world in `view-credentials.spec.ts` lists no connect origin, so the read never runs
there.

**Suggested fix.**
- In `startRead`, wrap the whole frame access (the `canFetch` call and its sequel) in `try`. A frame whose window cannot

#### <a id="bd4-lim-2"></a>BD4:LIM-2 · A bare-string custom property is a load that neither the prepayment nor VIEW_MAX_DISTINCT_URLS sees

- **Severity:** medium. **Effect:** availability-only. **Scope:** strict, with the `origins` opt-in (`withoutCors`).
- **Class:** P (a budget that counts a proxy). B also applies: the model of "what CSS loads" differs from the browser's.
- **Where:** `src/lib/in-sandbox-view.ts:2305` (`CSS_URL`), `:2534` (the distinct check in `applyCss`), `:2536` (`countLoads`), `:1379` (`cssLoadBound`), `:2312` (`cssMayLoad`, the same gap for renders' style attributes).
- **Path:**
  1. The guest renders `<style>#t{background-image:image-set(var(--u) 1x)}</style>`. Its one `image-set(` is counted once.
  2. It then calls `set('t', { css: { '--u': '"https://W/n"' } })` with a new `n` each time, where W is in `origins.withoutCors`.
  3. `cssInto` keeps the string, because W is a withoutCors origin.
  4. `cssLoadBound` counts 0, since it looks only for function tokens and `@import`.
  5. `CSS_URL.test` is false, so past `VIEW_MAX_DISTINCT_URLS` the set is not refused.
  6. The browser loads every new URL. Each load is charged only when its resource-timing entry arrives, after the response ends. That is the S73 "first burst behind a slow server" shape again, and the lifetime distinct-URL cap does not hold. One set can name 16 such properties, so up to 16 loads per frame.
  7. Renders hit the same gap through a style attribute (`style='--u:"https://W/…"'`), because `cssMayLoad` and `cssLoadsOf` use the same counters.
- **Reproduction:**
  - **Unit:** `bunx vitest run test/unit/probe-bd4-lim.test.ts`, block "LIM-2". The view runs as stringified, with `maxDistinctUrls: 1`. `url(W/1.png)` is refused with `VIEW_MAX_DISTINCT_URLS`. - **Fix, by construction:** one load model for both the drop and the count.
  1. Derive the count from `cssReferences(text, 'network')` plus the references that `withoutNetworkReferences` kept: every kept reference counts 1, and an `@import` counts `perSheet`.
  2. Make `CSS_URL` "kept references > 0".

#### <a id="bd4-new-1"></a>BD4:NEW-1: host-page input reaches the strict view's guest (focus moves and keyboard modifiers)

- **Severity:** high (a documented security property does not hold)
- **Data / availability-only / no data effect:** data (host-user activity: focus leaving the sandbox, and host modifier-key state)
- **Strict or not strict:** strict (default configuration, no opt-in)
- **Class (research 18):** A (host-page state a sandbox document receives; the view's input forwarding is the chokepoint)
- **File:line:**
  - `src/lib/in-sandbox-view.ts:286` `VIEW_EVENT_TYPES` adds `focusin`, `focusout` (new in #74; before #74 the list was `click input change submit keydown`).
  - `src/lib/in-sandbox-view.ts:1967-1998` `forward()`: any trusted event of a subscribed type is forwarded. A move outside the box is forwarded when `pressed` and `buttons !== 0` (line 1998), and `entryOf` attaches `modifiers` from that host-originated event (lines 1859, 1875).
  - `src/lib/in-sandbox-view.ts:2005-2010` the listeners for those types are installed on the view's own window, so events caused by the host page's focus moves are delivered there.
  - Claims that are violated: `docs/THREAT-MODEL.md:113` ("the view's input tells the guest about the view only"); `docs/API.md:1344` ("Nothing of your page's own input reaches the guest"); `src/lib/in-sandbox-view.ts:1711-1716` (the same claim in code).
- **Concrete path (all engines):**
  1. Strict embed, `sandboxView.on('focusout', null, …)` and `on('focusin', null, …)` in the worker. The view holds an `<input>`.
  2. The user clicks the view's input, then clicks a `<input>` on the host page, then types into it.
  3. The guest receives `focusin {ids:['field']}`, then `focusout {ids:['field']}` at the host click. Keystrokes typed into the host field do not reach the guest (no `keydown`).
  4. Separately: the user presses the mouse in the view, holds Shift on the host page, and drags out of the view. The guest receives `pointermove` events with clamped coordinates (x=400, y=180 at the edge) and `modifiers.shift === true`, which is the host page's keyboard state.
- **Reproduction (executed):**
  - BD4-A (`bd4-probe.spec.ts`), chromium, firefox and webkit, the same output on each: `[{"label":"pointerdown","x":40},{"label":"focusin","ids":["field"]},{"label":"focusout","ids":["field"]}]`. No `keydown` entry.
  - BD4-G (`bd4-probe-g.spec.ts`), chromium, firefox and webkit: `outsideMoves=[{"label":"move","x":400,"y":180,"modifiers":{"alt":false,"ctrl":false,"meta":false,"shift":true}}]`.
- **Why the existing chokepoint and structural tests miss it:** the chokepoint is an allowlist of event types and the `isTrusted` check. Both are about who dispatched the event (the browser, not synthetic) and what type it is. Neither asks whether the event's cause or its modifier state is inside the view. The tests (`strict-pointer-events.spec.ts`, `strict-focus-events.spec.ts`, `test/unit/view-input.test.ts`) drive input inside the view or clamp coordinates. None drives a host-page focus change, or host modifier state during a held press. Research 23 (`docs/research/23_view_input/README.md:49`, `:148`) reads the lone `focusout` as "focus left the view", which is the design intent, but no embedder-facing text or threat-model row says that the host's own focus moves are visible to the guest.
- **Suggested by-construction fix:** one allowlist of forwarded fields per event type, each marked either "the view's own state" or "geometry inside the box". Then:
  1. Drop `modifiers` from a forwarded event whose pointer is outside the box (or from any event not targeted at a view element).
  2. Forward a `focusout` only when a `focusin` of a view element follows in the same task (an in-view move). A lone `focusout` is dropped. If the owner keeps the lone signal, amend `THREAT-MODEL.md:113`, `API.md:1344` and `in-sandbox-view.ts:1714` to say what it reveals, and add a regression test that pins it.
  3. Structural test: enumerate the inputs of `forward()`, `entryOf()` and `describe()` and fail on any read of host-owned state (a modifier outside the box, a focus change with no in-view counterpart). Use BD4-A and BD4-G as the regression tests.
- **Owner's call:** the content leaked is small (one focus-left event per host focus change, and the modifier flags during an in-view press; no keystrokes, no host coordinates, no host content). The severity is high only because the threat-model row is a stated guarantee. If the owner decides the signal is acceptable and documents it, this becomes a docs-drift item, not a finding.

#### Root cause and recommendation

Both findings sit in `src/lib/host-csp.ts`, which #71 (BD3:CHL-1's fix) rewrote: the evaluation rule of research 22 ("a
pass's data findings sit in code that the previous pass's fixes added") triggers again, and research 22 says that if
pass 4 still finds host-adaptation data findings, the served-document mode is taken up.

The root cause is the read itself: it predicts the effective `connect-src` of a sandboxed `srcdoc` document from one
browser decision on one URL in a different, unsandboxed `about:blank` frame, under a time bound. One URL cannot
characterise a policy (CHL-1); a time bound on the host's thread is another prediction (CHL-2); and the frame cannot
show the sandbox document's own reading (WebKit's `'self'` differs there), which is why the library re-parses the text.

- **A decoy set (http, https, ws, wss, custom scheme) and timeout -> `undefined`, uncached**: fixes both measured cases,

  prediction. Not recommended as the fix.
- **Test each listed origin instead of a decoy**: unsound. A request that cannot leave needs the refused port, which
  changes the origin (a policy naming `https://O` refuses `https://O:6000`, so a good entry is dropped), or else it
  connects to O; and it still runs in a frame whose `'self'` is not the sandbox document's.
- **Recommended, by construction: no read.** When `origins.connect` or `fetchBridge.allow` is non-empty, take the page's
  policy only from `hostContentSecurityPolicy` (a text, or `false` to state that none applies); absent, drop both lists

  promise (the embedder's lists are the authority; the host page's `connect-src` is applied only by the browser, per

  the hop, or the text of X's sheet. The view's CSP admits every *listed* origin on the hop.
- **What the docs claim for a listed origin that is not in `withoutCors`.** README:698/711: "every load of the view send
  none, on any engine … except … `origins.withoutCors`, which carries that origin's own cookies". THREAT-MODEL:392:
  "neither does any load of strict mode's view but one to an origin of `origins.withoutCors`". THREAT-MODEL:415, API.md
  `#the-views-loads` ("no cookie of any kind"). The e2e title in `view-credentials.spec.ts:359`: "…every other keeps the
  rule". All of them say Y receives no cookie on any engine. On Firefox and WebKit, Y receives its `SameSite=None` cookie
  on four load kinds, so the documented property is false.
- **The read follows the same path.** Through the hop, a redirected `<img>` gets its size, and an `@import`ed Y sheet
  affects layout. With #74 the guest reads Y's credentialed responses as in DOC-2. That covers every listed
  images/media/styles origin, not only the one the embedder opted out.
- **Is the precondition realistic? Yes, moderately.** An open redirect on X is enough, and so is X serving content the
  guest controls. The guest picks X's path. A `withoutCors` candidate is typically a CDN or file host without ACAO. Hosts
  that serve user-uploaded files (raw-file CDNs, user content) let the guest publish a sheet that names any listed origin.
  No redirect is needed then. X's own legitimate CSS that references a second CDN also triggers it, with no attacker
  content. Engine reach is the same as DOC-2: Firefox without TCP, WebKit outside Safari's default. Chromium is safe.

**Minimal by-construction fix.** A CSP source list cannot tell "no-cors allowed" from "CORS only", and the hop is the
browser's. So close the mix in config (`config-schema.ts`, one rule): when `withoutCors` is non-empty in strict mode,
every origin of `images`, `media`, `styles` and `fonts` that is not in `withoutCors` is dropped, with a warning naming it
("a withoutCors origin can redirect or import to it with its cookies"). Then "only `withoutCors` origins receive their
own cookies" holds by construction, because they are the only listed load origins. The weaker alternative is docs only:
state that with `withoutCors` non-empty, every listed images/media/styles/fonts origin may receive its own cookies.
Structural test: this probe as an e2e, asserting that Y gets no cookie on any engine and no hop to Y is admitted.

#### BD4:DOC-5: CONFIRMED-WITH-CHANGES. Low, no data effect on a listed asset (a docs inaccuracy). Not medium.

**Measured** (`page.emulateMedia({colorScheme})`; guest CSS `@media (prefers-color-scheme: dark)` widens `#s0` in a 1x1
box; two stacked elements, the top one hidden in dark mode; a trusted click at their spot; the control is a sandboxed
`srcdoc` iframe running `matchMedia`):

```
all three engines  light: before any input {"width":11}; after a user click {"click":"a"} | opaque iframe matchMedia(dark)=false
all three engines  dark:  before any input {"width":30}; after a user click {"click":"b"} | opaque iframe matchMedia(dark)=true
```

**The answers.**
- **The technical claim holds.** Since #74, a strict guest reads the user's media features with no input. A worker has
  no `matchMedia`, `devicePixelRatio` or `screen`.
- **Earlier channels already exposed these.** (1) Any cross-origin, even opaque, iframe reads them directly through
  `matchMedia`, and so does every cooperative-mode guest. (2) The strict view before #74 exposed them only behind a user
  gesture. The click detail's target `id` (unchanged by #74) tells which media-dependent element was under the click: the
  measured `a`/`b`. The same applies to the `input`/`change` targets. Auto-resize goes to the host only (RESIZE), and
  `violation` goes to the host only, so neither reached the guest. #74's change is the step from "after a user click" to
  "without input".
- **No documented asset is touched.** The THREAT-MODEL assets (line 29) are the host page's DOM, storage, cookies, the
  user's session, the URL and origin, the thread, exposed methods and data handed to the guest, and other sandboxes. The
  user's display and accessibility preferences are not among them. "CSS-based probing of the view's own content" is out
  of scope (line 277). The research 23 claim "less than any cross-origin iframe gets" stays true, because an iframe gets
  `matchMedia`. The THREAT-MODEL:113 row "tells the guest about the view only" is defensible: media features are the
  view's rendering environment. It is incomplete, though.
- **What is actually wrong.** Research 23 §3.1, row "Layout readback", "Already available to: the worker has
  `OffscreenCanvas` `measureText`". That is false for media features: measureText gives font metrics, not color scheme,
  motion, contrast, pointer or resolution.

**Minimal fix.** Docs only.
- Add a research 23 §3.1 row: "Media features (color scheme, reduced motion, contrast, forced colors, hover/pointer,
  resolution, screen size) | the user's display and accessibility settings | any iframe and cooperative guest
  (`matchMedia`); strict before #74 only through a click's target | readable through layout readback, without input".
- Reword THREAT-MODEL:113 to "about the view and its rendering environment (the media features any iframe reads)".
- If the owner adds the user's preferences to the assets, it becomes a fingerprinting item for the ledger. Quantising the
  readback (no `@media` in the view's CSS whenever a readback is subscribed) would be the chokepoint. It is
  disproportionate for a surface every iframe has.


### Verdict on BD4:NEW-1

Reproduced on chromium (load was 10.7, so one engine only): BD4-A gives pointerdown, focusin{ids:[field]}, focusout{ids:[field]} and no keydown;
BD4-G gives one outside move {x:400,y:180, modifiers.shift:true}. Both match the reviewer. Probes were run from a copy and removed; no src/ change.

1. What reaches the guest
 - focusout: the view document's own focusout for a view element ("this element of yours lost focus"). Its cause is a host click, but the
   payload is the view's own ids and nothing else (no relatedTarget, no host element, no coordinates). The guest learns one bit plus timing: focus left the view.
 - Modifier flags: the browser's own modifier state on a pointermove that the view document receives during a press that began in the view.
   Coordinates are clamped to the edge. Only those four booleans are forwarded.
 - No keystroke (keydown never arrives for host typing), no host-page coordinate (clamped), no host element identity.
 - A modifier held during the user's own in-view drag is the user's gesture state. It is host input only in the sense that the Shift key was pressed on the host page.
2. Versus the browser
 - The library forwards nothing the view document does not already get. Any cross-origin iframe sees window blur/focus and document.hasFocus() for the
   same event, and receives captured moves past its edges (every engine, with or without capture) with ctrlKey/shiftKey etc. on them. The view frame
   already had both before #74. #74 only relays them to the worker, which is the view's owner. It is less than an iframe: it
   clamps coordinates, and the lone focusout carries no relatedTarget.
3. Classification: no host data leaks and the guest cannot manipulate anything across the policy. The effect is a one-bit focus-left signal and four booleans during a
   drag the user started in the guest's view. Board rule: high needs a documented property that fails with a real data effect. Here
   the effect is nil or negligible, so it is not high. The wording in THREAT-MODEL.md (row "the view's input tells the guest about the view only"), API.md ~1344
   ("Nothing of your page's own input reaches the guest") and the comment at in-sandbox-view.ts:1711-1716 is imprecise, so low (medium at most) docs-precision.
4. Research 23 already documents the focusout behaviour: README.md:49 ("a focusout with no focusin after it means focus left the view") and :148
   (focusin/focusout "when the user enters or leaves the view's controls", "iframes (the window's blur and focus)", forwarded without relatedTarget).
   Not documented there: modifier flags on an outside move during an in-view press (row :143 covers position only; :145 says "nothing of the host page's input reaches the view").
   So the focus half is documented in research and only missing from the embedder-facing text; the modifiers half is undocumented.
5. Minimal fix: docs only. In API.md ~1344 and the THREAT-MODEL row, say "Nothing of your page's own keystrokes, coordinates or elements reaches the guest. It learns
   that focus left the view (a focusout without relatedTarget) and, for a move outside the view during a press that began in it, the modifier keys held, as any
   iframe's document does." Fix the code comment in the same way, and add the modifiers to research 23 row :143. Optional code (not needed, and
   it breaks shift-constrained drags that cross the edge): zero modifiers when a pointermove is outside the box.


### Verdict on BD4:LIM-2 (after #75)

#### Verdict: REFUTED (no load)

No guest-CSS route makes any network load to a listed cross-site origin X in strict mode on
Chromium, Firefox or WebKit. The LIM-2 route was found while `origins.withoutCors` still existed
(#75 removed it). Post-#75 the view drops **every** network URL in guest CSS by construction:
`withoutNetworkReferences` over `cssReferences(text, 'network')` (`src/lib/css-references.ts`) emits
a reference for any **string or url token** whose decoded value `isNetwork` (absolute http(s)),
anywhere outside a non-`@import` at-rule prelude — custom-property strings, `image-set()`,
`content`, `cursor`, `list-style-image`, and `src()`/`url()` in `@import`/`@font-face` included —
and `withoutNetworkReferences` rewrites each to `""`. This runs on `render()`, `<style>` text,
style attributes, `set({ css })` values (`applyCss` -> `cssInto`, `in-sandbox-view.ts:2495`) and
registered stylesheets alike, so the LIM-2 path (`--u:"https://X/.."` consumed by
`image-set(var(--u))`, via `set({ css })` or `<style>`) is dropped before the browser sees it.
