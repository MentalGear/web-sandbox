#### <a id="bd1-iso-1"></a>BD1:ISO-1: the fetch bridge runs in the host page's own fetch environment (its Service Worker and any `fetch` wrapper), so it gives the guest more than a direct request would

- **Severity**: high. It needs a non-default, documented configuration (`fetchBridge`) and a realistic precondition on the
  host page. A documented security property does not hold under it: ADR-006's "bridge discipline", which promises
  `credentials: 'omit'`, `cache: 'no-store'`, header allowlists and "the bridge grants no more than a direct guest request
  would". The guest reads the signed-in user's data, or requests carrying the user's token.
- **Class**: E-net, in the bridge's channel. The bridge's request leaves through a host path that the bridge's own rules
  do not govern. In research 18's terms it is close to B: the bridge assumes the page's `fetch()` is the platform's
  network fetch, which is a browser and environment decision it re-derives.
- **Where**:
  - `src/lib/fetch-bridge.ts:626`: `await (fetchImpl ?? globalThis.fetch)(outgoing, init)`. `host.ts` passes no
    `fetchImpl` (`src/host.ts:1721`), so this is the host page's `globalThis.fetch`, read at call time.
  - `src/lib/fetch-bridge.ts:8-20` and `docs/ADR-006-fetch-bridge.md:13, 43`: the discipline as stated.
  - `docs/THREAT-MODEL.md:115`: the egress row "The fetch bridge sends only what the embedder allows".
- **Path**:
  - **(a) The Service Worker.** The guest calls `sandboxFetch('https://api.example/me')`, and `api.example` is in
    `fetchBridge.allow`. The broker calls `sandbox:fetch` and `validateRequest` passes it. Then `fetch(Request, init)`
    runs in the host page's window. If that page is controlled by a Service Worker, the request is a fetch event of
    that worker.
    - A cache-first or stale-while-revalidate worker answers from its cache, by URL. This is Workbox's runtime-caching
      shape, and common in PWAs for their API origin. The cached response is whatever the host app stored for that
      URL, typically a credentialed response with the user's private data.
    - `credentials: 'omit'` and `cache: 'no-store'` are fields of the request that the worker is free to ignore.
    - A direct guest request comes from an opaque origin, which no Service Worker ever controls, so it gets none of this.
  - **(b) A `fetch` wrapper.** The bridge reads `globalThis.fetch` when it makes each request. So any wrapper the host
    app installed runs on the guest's request. Examples are an auth wrapper that adds `Authorization: Bearer <token>`
    for the app's API origin, and APM or tracing wrappers. The wrapper adds headers that the bridge's header
    allowlist never admits: `Authorization` is admitted only when listed, and `Cookie` never. The guest then receives
    the authenticated response.
- **Reproduction**: `test/e2e/p1-iso-probe6.spec.ts` with `test/e2e/p1-iso-sw.js`, a 7-line cache-first worker.
  Command: `bunx playwright test test/e2e/p1-iso-probe6.spec.ts --project=chromium --project=firefox --project=webkit`.
  Both tests assert the property, and they **fail** on the current code:
  ```
  chromium controlled: true guest got: {"status":200,"text":"PRIVATE-USER-DATA of the signed-in user"} network hits: []
  webkit   controlled: true guest got: {"status":200,"text":"PRIVATE-USER-DATA of the signed-in user"} network hits: []
  firefox  controlled: false (Playwright's Firefox did not let the worker control the harness: not evidence either way)
  chromium guest saw its request as: {... "authorization":"Bearer USER-SESSION-TOKEN", "origin":"http://localhost:27344" ...}
  firefox  guest saw its request as: {... "authorization":"Bearer USER-SESSION-TOKEN" ...}
  webkit   guest saw its request as: {"authorization":"Bearer USER-SESSION-TOKEN", ...}
  5 failed, 1 passed (Firefox (a), uncontrolled)
  ```
  In (a) the network saw nothing (`network hits: []`). The guest's credential-less, no-store request was answered from
  the host app's cache. In (b) the recorder's `/echo` shows that the request which left carried a header that
  `fetchBridge.headers` did not list.
- **Why the existing chokepoint and tests miss it**:
  - `createFetchBridge` and `validateRequest` decide what `RequestInit` says. Nothing decides what context executes it.
  - `fetch-bridge.spec.ts` runs on a harness that has no Service Worker and an unwrapped `fetch`.
  - The bridge's unit tests inject `fetchImpl`.
  - The threat model's out-of-scope entry, "a compromised host page", does not cover this. A caching Service Worker
    and an auth wrapper are ordinary embedder code, and the docs never say that the bridge runs through them.
- **Suggested fix, by construction**: one chokepoint for the context a bridge request runs in, and a structural test for
  it.
  1. Capture the platform's `fetch` once, at module evaluation, and never read `globalThis.fetch` per call. This closes
     (b) for wrappers installed after the import.
  2. Make (a) a stated precondition, or remove it:
     - A page `fetch()` cannot opt out of its Service Worker. So either issue the bridge's requests from a context no
       worker controls, or check for one. Such a context is a library-owned sandboxed iframe or a `data:` worker with
       an opaque origin, which matches "no more than a direct guest request" exactly, `Origin: null` included.
       ADR-006 would have to revisit its choice of the host origin in `Origin`.
     - Or refuse or warn while `navigator.serviceWorker.controller` is set, and document in API.md and ADR-006 that
       a controlling Service Worker handles every bridge request.
  3. Structural test: an e2e spec that runs the bridge's suite on a harness with a cache-first Service Worker and a
     header-adding `fetch` wrapper, the two probes above, on every engine.

#### <a id="bd1-iso-2"></a>BD1:ISO-2: the `keepalive` guard is shadowable in worker realms: the platform's `fetch` stays on `WorkerGlobalScope.prototype`

- **Severity**: low. There is no egress today: Firefox's worker `fetch` with `keepalive: true` is refused by
  `connect-src`. But the guard does not hold where the source says it holds.
- **Class**: G, guest-controlled state around library code. The guard relies on shadowing, not on the capture.
- **Where**:
  - `src/lib/in-sandbox-script.ts:299-319` claims "Every engine, every mode … not configurable, so the guard stays
    underneath any wrapper". It installs the guard as an own property on the global (`:319`).
  - In a dedicated worker the platform's `fetch` lives on `WorkerGlobalScope.prototype`, in all three engines.
    `WORKER_GLOBALS` keeps both `fetch` and `WorkerGlobalScope` (`src/lib/worker-globals.ts:54, 56`), so the original
    stays reachable.
- **Path**: guest code in the strict or worker-mode worker runs
  `Object.getOwnPropertyDescriptor(WorkerGlobalScope.prototype, 'fetch').value.call(self, url, { keepalive: true, … })`.
  That is the platform's fetch, without the guard.
- **Reproduction**: `test/e2e/p1-iso-probe.spec.ts`, all engines, strict, worker and cooperative mode:
  ```
  <engine> strict|worker {"own":true,"protos":["WorkerGlobalScope"],"nativeFound":true,
     "guarded":"TypeError: fetch() with keepalive is not available in the sandbox","native":"TypeError: …", …} blocked hits: []
  <engine> cooperative   {"own":true,"protos":[],"nativeFound":false, …}
  ```
  The native path is reached in every engine's worker. It is refused today only because each engine's worker applies
  `connect-src` to keepalive. In the document (cooperative mode) `fetch` is an own property of `window`, so the guard
  does replace it there.
- **Why it is missed**: PD2 (`test/e2e/guest-realm-hardening.spec.ts:235`) calls the global `fetch` only. V1's
  `ATTEMPTS` has no keepalive attempt.
- **Fix**:
  - In worker realms, define the guarded `fetch` on the owner the platform used, `WorkerGlobalScope.prototype`, as
    non-configurable, or delete the prototype's copy. A guard is then never only a shadow.
  - Structural test: for each guarded name, the read-once and capture scan asserts that no prototype on the global's
    chain still holds the original.
  - Add a keepalive attempt to V1's `ATTEMPTS`.

#### <a id="bd1-iso-3"></a>BD1:ISO-3: cooperative mode, the guest replaces its own document without being ended, and the replacement has none of the bootstrap's hardening

- **Severity**: low. It is the same capability as the documented "a frame the guest creates is a realm of its own"
  (S44 and S13). But it contradicts the threat model's lifecycle row and widens the WebRTC note.
- **Class**: L, with E-net in cooperative mode only.
- **Where**: `docs/THREAT-MODEL.md:152` says "A guest that reloads or rewrites its document is ended". The `frameLoad`
  and `announced` inputs only see the wrapper's load and a second announcement.
- **Path**: guest code runs `location.href = 'about:blank'`, or `document.open(); document.write(…)`, or, in WebKit,
  `location.href = 'javascript:"<script>…"'`.
  - The about:blank navigation does not fire the wrapper's load, because the guest frame is its child. The rewrites
    post no announcement unless they run a bootstrap. So the element stays `ready` and the guest's port is dead.
  - In WebKit the `javascript:` replacement document is a new realm without the bootstrap. `new RTCPeerConnection()`
    succeeds there, in the guest's own frame, not only in frames it creates. The guest policy stays in force: nothing
    reached the blocked listener.
- **Reproduction**: `test/e2e/p1-iso-probe5.spec.ts`:
  ```
  webkit javascript allowed: ["/p5-javascript-control","/p5-javascript-rtc-present"] events: [] state: ready
  <all>  open       allowed: ["/p5-open-control"] blocked: [] events: [] state: ready
  <all>  blank      events: [] state: ready
  ```
  Also seen while probing: a click on `<a href="#x">` in the guest navigates the guest frame to `about:blank#x`,
  because the base is `about:blank`. It is a cross-document navigation, and nothing ends the environment.
- **Fix**:
  - Narrow the threat model row to "a guest that loads a document which runs a bootstrap again, or reloads the wrapper".
  - Add document replacement and self-navigation to `about:blank` to S44's frozen list, next to S13's "frame the guest
    creates". Cooperative mode takes no new patch under the owner's rule.

#### <a id="bd1-iso-4"></a>BD1:ISO-4: the `origins.connect` reference says the wrong thing for strict and worker mode, and leaves out what an `https:` entry opens

#### <a id="bd1-lim-1"></a>BD1:LIM-1: the uncaught budget's character count fails open for a rejected Error that carries a `Symbol.toStringTag`; Firefox's host page is frozen for as long as the guest keeps it up

- **Severity:** high. A budget that fails open in the default configuration (strict mode, also worker mode by the same
  code). The documented bound on Firefox's host-thread cost ("past them the sandbox ends") does not hold, and the stall
  is bounded by nothing the library states.
- **Class:** G (library code decides what to count from state the guest controls: the reason's `Symbol.toStringTag`),

- **Guest writes:** rates are counted before the work.
- **structured-size, besides BD1:LIM-3:** getters and Proxies are never measured live, because the snapshot comes

- strict, 128 Mi-character messages (load 1.0): ran at +1003 ms; 1679 ms after it.

The reviewer saw 1.3 s late and about 5 s of stalls after `terminate()` at load 6 to 19. That fits a shared machine.
The time after `terminate()` is the reports Firefox had already queued. The browser's queue bounds it. No library
limit does.

**Is it bounded by anything the library states?** No. The documented bound (API.md budgets row; egress.ts
`UNCAUGHT_CHARACTERS_PER_SECOND`; THREAT-MODEL row 194) is "bounded by the count and the characters, past them the
sandbox ends". The character half fails open. The count (1000/s) does not bound the cost, because each report's cost
grows with message length, and only the character budget limits that. Without the embedder acting, the sandbox stays
`ready` for as long as the guest keeps it up. A single stall of 5 to 7.6 s also delays any `terminate()` the
embedder schedules.

**Severity: high.** A budget that fails open in the default config (strict, also worker) falls under CONTRIBUTING
exception 3, so it is not an availability finding. The stall is also bounded by nothing the library states
(exception 1). It is not critical, since no host state is read or changed and nothing is exfiltrated.

**Fix by construction.**
- *Chokepoint:* `reportOf` counts characters for every object reason, not only error-like ones, with no gate on the
  tag. Read `name` and `message` once each, own or inherited, and count their lengths. Over-counting is allowed
  ("err toward refusing").
- *Structural test:* a unit property test over a closed list of reason shapes, checking that `characters` is at least
  the length of every string reachable as `name` or `message`. The shapes: Error, own-tagged Error,
  `Error.prototype`-tagged Error, DOMException, DOMException tagged by defineProperty, a subclass, a Proxy of an Error,
  a plain object, an array, a string.
- *e2e:* add the tagged reason to N-1 (`test/e2e/error-cost-and-queued-calls.spec.ts`) on Firefox, asserting that the
  sandbox ends with `uncaughtBudget`.
- *Scan:* no budget decision in the bootstrap may branch on `tagOf` of a guest value.

#### BD1:LIM-2: on desktop Chromium the isolated view misses its liveness check during one documented stall. CONFIRMED, medium

Desktop Chromium is installed at `/opt/pw-browsers/chromium-1208` (145.0.7632.6). I ran the reviewer's probe with
`PROBE_CHANNEL=chromium` (load 2.2 at the start, 3.7 at the end):
- bidi paragraph, 240 000 characters: **terminated after 5730 ms, `the sandbox view stopped responding`**; longest
  host stall 12 ms. The 12 ms confirms the view runs in its own process.
- `:has()` over 37 000 later siblings: ready, with the first-overrun warn line. At this lower load the operation
  finished in under 5 s. The reviewer, at a higher load, saw it end. So the outcome depends on whether one operation
  takes longer than `VIEW_LIVENESS_TIMEOUT_MS`, which the machine's load affects.

The reviewer's headless-shell control (ready, first-overrun line, the host stalled 44.7 s and 4.7 s) matches the
mechanism: on a shared thread a view stall is a host stall, and host stalls are not counted.

**Intended or not.**
- API.md (b) says the first overrun is survived, and that a single stall is bounded by the caps of (c). It says
  nothing of the liveness check.
- ADR-005 A5 states the purpose of liveness: Chromium's error page (P4) ends view and worker silently, with "host
  stalls not counted".
- API.md's process table puts desktop Chromium 127+ first, with the view in its own process.

So the liveness check was never meant as an operation bound. On an isolated view it ends a sandbox that (b) says
survives.

**Severity: medium.** This is CONTRIBUTING exception 2: the library's own limit ends a healthy sandbox, a correctness
bug. It fails closed (the sandbox ends), so it has no security effect. Docs (b) are wrong on the engine they list
first.

**Fix by construction.**
- *Chokepoint:* one predicate rules on a busy view, the repeated-overrun rule. The view posts `VIEW_BUSY` before each
  flush and `VIEW_IDLE` (or its next PONG) after it. The host's view watchdog does not count ticks while an announced
  operation is open. The P4 error page still goes silent without a BUSY, so it is still caught.
- *Structural test:* a Playwright project with `channel: 'chromium'`, running `test/e2e/view-bound.spec.ts` (b) and
  asserting the same verdicts as the shared-thread engines. Fallback if that is not wanted: state the 5 s outer bound
  in API.md (b) and (d) and in the reasons table.

#### BD1:LIM-3: a sparse array measures 16 bytes. CONFIRMED-DIFFERENT-SEVERITY: high, and the stall is in library code, not the embedder's

The reviewer said the cost was the embedder's `String(args)` (the harness and the playground). It is not. **The
library's own `freezeDeep` (`src/lib/element-events.ts:55-56`) runs
`for (let i = 0; i < object.length; i++) keep(object[i])` on the host page's thread for every array in every
`sandbox-log` detail.** For an array of length 2^32-1 that is about 4.3 billion iterations. It runs at every dispatch
(`host.ts:1597`, `_dispatchLog` → `elementEvent` → `freezeDeep`), with or without a listener, before any listener
runs.

**Evidence.**
- *The library's path alone* (`v1-lim-sparse.spec.ts`): my element listener calls `stopPropagation`, so the harness's
  `String()` never runs. Guest code: `a=[]; a.length=2**32-1; a[5]=1; console.log(a)`. Chromium headless shell, load
  2.6: **strict, the event arrives after 88.5 s, host stalled 88 532 ms; worker mode, 90 455 ms**. The sandbox stays
  ready. The arrival has `length` 4294967295 and 1 key, so the clone keeps the array sparse.
- *The clone itself is cheap* (`v1-sparse-micro.mjs`, Chromium): structuredClone 2 ms, a MessagePort round trip 3 ms,
  `Object.keys` 0 ms, dispatching a shallowly frozen event 0 ms.
- *Hypothesis test:* I patched `freezeDeep` to walk `Object.keys` for arrays, re-ran (load 2.0), then reverted. Strict:
  arrival at 6 ms, longest host stall 2 ms. Worker: 5 ms and 3 ms. The whole stall is `freezeDeep`.
- *Per engine, length 2^28* (`v1-lim-sparse-term.spec.ts`, load 3.7):
  - Chromium: 3056 ms per line, so about 49 s for 2^32.
  - Firefox: 499 ms per line, so about 8 s for 2^32.
  - WebKit: the line never arrived, and the host had no cost.
- *Can the embedder end it?* 10 lines of 2^28, `terminate()` scheduled at +1000 ms (load 2.9):
  - Chromium: **one stall of 33 086 ms. `terminate()` ran only after every queued line was processed**, because the
    port's message tasks ran ahead of the timer.
  - Firefox: `terminate()` ran at +1980 ms, between lines.

**The documented property, and how it breaks.** The byte measure is accurate for what structured-size.ts defines (the
bytes clone copies), and the clone is small. But the library rests a host-thread cost bound on that measure:
- `element-events.ts` header: freezeDeep "is bounded by what a detail can hold: a log line measures at most
  LOG_MAX_BYTES on receipt … freezes in 8–12 ms".
- API.md budgets, the log-lines row: cost "none beyond the count and the bytes".
- API.md `sandbox-log`: "`LOG_MAX_BYTES` bounds all arguments of a line together, whatever they are".

freezeDeep walks by `length` and the measure counts by keys, so the budget fails open for the library's own work.

**Bound.** One 16-byte line costs about 49 to 90 s in Chromium. The guest's relay passes 1000 such lines a second
(LOG_EVENTS_PER_SECOND; 4 MiB/s is about 260 000 lines of 16 bytes, so the count is the limit), which is up to about
13 hours of host thread per guest second. `terminate()` cannot run on Chromium until the queued lines drain. So the host
page is frozen beyond the embedder's reach, by default (strict and worker; cooperative mode probably too, since it uses
the same dispatch; not run).

**Severity: high.** It falls under CONTRIBUTING exceptions 1 and 3: the host page can never regain control in
practice, and the byte budget fails open for the library's own walk. The embedder's own `String()` (harness,
`playground/playground.ts:128`) adds a second stall of the same order, as the reviewer reported. That part alone would
be a docs or harness issue (medium at most). It is not critical, because no data crosses the policy.

**Fix by construction.**
- *Chokepoint 1:* `createSizeOf` charges an array by its extent: `max(8 * length, keys)`. Over-counting relative to
  clone is allowed ("err toward refusing"). A sparse array of more than about 130 000 slots then goes past
  `LOG_MAX_BYTES` and `RPC_MAX_BYTES`. That makes "bounds all arguments whatever they are" true for every walk,
  including the embedder's.
- *Chokepoint 2:* any library walk over a detail visits only what the measure counted. Make `freezeDeep` iterate
  `Object.keys` (or the measure's own key list). Defense in depth.
- *Structural test:* a property test (fast-check) over generated snapshots, sparse, holey and large-`length` arrays
  included. For each, the steps freezeDeep takes and `String(value).length / 2` are at most k × `sizeOf(value)`.
  `test/unit/element-events.test.ts` measures freezeDeep only on the densest dense line.

**Shared root cause with BD1:CHL-2 (Blob/File measured as 64 bytes).** Both come from structured-size's per-type
formulas measuring a proxy instead of everything the receiver gets:
- for arrays, own keys and not `length`;
- for File and Blob, a constant and not the `name` and `type` strings clone copies.

The existing structural tests compare the measure with clone only on dense samples with no handles. One fix covers
both: each allow-listed type's formula is the sum over every field the clone carries or a host walk reads (`length`,
`name`, `type`). The property test above then gets generators for File and Blob with long `name` and `type`, and for
sparse arrays.

### Verdict on BD1:ISO-1

**Verdict: CONFIRMED, high.**

Reviewed at `9141e4ed37e97002737d7f13e88a1508bed2bcaa`, in the detached worktree
`<the reviewer's worktree>`. `src/` was not changed. Engines: Playwright's
Chromium 145, Firefox 146 and WebKit 26.

The probes are untracked files in that worktree:
- `test/e2e/p1-iso-probe6.spec.ts` and `test/e2e/p1-iso-sw.js`, copied from the reviewer;
- `test/e2e/v1-iso1-fixes.spec.ts`, which shows which fetch contexts the host page's Service Worker controls and which
  ones a host `fetch` wrapper reaches;
- `test/e2e/v1-iso1-xrealm.spec.ts`, which runs the bridge's exact `fetch(Request, init)` call through the `fetch` of a
  fresh realm.

#### 1. Reproduction, per engine

Command: `bunx playwright test test/e2e/p1-iso-probe6.spec.ts --project=chromium --project=firefox --project=webkit`.
Result: 5 failed, 1 passed, the same as the reviewer's run.

| | (a) cache-first Service Worker on the host page | (b) host `fetch` wrapper that adds `Authorization` |
| :--- | :--- | :--- |
| Chromium | Controlled. The guest got `PRIVATE-USER-DATA of the signed-in user`, and the network saw 0 requests. | The target received `authorization: Bearer USER-SESSION-TOKEN`. Through `/echo`, the guest read the token back. |
| WebKit | Controlled. The same result: the private data, 0 network hits. | The same as Chromium. |
| Firefox | The worker never controlled the harness under Playwright, in every context I tried. This is a harness limit, not evidence of safety. | The same as Chromium. |

Effect (b) is not limited to an echo endpoint:
- The guest's request now carries the user's credential. The bridge makes `GET`, `HEAD` and `POST` by default, so the
  guest can read the user's private data from the listed API and make state-changing `POST`s as the user. This is a
  confused deputy.
- The guest sees the token itself only if the listed origin reflects it, or if the guest controls that origin.
- A wrapper scoped to the app's own API sends nothing to an origin the attacker owns. Global wrappers do: APM and
  tracing SDKs (Sentry `sentry-trace`/`baggage`, Datadog `traceparent`) add headers to each origin on their target
  list. The bridge's header allowlist was meant to rule all of this out.

#### 2. What the library promises

The library promises the opposite of this behaviour, without conditions:
- `docs/ADR-006-fetch-bridge.md`: "the bridge grants no more than a direct guest request would". The Consequences
  section says "no `Cookie`, `Authorization` or `Referer` reaches the target". Effect (b) breaks this directly.
- `docs/API.md` §`fetchBridge`: "Every request the host makes is pinned to no credentials … `cache: 'no-store'`".
- The `src/lib/fetch-bridge.ts` header comment, and the egress row of `docs/THREAT-MODEL.md`: "The fetch bridge sends
  only what the embedder allows".

No public document says that a bridge request goes through the host page's Service Worker or through its patched
`fetch`. The `fetchBridge` opt-in warning names only `Origin`. `fetchImpl` does not appear in any doc.

**Is this the embedder's choice?** The threat model trusts the embedder's scripts not to be hostile. It does not say
the embedder accepts having ambient app code (a caching worker, an auth or APM wrapper) applied to requests that the
guest triggers.
- The library chose the context the request runs in (`globalThis.fetch`, read on every call).
- The embedder chose only the allowlist, relying on the documented discipline.
- The attacker is the guest. It gets data and authority that the embedder's policy said the bridge never grants: the
  host app's cached, credentialed responses, and requests made with the user's bearer token.
- The out-of-scope entry "a compromised host page" does not apply here: nothing on the host page is compromised.

So this is a documented security property that does not hold, not a gap in the docs.

#### 3. The `fetchImpl` option

`FetchBridgeOptions.fetchImpl` (`src/lib/fetch-bridge.ts:490`) is documented as "The fetch to use; the page's by
default". It is internal:
- It is not part of the public `fetchBridge` config.
- `host.ts:1721` never passes it.
- Only the unit tests inject it (`fetch-bridge.test.ts:118`, `:239`).

It shows that the code knowingly uses the page's `fetch` as the default. It also gives an existing seam for any of
the fixes below. It does not count as a documented warning to embedders.

#### 4. Fix options, as tested

Matrix from `v1-iso1-fixes.spec.ts`. "SW" means the host page's cache-first Service Worker answered the request.
"wrapper" means the host's `Authorization` wrapper applied to it.

| Context the request runs in | Chromium | WebKit | Firefox | `Origin` sent |
| :--- | :--- | :--- | :--- | :--- |
| Host page `fetch` (today) | SW, wrapper | SW, wrapper | wrapper (no SW control in the harness) | host |
| Same-origin `about:blank` iframe's `fetch` (a fresh realm) | not SW-controlled, no wrapper | **SW** (the frame inherits the controller), no wrapper | no wrapper | host |
| Same-origin `srcdoc` iframe | **SW**, no wrapper | **SW**, no wrapper | no wrapper | host |
| `blob:` worker created by the host | **SW**, no wrapper | **SW**, no wrapper | no wrapper | host |
| `data:` worker (opaque origin) | not SW-controlled, no wrapper | not SW-controlled, no wrapper | no wrapper | `null` |
| Sandboxed `srcdoc` iframe (`allow-scripts`, opaque origin) | not SW-controlled (the frame has no `navigator.serviceWorker`: `SecurityError`), no wrapper | the same | no wrapper | `null` |

The candidates, one by one:

- **Capture `fetch` once, when the module is evaluated.** This closes (b) only for wrappers installed after the
  library's module runs. APM snippets in `<head>`, and auth modules that are imported first, run before it. It does
  nothing for (a). It is not a construction.
- **Take `fetch` from a fresh same-origin realm** (a hidden `about:blank` iframe that the library owns). It closes (b)
  on all three engines. `v1-iso1-xrealm.spec.ts` confirms the bridge's exact call works there:
  `realm.fetch(new Request(url, init), init)` with a `Request` from the host realm succeeds on all three engines, sends
  no `Authorization` or `Referer`, and aborts with `AbortError`. It does not close (a): WebKit's `about:blank` frame is
  SW-controlled, so this works on Chromium only. A page has no "skip the Service Worker" flag, and `cache: 'no-store'`
  does not bypass the worker.
- **`blob:` worker created by the host.** It is SW-controlled on Chromium and WebKit, as the spec requires (a blob
  worker inherits its creator's controller). It closes nothing for (a).
- **`data:` worker.** It closes both effects, but the host page's CSP would need `worker-src data:`, which the library
  should never ask an embedder for.
- **A library-owned sandboxed opaque-origin frame that runs the fetch.** It closes both (a) and (b) on all three
  engines, by construction:
  - A context with an opaque origin is never a Service Worker client.
  - Host code cannot reach a cross-origin realm.
  - It matches "no more than a direct guest request would", including `Origin: null`. This is ADR-006's own "Revisit
    if" option.
  - The policy code (`validateRequest`, the record, the caps) stays on the host. Only the pinned
    `fetch(Request, init)`, the abort and the capped body read cross a `MessageChannel`.
  - The costs:
    - `Origin` changes to `null`, so targets need `ACAO: *` or `null`. ADR-006 already says `*` works, because no
      credentials are sent.
    - The frame inherits the host page's policy, so its script has to pass the host's `script-src`. That means one
      more hash for the embedder, or the fetcher runs inside a library frame that is already allowed. The frame's own
      `<meta>` `connect-src` could be the allowlist, which adds a second layer of enforcement.
- **Detect and warn.** Check `navigator.serviceWorker.controller` on every request, and say in API.md, ADR-006 and the
  threat model that a controlling Service Worker handles bridge requests. This is a stopgap, not a fix: a worker can
  claim the page after the sandbox is mounted, and a warning does not stop the data from flowing.

**Recommendation:**
1. Move the request into a library-owned sandboxed opaque-origin context. This is the only option I tested that
   closes both effects on Chromium and WebKit.
2. Update ADR-006 decision 6 (`Origin: null`) to match.
3. Until that lands:
   - take `fetchImpl` from a fresh `about:blank` realm, which closes (b) everywhere and (a) on Chromium;
   - document the Service Worker caveat, with a warning while the page is controlled.
4. Add the structural test the reviewer proposed: run `fetch-bridge.spec.ts` on a harness that has a cache-first
   Service Worker and a header-adding wrapper.

#### 5. Rating: high (confirmed)

- **Why it is high:**
  - A documented security property does not hold. ADR-006's discipline and the explicit claim "no `Authorization`
    reaches the target" both fail.
  - The guest, which is the adversary, gets the user's private cached data, or requests made with the user's
    credentials, from an origin the embedder listed.
  - The precondition is realistic. The natural use of the bridge is to let the guest reach an API the host app
    already uses, and Workbox runtime caching and auth or APM fetch wrappers are common in exactly those apps.
- **Why it is not critical:**
  - The bridge is off by default.
  - Effect (a) needs a Service Worker that caches the listed origin. Effect (b) needs a wrapper that targets the listed
    origin.
  - The token reaches the guest only through reflection, or when the guest owns the origin.
- **Why it is not medium:** the issue is not wording. The embedder who follows the docs is exposed, and the docs give
  them no way to know they need to act.
