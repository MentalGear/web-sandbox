# S74 review board, pass 6 (2026-11-07)

The sixth pass of the final independent review board (backlog [S74](../../BACKLOG.md#s74)), on the branch of the pass-5
fixes at `c404689` ([BOARD-PASS-5-2026-10-25.md](BOARD-PASS-5-2026-10-25.md): the sealed-app recipe, the test pins for
sealed mode, the archive and research 22; #88), with the same scope as pass 5: **sealed mode**, the default (a worker and
an inert view, no network by construction, nothing read from the host page but `crossOriginIsolated`), with its own
opt-ins. Only a data finding that reaches sealed mode counts against a clean pass; strict mode with `origins` or
`fetchBridge`, and cooperative and worker mode, are marked and fixed or documented without blocking the board. The
changes since pass 5 that the brief asked the reviewers to read with extra care were the pass-5 fixes of #86 and #87 (the
RPC chokepoint, `unexpose()`, the worker's allowlist, the reasons and the messages) and #88 (the recipe and its docs).
Six reviewers worked in isolated worktrees, one each for isolation (ISO: the inherited context of sealed mode), channels
and frames (CHL), limits and the app runtime (LIM), the current docs against the code (DOC), mutation testing of the tests
(TST) and a newcomer who builds an app from the docs alone (NEW). Three verifiers then checked the findings: ISO-1 and
ISO-2; LIM-1 and LIM-2; and the low findings with a docs claim or a data label (DOC-1 to DOC-4, CHL-2, CHL-3, CHL-4,
NEW-1, NEW-2). The other findings have no verdict.

**Result: not clean.** Confirmed findings that leak or can manipulate data and reach sealed mode: **5** (all verified).
**Two are high** and are the library's own isolation: [BD6:ISO-1](#bd6-iso-1) (a sealed guest read the host page's
Content-Security-Policy text, nonce and report-endpoint key included, on Chromium and Firefox) and [BD6:ISO-2](#bd6-iso-2)
(the guest made the browser POST CSP reports, with URLs and text it chose, to the host page's report endpoint, on Chromium
and Firefox, so sealed mode did make network requests). Both come from one channel that `INHERITED_CONTEXT` had no row for:
the sandbox's frames and workers inherit the host page's whole policy list, and every refusing check of that list reports
the policy's text to the guest and the guest's string to the host's `report-uri`. The other three are **low** and sit where
the host to app API and the recipe hand over more than intended: [BD6:LIM-1](#bd6-lim-1) (with [BD6:CHL-1](#bd6-chl-1); the
pass-5 error-text fix was incomplete: the library's own refusal of an argument it cannot copy carried the engine's text),
[BD6:LIM-2](#bd6-lim-2) (the recipe's `stop()` did not cut the first app off from the next one on the same element) and
[BD6:CHL-3](#bd6-chl-3) (a failed load left the first app running, with its `save` exposed). So pass 6 did not count toward
clearing the board: **0 of 2 consecutive clean passes.** Two of the five sit in the recipe that the previous round
rewrote (#88), so the evaluation rule of [research 22](../../research/22_review_trajectory/README.md) triggered again, in
its second form. What held: no request reached a listener on any engine from a newcomer's app (fetch, XHR, WebSocket,
remote import, nested worker, `sendBeacon`, `EventSource`, caches, IndexedDB, a service worker, `ping`, meta refresh,
prefetch, forms, frames, inline SVG, stylesheets), no forged frame was accepted, the 44 of 45 single-point mutations of the
sealed code that the unit suite caught, and the `appId`-keyed recipe, `unexpose()`, `compactViews` and `LibraryDetail`
reasons that pass 5 added.

## Decisions

How each finding was resolved. **No owner decision was needed:** each finding was solved by construction, as far up the
ladder as it goes (the wrong state made impossible to build, then impossible to reach, before a check or a documented
limit). The fixes are in four places: #89 (the RPC refusal texts and the low code findings), the fix 1 pull request
#90 (guest code never makes the browser check the host page's policy), the CSSOM fix (the view applies a guest's styles
through the CSSOM; it has no number yet) and this pull request (the recipe and the docs, and this archive).

- **Owner's board rule, 2026-10-21 and D5, 2026-10-24** (unchanged for this pass). A pass is clean when none of its
  confirmed findings leaks or can manipulate data and reaches sealed mode, at any severity, a docs gap that leads an
  embedder into a leak included. Availability-only findings are backlogged and do not count; neither do docs drift, test
  gaps and correctness bugs with no data effect.
- **[BD6:ISO-1](#bd6-iso-1) and [BD6:ISO-2](#bd6-iso-2)** (a sealed guest read the host page's policy text, and made the
  browser report its refusals to the host's endpoint) are fixed in #90, class A (the host page's context a sandbox document
  inherits). The construction: the guest's worker never reaches a refusing check of the host page's policy.
  - **Strings run as code:** before the entry runs, `eval`, `Function`, the constructor of every function kind and
    `setTimeout`/`setInterval` given a non-function handler are replaced with the library's own `EvalError`, which never calls
    the platform (`src/lib/code-from-strings.ts`); every copy on the global's prototype chain is removed. The engine's check
    never runs, so there is no event, no report and no engine message.
  - **`import()`:** the build refuses an entry whose text holds `import` followed by `(` (`src/lib/entry-imports.ts`, the
    reason `entryImport`). `import()` cannot be stopped inside the frame, and sealed mode could never load one (the view's
    `script-src` is a hash), so the refusal removes no capability. A raw-text scan, checked against the engine on hand-written
    cases and 6000 generated texts, was used and not the lexer that the verifier suggested: es-module-lexer misses an
    `import()` placed after a classic-script HTML comment, which the engine runs. The cost is that `import(` inside a string or
    a comment is refused too, and the reason text says so.
  - **`scriptUnsafe` in sealed mode** is refused at configuration (the reason `sealedScriptUnsafe`; the type is now
    `scriptUnsafe?: false`), because a string run as code is checked against the host's policy. Sealed mode therefore has no
    `execute()`: about 117 `execute()`-driven sealed test cases skip with the reason and are covered through strict mode's
    identical view and worker, and sealed mode's own tests run from entries.
  - **Violation events:** the bootstrap's first listener relays each violation to the element and then stops it, and every
    getter of `SecurityPolicyViolationEvent.prototype` reads blank to guest code.
  - **The view runs no guest code:** its policy admits the bootstrap's hash alone.
  - **The row and its test:** `INHERITED_CONTEXT` gains `cspPolicyText` and `cspReporting`; the maker list of the no-network
    suite covers every code-from-string sink, every compiler the worker lacks and every `import()` form; a new spec
    (`test/e2e/sealed-host-policy.spec.ts`) runs the guest on the realistic host with a nonce, `'report-sample'` and a keyed
    `report-uri`, and holds that the endpoint receives nothing the guest caused and no string the guest can reach holds the
    nonce or the key, while a control shows that the endpoint still receives the host page's own violation.
  - **Cost:** the refusal adds about 0.18 ms to a worker start on Chromium and under 1 ms on Firefox and WebKit; the build's
    scan costs 1 to 2 ms per MiB of entry on the host thread (measured 2026-11-07, a loaded 4-core VM).
  - **Documented limits, not fixed:** strict mode with `scriptUnsafe` and worker mode (strings still reach the platform;
    Chromium's `EvalError` quotes the host's refusing directive), and cooperative mode, which reads its own violation events.
    `report-to` is asserted on WebKit only (Chromium headless delivered nothing, not even the host page's own report, and
    Firefox has the Reporting API off).
- **The view's share of [BD6:ISO-2](#bd6-iso-2)** (the guest's inline styles under a host `style-src` without
  `'unsafe-inline'`, and `blob:` loads of registered files and written images under a host `img-src`, `font-src`,
  `media-src` or `style-src` without `blob:`, make the browser post reports naming `blob` or `inline`, with the first
  characters of the style when the host has `'report-sample'`) was left by #90 as a documented, "reduced" part of the
  `cspReporting` row. **The CSSOM fix** removes the style part by construction: the view never inserts a guest `style`
  attribute or `<style>` element into its document and applies the style text through the CSSOM, which no `style-src`
  governs. The `blob:` loads of files the embedder registered or the app wrote stay documented.
- **[BD6:LIM-1](#bd6-lim-1) with [BD6:CHL-1](#bd6-chl-1)** (the library's refusal of an argument it cannot copy, and a send
  that fails, carried the engine's text in a plain host `Error`, which a host method that passed it on sent to the app)
  are fixed in #89, class P (what crosses is not what the API shows): the refusals have fixed texts ("RPC arguments are not
  transferable: they hold a value structured clone cannot carry", "RPC call could not be sent"), the engine's error is the

  errors the library made (`src/lib/minted-errors.ts`, filled by `codedError`, `fileError` and `fetchRefusal`) is what

  that reads `null[marker]`) hold it on three engines. The one visible change besides the texts: the console line now reads

- **[BD6:LIM-2](#bd6-lim-2), [BD6:CHL-3](#bd6-chl-3) and [BD6:DOC-1](#bd6-doc-1)** (the recipe's `stop()` did not cut the

## Reviewer reports

### ISO: isolation, the inherited context of sealed mode

The first part of the reviewer's full report, as far as it was kept (it ends in the middle of the reproduction of
BD6:ISO-2), and below it the reviewer's final report. The verdict is under [Verdicts](#verdicts).

I reviewed `main` at c404689d655c7a9ca0553155401356a083626905, in a detached worktree at
`<worktree>`. The probe specs are in that worktree's `test/e2e/p6-iso-*.spec.ts`
and are not committed. I used Playwright headless with each engine run alone (`--workers=1`). Load average was 0.05 to 2.1.
The results rest on state and on what the server recorded. None of them depends on timing.

Both findings come from one channel that `INHERITED_CONTEXT` does not have. A srcdoc frame inherits the host page's whole
CSP list, and the guest's `blob:` worker inherits it from the view. That covers more than what the list admits (the
existing `csp*` rows). It also covers **the policy text** and **the policy's reporting endpoints**. The browser checks
every policy in the list, and each policy that refuses an action reports it on its own: to the guest's realm as an
event, in the engine's error text, and to the host page's `report-uri` or `report-to` as a POST.


#### <a id="bd6-iso-1"></a>BD6:ISO-1: a sealed guest reads the host page's Content-Security-Policy text, including its nonce and its report endpoint's key

- **Severity**: high. The guest reads host-page state in the default configuration. The only precondition is a host page
  that sends a CSP with `script-src` (or `default-src`) without `'unsafe-eval'`, or with `require-trusted-types-for`.
  That is every page that follows docs/API.md#host-page-policy with a policy at all. This is the same rating that
  BD5:ISO-1 got for the same kind of read. Critical's wording ("reads host-page state ... in a default configuration")
  applies word for word. I rated it high because sealed mode's only way out is the embedder's exposed methods (and see
  BD6:ISO-2).
- **Effect**: data (a read of host-page state).
- **Scope**: sealed, on Chromium and Firefox. Strict mode and worker mode are affected the same way. WebKit raises no
  violation in a worker (ledger `worker-violation-reports`), and its error text quoted the view's own policy, not the
  host's. With `scriptUnsafe` the view admits eval, so I expect WebKit to quote the host's directive too. I did not run that.
- **Class**: A, the host page's context that a sandbox document inherits. The missing row is the host page's policy
  text. The worker's code-from-string sinks and the violation event's fields are the captured-intrinsics surface of the
  guest realm.
- **Where**:
  - `src/lib/worker-globals.ts:42` keeps `eval` and `Function`, and `:64` keeps `SecurityPolicyViolationEvent`.
  - `src/lib/in-sandbox-script.ts:383-409`: the bootstrap's capture listener (`relayViolation`) relays the event but
    does not stop it. Every guest `addEventListener('securitypolicyviolation', …)` then receives the trusted event and
    can read `originalPolicy` and `sample`.
  - The engine's own `EvalError` message (Chromium) quotes the directive that refused, and that directive is the host's.
  - `src/lib/inherited-context.ts`: no row covers this. `cspScript` (remains) covers only what the host's `script-src`
    admits.
  - `test/unit/host-policy-source.test.ts:56` calls `originalPolicy` "the one API that reports a page's policy text",
    and makes sure that **host code** never reads it. Nothing makes sure the **guest** cannot read it.
- **Concrete path**:
  1. The embedder serves a page with a CSP: the realistic host's policy, plus `'nonce-…'` and a `report-uri …?sentry_key=…`.
  2. The guest's entry (default config: `setConfig({ entry: 'main.js' })`) runs
     `self.addEventListener('securitypolicyviolation', e => seen.push(e.originalPolicy))`, then
     `try { eval('1') } catch {}` (or `new Function`, string `setTimeout`, or `import('data:…')`).
  3. The browser checks the worker's inherited list: the host's policy, the wrapper's and the view's. The host's
     policy refuses the action, and the event is dispatched in the worker with `originalPolicy` set to the host
     page's full header text.
  4. On Chromium the guest does not even need the event: `e.message` of the caught `EvalError` is
     `… violates the following Content Security Policy directive …: script-src 'self' 'sha256-…' 'nonce-HOSTNONCE-…'`.
- **Reproduction** (all in the worktree):
  - `test/e2e/p6-iso-policy-text.spec.ts` uses the realistic host page in sealed mode with the default config.
    - Chromium **fails**: the guest saw 5 events, 4 of them with `originalPolicy` = the host page's header (including
      `report-uri /__realistic-host/report/<session>` and `trusted-types app web-sandbox default`).
    - Firefox **fails** (6 events, `originalPolicy` = the host's).
    - WebKit passes (0 events).
  - `test/e2e/p6-iso-report-egress.spec.ts` uses the host policy with `'nonce-HOSTNONCE-c2VjcmV0LW5vbmNl'` and
    `report-uri …?sentry_key=REPORTKEY-0123456789abcdef`. Output:
    - Chromium: `{"guestEvents":300,"leakedNonce":true,"leakedKey":true,…}`
    - Firefox: `{"guestEvents":600,"leakedNonce":true,"leakedKey":true,…}`
    - WebKit: `{"guestEvents":0,"leakedNonce":false,"leakedKey":false,…}`
  - `test/e2e/p6-iso-error-text.spec.ts` checks the error text alone, with no listener:
    - Chromium, with and without Trusted Types:
      `EvalError: Evaluating a string as JavaScript violates … script-src 'self' 'sha256-evhiX…' 'nonce-HOSTNONCE-c2VjcmV0LW5vbmNl'`.
    - Firefox: `call to eval() blocked by CSP`, with no policy text.
    - WebKit: quotes the view's own `script-src 'sha256-…'`.
- **What the guest learns**:
  - the host page's script nonce, whose whole purpose is to be unknown to content the page did not write;
  - the host page's report endpoint and any key in its URL (Sentry and report-uri.com put keys there);
  - every origin the host app connects to (internal API hosts in `connect-src`);
  - the page's script and style hashes;
  - whether the page enforces Trusted Types, and its policy names.

  None of this is "the host origin, which is not a secret" (the `ancestorOrigins` row). It is state of the page's own
  response. The docs say that sealed mode reads nothing of the host page but `crossOriginIsolated`. That is true of the
  library, but the guest reads the page's policy.
- **Engine difference**: Chromium and Firefox leak and WebKit does not. This is not in the ledger as a security property.
- **Why the chokepoints and structural tests miss it**:
  - `host-policy-source.test.ts` scans only host code for `originalPolicy`.
  - `WORKER_STATE_READS` classifies names that read per-origin browser state. An event's field that carries the host
    page's policy is neither a global nor a navigator member, so its classification test cannot see it.
  - `violations.spec.ts` checks what the library relays to the element, not what the guest itself reads from the event.
  - `realistic-host.spec.ts` never has the guest provoke a violation of the host's policy.
- **Suggested fix (by construction)**:

     the platform. The entry points are `eval`, `Function`, the `constructor` of the async, generator and
     async-generator function prototypes, and `setTimeout`/`setInterval` with a string. The engine's check then never
     runs: no event, no report and no engine message. Without `scriptUnsafe` nothing is lost, because these always
     throw under the view's policy. With `scriptUnsafe`, wrap the platform's sinks and rethrow a refusal with the
     library's text.
  2. **Make the event's policy fields unreachable** for what cannot be removed (`import()`):
     - The bootstrap's capture listener, the first on the target, relays the event and then calls
       `stopImmediatePropagation` (captured), so no guest listener receives a browser violation.
     - The `originalPolicy`, `sample`, `documentURI` and `referrer` getters of `SecurityPolicyViolationEvent.prototype`
       are redefined to return `''`. `readEvent` already reads through captured getters.
  3. Add a row to `INHERITED_CONTEXT`, `cspPolicyText`: "the host page's policy text and reporting endpoints, which
     every check of the inherited list reports with". Its sealed standing is `remains`, neutralised by `construct`.
  4. **Structural tests**:
     - An e2e spec on the realistic host with a nonce, `'report-sample'` and a keyed `report-uri`. The guest tries every
       code-from-string sink and `import()`, and listens for the event. On all three engines no string the guest can
       reach contains the nonce or the key. That is these probes, inverted.
     - A unit test that enumerates the function-constructor family from the language (the `constructor` of every
       function kind's prototype) against the prelude's list of sinks, so a new function kind is classified before it ships.

### Verdict on BD6:ISO-1 and BD6:ISO-2

Both confirmed on Chromium and Firefox and refuted on WebKit. The verifier's own probes ran on the realistic host, in sealed

- **Is the late `call()` inherent?** Yes, as with any reused handle (`_issue` binds a call to the environment current when it is
  made). The library does not make it worse, but it gives handlers no context bound to the environment that called them.
- **What the docs said:** `stop()` "ends the app and clears the element" overstates it. The reference documents that pending writes
  stay committable after termination. The flag advice names only `save`, not `call()` or commits, and nothing says mounts on one
  element must not overlap.
- **LIM-2 fix:**
  - Docs and recipe now: the flag check before any `call()`, commit or `registerFiles()`; one mount at a time on an element; a
    `running` check after each `await`; e2e rows for all three paths.
  - By construction, needing owner approval as the verifier put it: discard pending writes at `terminate()` (or add
    `discardGuestWrites()`), and give each host-method call a `{ signal, call }` bound to the environment that called it. Add both
    to the lifecycle model. **Not needed:** an element for each app removes the shared handle and the shared pending writes, so
    the fix took no API change (see the decisions).
