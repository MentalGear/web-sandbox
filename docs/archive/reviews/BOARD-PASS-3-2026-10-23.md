#### <a id="bd3-iso-1"></a>BD3:ISO-1: the same-site refusal fails open when the cookie-domain probe cannot write its test cookie, for example under a consent manager's cookie gate. A sibling origin is kept, and on WebKit it receives the host site's Lax and Strict session cookies

- **Severity:** high. A documented security property does not hold under a realistic precondition, and a reproduction
  was executed.
- **Effect:** data. The guest sends credentialed requests to the user's own site and reads a credentialed WebSocket answer.
- **Mode:** strict, at its default, with the `origins` opt-in. The same holds in every mode.
- **Class:** B (a browser decision re-derived). The fallback prediction errs toward admitting, but the class chokepoint
  requires that it "errs only toward refusing".
- **Code:**
  - `src/lib/host-site.ts:58-77`, `probeRegistrableDomain`. The first host-only write is read back at :66, and if that
    write fails the function returns `null`.
  - `src/lib/host-site.ts:85-95`, `hostRegistrableDomain`. The `null` is cached for the whole page life (:94).
  - `src/lib/origin.ts:107-109`, `sharesHostSite`. With `null` it falls back to "above or below the page's host", so a
    sibling is not on the site.
  - `src/lib/config-schema.ts:272-307`, `limitHostReach`. The sibling is kept with no warning.
  - Wiring: `src/host.ts:904`.

**Path.**
1. The host page is `https://app.example.com`. Like many EU sites, it runs a consent manager whose cookie gate wraps the
   `document.cookie` setter: writes of unconsented cookie names are held back, and reads pass through. Osano and
   Cookiebot's auto-blocking work this way.
2. The embedder lists its API in `origins`: `images: ['https://api.example.com']`,
   `connect: ['https://api.example.com', 'wss://api.example.com']`. The docs promise that this sibling "is dropped in
   every mode".
3. The probe's host-only `__ws_site_probe_*` write is swallowed, so `probeRegistrableDomain` returns `null`, and the
   `null` is cached.
4. `sharesHostSite` falls back to the name check, `api.example.com` is not "above or below" `app.example.com`, the
   result is `false`, and the entry is kept with no warning.
5. In strict mode, the view renders `<img src="https://api.example.com/...">` and the worker opens
   `new WebSocket('wss://api.example.com/...')`. The request gate admits the socket: its origin is listed.
6. On WebKit both requests carry the host site's `SameSite=None`, `Lax` and `Strict` session cookies. A WebSocket
   server that authenticates by cookie and does not check `Origin` answers with the user's data, and the guest reads it.

**Reproduction.** `test/e2e/p3-iso-site.spec.ts`, variant `consent` against control `plain`, 9/9 pass. The log is
`<scratchpad>/p3iso/site.log`.

| Engine | `plain` (control) | `consent` |
| :--- | :--- | :--- |
| WebKit | dropped with 2 warnings; the guest's WebSocket is refused by the gate; the listener sees nothing | no warning; the listener sees `img` and the `ws` handshake, each with `Cookie: sess_none=NONE-SECRET; sess_lax=LAX-SECRET; sess_strict=STRICT-SECRET`; the guest logs `WS-READ user-data-for:sess_none=…; sess_lax=…; sess_strict=…` |
| Firefox (Playwright, cookieBehavior 4) | dropped | kept; `sess_none` on both requests, read back over the socket. With release Firefox's default (Total Cookie Protection), the project's own facts table says none: not re-measured here |
| Chromium | dropped | kept, but no cookie arrives, because the wrapper is `credentialless`. The policy fails open without a data effect |

`test/unit/p3-iso-site.test.ts` (passes on `main`): `probeRegistrableDomain('app.example.com', consentJar) === null`,
then `limitHostReach` keeps `https://api.example.com` and its `wss` twin with no warning. A jar that keeps cookies
finds `example.com`.

**Why the existing chokepoint and tests miss it.**
- `test/e2e/host-site.spec.ts` checks only one failure: "a page whose cookies are blocked gets null". There, no cookie
  is sent either, so it looks harmless.
- docs/API.md:205 and THREAT-MODEL.md:108 and :140 describe the fallback as reached when "cookies [are] blocked, a page
  with no cookie jar". That leads the embedder to believe the gap costs only function.
- No test pairs "the probe cannot write" with "the browser still sends the cookies". A page-level wrapper of
  `document.cookie` does exactly that.
- The board's own design (BOARD-PASS-2, §4.A.3 item 2) said: "Where cookies are blocked or the page is opaque, fall back
  to a heuristic that errs toward same-site … Its errors are refusals, a functional loss, never a leak." The
  implementation errs toward cross-site, so the BD2 fix is incomplete.

**Suggested fix (by construction).**
- Make the class-B decision three-valued: same site, another site, or unknown. Make unknown refuse. When the probe
  cannot answer, every `origins` entry that shares the page's last label is dropped, with a warning that names the cause
  (as the BD2 design said). Siblings are lost only on pages whose probe fails, and the warning tells the embedder to
  pass the site explicitly (a `hostSite` option) or to use the fetch bridge.
- Optionally, make the probe immune to page-level wrappers: call the native `cookie` accessor from a fresh same-origin
  `about:blank` frame's `Document.prototype` on the host document. A cross-realm brand check passes.
- Do not cache `null` for the page life.
- Structural test: a property test over jar behaviours (keeps everything, refuses everything, refuses unknown names,
  refuses `Domain=`, throws) times host and entry pairs (self, parent, child, sibling, public suffix, other site). It
  asserts that `limitHostReach` never keeps an entry the real registrable domain covers. Add an e2e variant of
  `host-site.spec.ts` with a wrapped setter.

#### <a id="bd3-iso-2"></a>BD3:ISO-2: the element takes the host origin from `location.origin`, which is `'null'` in a same-origin `about:srcdoc` or `about:blank` host document. Then nothing is on the host page's site, not even the page's own origin, and on WebKit the guest's requests to it carry the page's session cookies

- **Severity:** high. A documented security property does not hold for a supported host configuration, and a
  reproduction was executed.
- **Effect:** data.
- **Mode:** strict, at its default, with the `origins` opt-in. The same holds in every mode.
- **Class:** B. The host page's origin is the browser's: `self.origin`. `location.origin` is a re-derivation from the
  document's URL, and it differs exactly in srcdoc and about:blank documents.
- **Code:**
  - `src/host.ts:904`: `hostOrigin: globalThis.location?.origin ?? ""`, and `hostRegistrableDomain()` with its default
    `location.hostname` (`src/lib/host-site.ts:85`), which is `''` there.
  - `src/host.ts:1827`, the fetch bridge's `hostOrigin`.
  - `src/lib/origin.ts:97-101`: `new URL('null')` throws, so the function returns `false` for every entry.
  - `src/lib/config-schema.ts:274`.
  - The library knows the trap: `src/lib/environment-check.ts:32` says "`location.origin` reads `'null'` in every srcdoc".

**Path.**
1. The host application renders its sandbox host in a same-origin `srcdoc` iframe (a preview or editor pane, a
   document written into an `about:blank` popup). The library is imported there and the element lives there. Its realm
   has the host's real origin (`self.origin` is `https://app.example.com`), and it has the host site's cookies.
2. In that realm, `location.origin` is `'null'` and `location.hostname` is `''`. `limitHostReach` gets
   `hostOrigin: 'null'`, `sharesHostSite` returns `false` for every entry, and the page's own origin
   `https://app.example.com` is kept with no warning.
3. Private hosts are still dropped (`isPrivateOrigin('null')` is false), so that side fails closed.

**Reproduction.** `test/e2e/p3-iso-site.spec.ts`, variant `srcdoc`, in `<scratchpad>/p3iso/site.log`. The realm reports
`locationOrigin: "null"`, `selfOrigin: "https://app.s74p3.test:P"`, `hostname: ""`, and no warning.

| Engine | Result |
| :--- | :--- |
| WebKit | The view's image and the worker's WebSocket handshake to the host page's own origin both carry `sess_none`, `sess_lax` and `sess_strict`, and the guest reads the credentialed WebSocket answer |
| Firefox (cookieBehavior 4) | `sess_none` on both, read back |
| Chromium | kept; no cookie, because the wrapper is `credentialless` |

Unit: `test/unit/p3-iso-site.test.ts`, "BD3:ISO-2". `limitHostReach` with `hostOrigin: 'null'` keeps
`https://app.example.com` and its `wss` twin, silently.

**Why the existing chokepoint and tests miss it.**
- `test/unit/host-origin-wiring.test.ts` asserts only that `location.origin` matches `https?://`, which is true on the
  harness page.
- The e2e harness is always a top-level document.
- `sharesHostSite` treats an unparseable `hostOrigin` as "nothing is same-site". That is the fail-open direction.

**Suggested fix (by construction).**
- Have one function in the class-B chokepoint give the host page's origin and host: `self.origin`, and the host from
  `new URL(self.origin)`. host.ts calls it in both places, and `hostRegistrableDomain` takes its host name from it.
- Treat an opaque or unparseable host origin as "unknown", which refuses (BD3:ISO-1's third value): drop every `origins`
  entry not listed as private, with a warning, or refuse the build.
- Structural tests:
  - a source scan, so no `location.origin` or `location.hostname` appears in host-side code outside that function;
  - a unit test that `limitHostReach` with `hostOrigin: 'null'` keeps nothing on any site;
  - an e2e variant with the element in a same-origin srcdoc frame.

#### <a id="bd3-iso-3"></a>BD3:ISO-3: redirects from a listed origin to an unlisted one are a security claim with no test, and Firefox's synchronous XMLHttpRequest ends differently from the other engines (not in the ledger)

- **Severity:** low.
- **Effect:** no data effect.
- **Mode:** strict.
- **Class:** E-net (the structural test is missing). The outcome difference is an engine difference with no ledger row.
- **Code:** `src/lib/in-sandbox-script.ts:412-423`. The gate checks only the first URL, and "a redirect to an origin it
  refuses is the browser's to refuse". THREAT-MODEL.md:158 repeats the claim.

**Path.** An open redirector on a listed origin is common (`/redirect?to=`). The request gate admits the first hop.
Whether anything reaches the second, unlisted origin rests entirely on each engine applying the inherited and the guest
policy to redirects, from a worker and from the view's loads.

**Reproduction.** `test/e2e/p3-iso-redirect.spec.ts`, 3/3 pass. It covers the worker's `fetch` (cors, no-cors,
`redirect: 'manual'`), async and sync `XMLHttpRequest`, and the view's `img`, `srcset`, CSS background, `@font-face`,
`video`, `audio` and `poster`. On all three engines the allowed listener saw every first hop, and the blocked listener
saw nothing. So the property holds.

The only difference is the synchronous `XMLHttpRequest`. Chromium and WebKit throw `NetworkError`. Firefox returns from
`send()` with `status` 0.

**Why the tests miss it.** No spec under `test/e2e/` makes a guest request that redirects. `fetch-bridge.spec.ts` covers
only the bridge, whose `redirect: 'manual'` is pinned.

**Suggested fix.**
- Add the probe to `request-gate.spec.ts`, or to the E-net structural tests, as the redirect row of the request gate's
  table.
- Either make the sync XHR outcome uniform (the gate could treat a refused redirect as its own refusal only if it saw
  it, which it cannot), or add a ledger row `redirect-refusal-outcome`.

#### <a id="bd3-iso-4"></a>BD3:ISO-4: the inherited-context registry has a row for cookies but none for the other ambient credentials a WebSocket handshake or a view load can carry

- **Severity:** low. Not measured.
- **Effect:** at most a docs gap.
- **Mode:** strict.
- **Class:** none of its own: this is the completeness of the inventory in `src/lib/inherited-context.ts`.

**Path, not executed.** A WebSocket handshake and a load of the view's markup or CSS cannot be stripped of credentials.
Besides cookies, an engine attaches cached HTTP authentication (Basic or Digest), integrated Windows or Kerberos
authentication on an intranet, and a TLS client certificate to a listed origin. In those engines that ride is the same
as the documented cookie ride.

The `cookies` row says that the request to another site "carr[ies] that site's own cookies". It does not say that the
user's other credentials for a listed origin ride too. The same-site drop covers the host's own site, but after BD3:ISO-1
and BD3:ISO-2 that drop is not reliable.

**Suggested fix.**
- Widen the row to "the browser's ambient credentials (cookies, HTTP authentication, client certificates)".
- Have `request-gate.spec.ts` assert that the WebSocket handshake carries no `Authorization` after a Basic challenge in
  each engine, or record what each engine sends in `cookie-facts.ts`.

#### Areas reviewed and found sound

**The request gate in the strict worker** (`in-sandbox-script.ts:170-690`):
- **Admission.** It admits on the exact `scheme//host[:port]` key of the resolved URL against `features.connect`.
  `features.connect` is `connectSources` of the narrowed `origins` (`host.ts:2041-2077`), the same input as the policy.
- **Single reads.**
  - fetch reads the guest's input and init once, through the captured `Request`. It reads `url` and `keepalive` from the
    built Request, and rebuilds the Request with `credentials: 'omit'`.
  - XMLHttpRequest resolves the URL once and hands the platform the resolved string. Re-entering `open` from a guest
    `toString` only refuses more.
  - XMLHttpRequest's `withCredentials` setter is inert. The native setter is never stored.
  - WebSocket converts http to ws and checks the converted URL.
- **Originals unreachable.** I found no route back to an original through:
  - the global and its prototype chain (`replaceGlobal`);
  - `constructor` (`adopt`) or `new.target` tricks;
  - getters on the init (`caller` and `arguments` give only the gated function or the guest's own values);
  - structured clone or transfer (functions do not clone; only ports and bytes are transferred);
  - nested realms: the strict worker has no `Worker`, `ShadowRealm` or `importScripts`.
- **The worker allowlist.** It leaves no other request maker. Dynamic `import()` falls under the view's hashed
  `script-src`.

**Redirects.** A redirect off a listed origin is refused on all three engines, for the worker and for every view load
kind (BD3:ISO-3).

**The view.** Its elements, attributes and URL attributes, `INERT_HREF`, the link `rel` allowlist (`stylesheet`,
`icon`), and the forced `no-referrer`.

**Cooperative mode (not strict).** In the guest realm itself, `sendBeacon` (string and Blob), `EventSource`, prefetch,
preload and modulepreload links, `<img>`, CSS `@import` and `url()`, and media to an unlisted origin all reached nothing
(`p3-iso-coop.spec.ts`, 3 engines).

**The uniform connect-src.**
- Every case of the parser (`host-connect.ts`) only narrows relative to what the engines admit. A wrong keep is still
  refused by the inherited policy, and a wrong drop costs function only. So no parser error moves data.

#### <a id="bd3-chl-1"></a>BD3:CHL-1: a build that waited on the host-page policy read, when the read's frame left the document, skips the `connect-src` narrowing: silently on Chromium and WebKit, and on WebKit the guest's `fetch()` and `sandboxFetch()` reach an origin the host page's CSP refuses

- **Severity:** high. A documented security property does not hold with a realistic precondition: "every origin of
  `origins.connect` and `fetchBridge.allow` that a policy of the page refuses is dropped, with a warning, before the

- **Data / availability:** data. The guest's requests, and their bodies, reach an origin the host page's policy refuses

- **Mode:** strict (default mode) with `origins.connect` or `fetchBridge.allow`; the same code serves cooperative and
  worker mode.
- **Class:** L (a resource shared across environments and across elements, the policy read, is consumed by a build

##### The path

1. Element X is inserted with `origins: { connect: [O] }` (or `fetchBridge.allow: [O]`) on a page whose CSP refuses

   appended to X's shadow root, and the module-level `inflight` promise is set.
2. Within the read's window (the decoy fetch plus `SETTLE_MS` = 50 ms after the frame's load), the frame leaves the

     document. The new build's gate returns the same `inflight`;

3. `read` sees `frame.contentDocument !== doc` or `!frame.isConnected` and returns `undefined`; `finish(undefined)`

#### Areas reviewed and found sound

- **The exact byte measure (`structured-size.ts`).** Each kind of the closed set counted against what clone carries: strings,
  BigInt (asIntN guard before writing digits), plain objects and arrays (own enumerable keys, non-index ones included; an
  array charged by the more of its length and its keys, so a sparse array is past every limit by length before its keys are
  listed), Map, Set, Date, RegExp (source; flags and `lastIndex` are not cloned), wrapper objects, ArrayBuffer and views
  (one count per buffer, de-duplicated with direct references in either order, so a transfer list never names a buffer
  twice), Blob (`type`, refused past `BLOB_TYPE_MAX_LENGTH` without the `unsupported` kind) and File (`name`, `lastModified`;
  `webkitRelativePath` is declared not serialized and is not guest-settable). Errors, platform objects and
  SharedArrayBuffer are Infinity. Every early exit returns a total past the limit; the walk never throws. A plain object of
  another realm fails the `ObjectPrototype` test and measures Infinity (refused, the safe side). The kind text is bounded
  to 64 characters and, at both ends, comes from a snapshot whose tags are the platform's.
- **Getters once.** The relay snapshots each argument with the captured `structuredClone` (getters run once, inside the
  clone, before the snapshot is reachable), reads an error's `name`/`message`/`stack` once each, and measures the snapshot it
  posts; the host measures the arrived frame. `describe()` of an object clone refuses may run a guest `Symbol.toStringTag`
  getter and return a long string, but it is measured and replaced by a placeholder before posting, and cut before the
  browser's console sees it.

  host's `toLogDetail` unchanged; `own: true` is posted only by the bootstrap's `ownLine` with fixed texts; `source` is set by

  receipt. `freezeDeep` freezes plain objects, arrays, Maps and Sets, walks keys (never `length`), and leaves only what the
  docs say it leaves (bytes, Map/Set entries, a Date's time).
- **RPC.** The whole frame is measured at both ends; a result's snapshot is what is posted; the received code is clamped to
  the codes the other side may report; library codes pass only for reserved calls on the guest's broker; error texts are
  cut with their marker once, idempotently.
- **The uncaught budget in strict mode, WebKit's muted errors.** A muted error ("Script error." in the worker) is counted 1
  in the worker's count window and by its full text in the view's character window; a non-muted one is cancelled by the
  prelude and counted in the worker. The two character windows are separate (a guest can spend 1 MiB a second in each),
  but each bounds a different cost (the view's bounds what reaches the view on the host's thread; non-muted errors are
  cancelled and reach nothing), so the host's cost stays within the documented rate. Entry errors (`GUEST_ERROR`) end the
  sandbox; the marker logic is as BR:ST4 documents.
- **The view's budgets.** Event details: every string clamped against one shared budget with `truncated: true`; file
  fields are skipped (no user file reaches the guest). `set()` on an input is charged by its `value` attribute's

- **The fetch bridge's caps.** `maxBytes` on the host per chunk and in the frame per pull; a bodiless response (HEAD, null-body

Note on the reorder scenario: the race needs the element whose shadow root holds the read frame (the first to ask) to be
the one moved. Moving any other waiter rebuilds it against the same, intact read.

**Firefox cached-null variant: confirmed.** A read frame removed before its load never loads, the read hits
`READ_TIMEOUT_MS`, and `finish(null, true)` caches `known = null` and `failed = true` for the page. Every later build
then skips narrowing, with the warning. Chromium and WebKit fire the `about:blank` load synchronously on insertion, so
the timeout path is not reached there, and this variant is Firefox-only. It is also not only a correctness problem.
With a host policy that one engine reads more widely than the library's parser (`connect-src 'self' 127.0.0.1:PORT`, a
host without a scheme, which `CONNECT_ENGINE_FACTS.firefox.bareHostAdmitted = 'yes'` and which the library drops), I
reran with `V3CSP=bare`. Firefox's sibling-unmount case and its later builds C and D reached O
(`/v3-unmount-sync-b`, `/v3-later-c`, `/v3-later-d`). So on Firefox the variant also lets the outcome differ from the
documented uniform one for the rest of the page's life.

**Realistic triggers** (all are the embedder's own DOM operations):
- a keyed list reorder or a reparenting by a framework (`insertBefore`/`append` of the first sandbox: disconnect, then
  connect, which reloads the read frame inside its shadow root);
- a sibling sandbox unmounted while another waits: a route change, a closed tab or panel, a conditional render that
  mounts and then discards, or a list filtered on its first render.

The window is the frame's load, plus the decoy fetch, plus `SETTLE_MS` (50 ms). In practice that is about 0 to 50 ms
after the first build asks, longer on a busy main thread, and 2 s on Firefox in the timeout path.

**Guest code cannot trigger it.**
- A strict guest runs in a worker under an opaque-origin view. It holds no reference to any host node. Every library
  frame is in a shadow root, and a cooperative guest's `top.length` is 0 (the CHL report, "multiple sandboxes", re-checked by
  reading).
- The read happens in the gate before the waiting build's guest exists.
- A running guest of another sandbox can end only its own environment. Teardown removes that element's wrapper, never
  another element or the read frame, and the element itself stays in the DOM.
- The only route runs through embedder code that reacts to guest events (a log or resize handler that re-renders the
  list), and that is the embedder's choice.
- So the precondition is an embedder action, not a guest capability.

#### 2. What is reachable

The data effect is narrow but real: guest code reaches an origin that **the embedder itself listed**, which the host
page's `connect-src` forbids, and which the library documents as dropped "on every engine" (API.md lines 124, 187 and
286, and the "Your connect-src" section; THREAT-MODEL line 133; engine ledger row `connect-src`: "the outcome is one on
every engine").

No unlisted origin is reachable. The request gate admits exactly `connectSources()` of the same unnarrowed input, so it
admits O and nothing else. The bridge's host-side allowlist is likewise the unnarrowed `fetchPolicy.allow`. What then
decides is the engine's own reading of the inherited host policy:
- **WebKit**: a `'self'` source admits origins it does not name (`selfAdmitsOtherOrigins: true`). The guest's `fetch()`
  and `XHR` (through the gate) and `sandboxFetch()` (through the bridge frame, which inherits the page's policy the same
  way) reach O, with request bodies, under the most common strict host policy, `connect-src 'self'`.
- **Chromium / Firefox**: the browser refuses O under `'self'`. That is no data effect, but the refusal is the engine's
  (`Failed to fetch` / `NetworkError`, bridge `FETCH_FAILED`), not the documented one (gate `TypeError` "refused by the
  sandbox", a library `violation`, bridge `FETCH_NOT_ALLOWED`), and no "dropped" warning appears. That is an API
  difference across engines. With a source an engine reads more widely than the parser (a host without a scheme on
  Firefox, or on Chromium without a port; `wss://h` admitting `https://h` on WebKit), the request leaves on that engine
  too, as the bare-host Firefox run shows.

`sandboxFetch` via `fetchBridge` does **not** reach a forbidden origin on all engines. It reaches on WebKit
(measured, `ok 200`), and on Chromium and Firefox only where their own reading of the host policy admits the origin.

#### 3. Rating

**High.**
- Not critical: the default configuration lists no connect origin, so it never reads.
- It needs a documented non-default opt-in (`origins.connect` or `fetchBridge.allow`) and a realistic precondition (an
  ordinary DOM move or unmount by the embedder within about 50 ms, or on Firefox at any time before the frame loads).
- A documented security property does not hold: "dropped, with a warning, on every engine". The engine difference in
  that property is undocumented, and the ledger says the opposite.
- I considered medium, because the destination is embedder-listed. I keep high because the narrowing exists exactly to
  refuse that origin, the host page's CSP is the authority the library says it applies, and the failure is silent on
  Chromium and WebKit.

**Counts against a clean pass: yes.** On WebKit, under strict mode with the `origins` / `fetchBridge` opt-in, guest data
(request bodies and URLs) leaves to an origin that the effective policy (the embedder's list intersected with the host
page's policy, as documented) refuses. That is data leaving across the policy, at whatever severity.

#### 4. Fix (by construction, at the class chokepoint)

I checked the reviewer's suggestion and agree with it. With the mutant applied, the reviewer's probe and my
reproduction both narrow on every case, on WebKit (22/22) and on Firefox (6/6, including the later-build case). No
fail-closed fallback fired, because the re-read always succeeded. It needs three refinements.

1. **One answer per build, which cannot be absent.**
   - `whenHostPoliciesKnown(root)` resolves with `HostPolicies` (a `readonly string[]` or `null`), never `void`.
   - The gate's result is handed to the build: `_reach(policies)` takes it as a required parameter instead of reading
     the module global `knownHostPolicies()`. "Not read" then has no representation in a build that asked.
   - A read whose frame left the document or was reloaded is not an answer: the read restarts in the shadow root of a
     waiter that is still connected. Simplest form: each waiter loops `whenHostPoliciesKnown(own root)` until it gets a
     defined result.
2. **Fail closed.**
   - If a build that asked still has no answer (retry bound reached), `_reach` drops every `origins.connect` and
     `fetchBridge.allow` entry with a warning, or ends the build with a reason.
   - `null` keeps its documented meaning only for a document that cannot fetch (jsdom), and for a frame that stayed
     connected and never loaded.
3. **Never cache a removal as a failure.**
   - On timeout, cache `null` and `failed` only if `frame.isConnected`.
   - Better, detect the removal at once instead of waiting 2 s: when the frame disconnects, settle the read as
     "not an answer" and retry. Otherwise the waiter on Firefox pays the 2 s timeout before its retry; the mutant shows
     that latency.
   - Optionally, give each element its own read frame (one read per waiting element when the shared one is lost), so
     no element's teardown can decide another's build. That is the class-L root.

**Structural tests.**
- **Unit, `host-csp`**: a fake frame that disconnects or reloads at each await point (before load, after load, after the
  decoy, during the settle), with 1 and with N waiters. Assert that every waiter resolves with a defined `HostPolicies`,
  and that a removal never sets `known = null` or `failed`.
- **Unit, `_reach` table** over {option `false`, a string, read `string[]`, `null` (cannot fetch), `null` (failed),
  absent} × {gate asked, not asked}. The absent row with a gate must narrow to nothing, and must not type-check without
  a policy argument.
- **E2E regression on all three engines**: the reviewer's probe plus my scenarios (keyed reorder, sibling unmount in the
  same task and one rAF later, mount-and-discard then a later build, and the bridge). In every case assert:
  `connect-src` without O, the "dropped" warning, nothing at the listener, a gate `TypeError` "refused by the sandbox",
  and `FETCH_NOT_ALLOWED` from the bridge.
- **A lifecycle-model check**: every resource of the page that one element creates and other elements consume (the read
  frame) is listed, and no element's teardown can change another element's build input.

**Docs.**
- Until it is fixed, the uniform-narrowing claim (API.md lines 124, 187, 286 and "Your connect-src"; THREAT-MODEL line
  133; the ledger's `connect-src` row) is false under a DOM move or unmount during the read.
- `hostContentSecurityPolicy` passed as a string avoids the read entirely, and is the workaround for embedders.

#### (1) Realism

##### BD3:ISO-1

The trigger is any page-level wrapper of the `document.cookie` setter that holds back unknown names while reads pass
through. My wrapper is installed on the instance and theirs on the prototype. Both defeat the probe, because it calls
`document.cookie` through the page.

I could not confirm from vendor documentation that Osano or Cookiebot wrap the setter. A web search found that the
mainstream CMPs (OneTrust, Usercentrics, CookieYes, Consently) block scripts, not the setter, and Usercentrics says it does
not touch cookies. So "a real CMP does this" is plausible but unverified, and the board should not cite the vendor names as
fact.

The precondition also has two other forms:

- **Any wrapper that throws** or filters reads, for example a privacy shim or a cookie polyfill.
- **A wrapper that swallows only `Domain=` writes.** Then the probe returns the host itself, not null, and the sibling is
  again kept. That is a confident wrong answer, not an undecided one.

The design intent was "errs toward refusing", and the code errs toward admitting. That holds whatever is wrapping the
setter.

##### BD3:ISO-2

The trigger is a host app that imports the library into a same-origin srcdoc pane, or into an about:blank pane it builds
with DOM calls. The docs nowhere require a top-level host document.

Correction to the reviewer: "a document written into an about:blank popup" is **not** affected. `document.open` gives the
document the opener's URL, so `location.origin` is right there. I verified this on 3/3 engines.

#### (2) What leaks, compared with the documented residual

**Request kinds.** The cookies ride on the view's `<img>` and CSS loads (and so on fonts and media) and on the worker's
WebSocket handshake. `fetch` and XHR carry none.

**What the guest can read.** It reads the WebSocket answer, if the server authenticates by cookie and does not check
`Origin` (the `Origin` is `null`). The loads are credentialed GETs whose bodies the guest cannot read. Not measured: a
side channel such as image dimensions or load and error, used as a logged-in oracle.

**WebKit (Safari and every iOS browser).** This is worse than the documented residual:

- The documented cross-site residual on WebKit is `SameSite=None` only, and Safari's default sends none.
- Here the host site's `Lax` and `Strict` session cookies ride.
- Under BD3:ISO-2, the page's **host-only** cookies ride too. That covers `__Host-` session cookies, to the page's own
  origin.
- The docs promise that these entries "are dropped in every mode". The fallback caveat in docs/API.md:205 does admit that
  "a sibling is not recognised", but only where cookies are blocked, which implies nothing rides. BD3:ISO-2 is not
  disclosed at all.

**Firefox.**

- With cookieBehavior 4: `SameSite=None` only. That is the same SameSite class as the residual, but it is the host
  site's session.
- With TCP (the release default): nothing. This confirms the facts table.

**Chromium.** Nothing, because of the credentialless wrapper. The policy result is the same as on the other engines
(kept, silent), so the API behaves uniformly and the cookie outcome is an engine fact.

#### (3) Severity

**Both are high.** For each, a documented security property ("an origin on the host page's site is dropped in every
mode") does not hold, in strict mode at its default plus the `origins` opt-in, under a realistic precondition. Both were
executed with data read back on WebKit.

**Both count against a clean pass.** Under the owner's rule, a confirmed data leak counts at any severity, so even a
board that downgrades the CMP precondition to medium still fails the clean pass.

**BD3:ISO-2 is the stronger finding.** It needs no third-party script, it hits the host's own origin, and it carries
host-only cookies.

#### (4) The fix by construction, at the class-B chokepoint (host-site.ts and origin.ts)

##### 1. The host origin

Take it from the realm's settings, not from `location`. Add one function, `hostRealmOrigin()`, that returns
`globalThis.origin` (`self.origin`). The host name for the probe is `new URL(self.origin).hostname`. host.ts:904 and
:1827 and `hostRegistrableDomain`'s default all use it.

Do not use these instead:

- `document.baseURI`: it is a URL, and a `<base>` element can move it.
- `document.domain`: it is deprecated and can be set by the page.
- `top`: it is unreadable across origins.

The cookie jar is keyed by the element's realm, and the element's `ownerDocument` shares it.

An opaque `self.origin` (a sandboxed host document) has no jar of its own. Its requests carry only `SameSite=None` cookies,
which is the documented cross-site residual. Keep its entries, with a warning that the host origin is opaque.

##### 2. The registrable domain

Make the answer three-valued: same site, another site, or unknown. Unknown refuses, using a sound over-approximation:

- A registrable domain is always a public suffix plus one label, so it has at least two labels.
- So when the probe cannot answer, an entry counts as on the site when its **last two labels** equal the page's
  (`api.example.com` and `app.example.com` share `example.com`; `x.example.co.uk` shares `co.uk`).
- That is never narrower than the truth. Over-refusal is a functional loss, never a leak.

Do not cache null. Bundling the Public Suffix List is not needed for safety, and the library chose not to.

Optional, for accuracy only: run the probe through the native `cookie` accessor of a fresh about:blank frame's
`Document.prototype`, called on the host document. This also handles the confident-wrong "only `Domain=` refused" jar.
It weighs against CMP compliance: the library would write a cookie the CMP held back. It is not needed for the security
property.

##### Cost

- **Local-first hosts are unaffected:** localhost, IP addresses, `[::1]` and single-label hosts are decided by name and
  never probed.
- **`*.localhost`:** `app.localhost` and `api.localhost` already differ in their last two labels.
- **Pages whose probe fails:** they lose entries under their own last two labels, and under a multi-label suffix (`co.uk`,
  `github.io`) also unrelated sites, with a warning that points to `fetchBridge`.

### 2. Root cause

- **For every request the engine makes on a document's behalf, the engine chooses the credentials.** Element and CSS
  loads are `no-cors` with credentials `include` (WebKit also loads fonts this way). A WebSocket handshake always carries
  credentials.
- **The engine also decides which cookies are attached.** It decides from the target URL and the **top-level site**. The
  requesting document's opaque origin does not enter into it.
- The sandbox's documents sit under the host's top-level site, so each such request is "a request of the host site":
  - it is same-site with the host site's siblings, and WebKit then attaches Lax, Strict and host-only cookies;
  - it is a third-party request to every other site.

The library let the engine make those requests: the strict policy lists `origins.images`, `media`, `fonts` and `styles`,
and the renderer keeps their http(s) URLs. The library then tried to **predict the browser's cookie decision** to judge
which targets were safe. That prediction is the class-B re-derivation in `host-site.ts`, `sharesHostSite` and
`limitHostReach`.

Every recurring cookie finding is that prediction failing or not covering a case:

| Finding | How the prediction failed |
| :--- | :--- |
| BD2:NEW-2 | the wrong engine scope |
| BD3:ISO-1 | the probe fails open |
| BD3:ISO-2 | the wrong host origin |
| BD2:ISO-2, BD3:NEW-7 | cross-site targets, which the prediction never covered |
| BD3:DOC-1 | the request kinds the docs enumerate by hand |

The gate already shows the alternative: `fetch` and XHR stopped producing findings once the library set
`credentials:'omit'` itself.

**The peak:** own the credentials mode of every request kind that has one. Then "is this origin same-site?" decides only
for the one request kind the platform gives no credentials mode, the WebSocket handshake.

### 3. The proposed constructions

#### 3.1 Construction V (the peak for the view): the view never lets the engine load a network URL

**The mechanism.**

1. **The policy fails closed.** The strict view's policy becomes `img-src blob:`, `media-src blob:`, `font-src blob:`
   and `style-src 'unsafe-inline' blob:`.
   - It holds `blob:` only where the build needs it. It never holds an `Origin`.
   - So any path the library misses fails closed with a violation and never carries a cookie: an engine-specific CSS
     function, a new URL attribute, an SVG feature re-allowed later.
   - Measured (probe C, all three engines): a direct `<img>` and a CSS `background:url()` to the origin each raise an
     `img-src` violation, and **nothing reaches the listener**. The minted image renders (`naturalWidth` 3).
2. **One loader, as library code in the view.** The renderer keeps an http(s) URL attribute only when it names an origin
   listed for its kind. That is today's exact-origin check, `refusedUrl`, the same admission the gate uses.
   - It removes the attribute and records `(element, attribute, url, kind)`.
   - After insertion, the loader runs with a captured `fetch`, called with one frozen init, like
     `BRIDGE_REQUEST_OPTIONS`:
     `{credentials:'omit', mode:'cors', referrerPolicy:'no-referrer', cache:'no-store', redirect:'follow'}`.
   - It checks that the final `response.url` is still an origin admitted for the kind.
   - It checks the response `Content-Type` against `VIEW_LOAD_KINDS[kind]` (`VIEW_FILE_TYPES`), so it never mints SVG or
     HTML. It reads the body under a byte cap.
   - It mints a URL with `URL.createObjectURL(new Blob([bytes], {type: checked}))`, adds it to `minted` (the δ machinery
     at `in-sandbox-view.ts:1505-1530`), and sets the attribute. A `srcset` gets each candidate rewritten.
   - A refusal is reported through the view's existing violation path: no CORS, wrong type, too large, a redirect off the
     list. The URL is revoked when its element's content is replaced (the view's ops know when).
3. **CSS.** For every text an operation adds as CSS (exactly the list `cssLoadsOf` already enumerates: kept `style`
   attributes, `<style>` text in HTML and SVG, text written into a `<style>`):
   - It is tokenised with `css-references.ts`, which today is host-only. It has no imports, so it can be stringified into
     the view like `sanitizeRender`.
   - Each reference to an admitted origin of kind `image`, `font` or `style` is loaded as above and replaced with
     `url("blob:…")` by `replaceRanges`.
   - `@import` is loaded as `text/css`, rewritten in turn up to a fixed depth, and minted as `text/css`.
   - A reference that is not admitted is left as written, and the policy refuses it (fail closed).
   - The sheet or attribute is applied once its references are settled, or progressively.

**What it closes, by finding.**

- **BD3:NEW-7** is closed. The guest still picks the path, but the request is anonymous, like `fetch`. The docs should
  say so.
- **BD2:ISO-2** is closed for the view's loads. Its fetch and XHR part was closed by the gate. The WebSocket remains
  (§3.2).
- **BD2:NEW-2** is closed for the view's loads on every engine, **whatever the site decision says**.
- **BD3:ISO-1 and BD3:ISO-2** no longer reach the view, whatever the probe or host origin answers. They stay relevant for
  `wss:` and for cooperative and worker modes (§3.2, §3.4).
- **BD3:ISO-4** is closed for the view: `omit` also excludes HTTP authentication and client certificates by the Fetch
  spec. Not measured.
- **The new WebKit font fact (V8)** is closed.

**Engine facts measured (probe B and C, all three engines identical unless noted).**

- `fetch(omit, cors)` to a cross-site origin: no cookie.
- Its blob renders as an image (3×5) and plays as audio (`loadedmetadata`, duration 0.1 s).
- Overhead, fetch to decode, for a 75-byte PNG on loopback: 7–12 ms.
- A server without `Access-Control-Allow-Origin` fails the fetch. The errors are `TypeError` "Failed to fetch",
  "NetworkError…" and "Load failed", so the load fails closed.
- A `no-cors` fetch gives an `opaque` response whose blob is 0 bytes on all three. **No browser API reads a cross-origin
  body without CORS.** So this is the only uncredentialed path, and it costs CORS.
- `crossorigin="anonymous"` (`<img>`, `<audio>`) also sends no cookie on all three (mode cors, `Origin: null`). It needs
  the same CORS and cannot reach CSS loads.
  - CSP cannot tell an `<img>` load from a CSS image load (both are `img-src`), so that cheaper variant can never give the
    fail-closed policy of step 1. It is rejected.
- A COEP `credentialless` view would strip no-cors loads in the engine, but a srcdoc document cannot carry the header, and
  WebKit lacks the mode. Rejected.

**Costs.**

- **CORS is required of every origin in `images`, `media`, `fonts` and `styles`** (`Access-Control-Allow-Origin: *` or
  `null`). Fonts already need it on Chromium and Firefox. Owner decision D1.
- **Memory:** each loaded resource is held as a Blob in the view's process until revoked. It needs a per-view byte budget
  (a provisional name, §4) beside `VIEW_MAX_DISTINCT_URLS`.
- **Latency:**
  - the first paint of an image waits for the whole body, not progressive decode;
  - `loading=lazy` is lost unless the loader adds an IntersectionObserver later;
  - `srcset` loads all of its candidates, or the loader picks one by `devicePixelRatio`.
- **Streaming media:** there are no range requests. A video is downloaded whole, under the cap, before it plays.
  - MediaSource could stream, but only fragmented MP4 or WebM, and iOS has only ManagedMediaSource.
  - So it would not be uniform. Owner decision D3.
- **SVG images from a listed origin stop showing:** `image/svg+xml` is not in `VIEW_FILE_TYPES` (BR:ST1). Inline `<svg>`
  still works.
- **A side gain, class P:** the loader is the view's only load-maker, so the URL and load budget is charged exactly,
  before any load starts.
  - The S73 CSS prepayment (`cssLoadBound`, `perSheet`) and the resource-timing reconciliation (`observeLoads`) reduce to
    an assertion that nothing else loaded. That is a deletion to make in a later PR, not here.
- **What it touches:** the view's `connect-src` must admit the resource origins for the loader, and the worker inherits
  the view's policy.
  - The gate's admission stays exactly `features.connect`, so the guest's own `fetch` cannot reach them. The second layer
    is wider for the worker, and every such request would still be `omit`.
  - The alternative is to run the loader in the bridge frame, which has its own policy and so keeps the worker's policy
    narrow. That adds a hop and a frame per build. Owner decision D4; my pick is the view.

**Structural tests that keep it closed.**

1. **Unit (property):** for any parsed `origins`, the strict template's `img-src`, `media-src`, `font-src` and
   `style-src` hold no `Origin`, only `'none'`, `blob:` and `'unsafe-inline'` (style). That is the fail-closed half.
2. **Unit (scan, the request-gate pattern):** the view bootstrap's text calls the captured `fetch` in exactly one place,
   with the frozen init. It has no other `fetch(`, `new Request`, `XMLHttpRequest`, `new Image` with a network URL, or
   `setAttribute` of an `RENDER_URL_ATTRIBUTES` attribute outside the loader.
3. **E2E, `cookie-carriers.spec.ts`, every engine:**
   - The guest exercises one request per row of a `STRICT_REQUESTS` table: the W and V rows above.
   - **An enumeration test fails** if `RENDER_URL_ATTRIBUTES`, the CSS reference kinds or `STRICT_WORKER_GLOBALS` gain a
     maker with no row.
   - The listener asserts that every hit except a WebSocket upgrade has no `Cookie`, `Origin: null`, and on engines that
     send it `Sec-Fetch-Mode: cors` and `Sec-Fetch-Dest: empty`. Those two prove that a library `fetch` made it, not the
     engine.
   - Each row has its positive control: the same load from a plain srcdoc frame carries the cookie (probe B's control).
4. `cookie-facts.ts` is regenerated: the "loads of markup and CSS" carrier disappears from strict.

#### 3.2 WebSocket (W3): options

**Facts.**

- The platform has no credentials option for `WebSocket`, and none for `WebSocketStream` either (that API is absent in
  Firefox and WebKit, measured).
- WebTransport sends no cookies by design, but `typeof WebTransport` is `undefined` in WebKit 26 (probe B). Chromium and
  Firefox have it. It also needs HTTP/3 servers.
- The handshake's `Origin` is `null` on all three engines (probe A, v3-iso).

| Option | Uniform? | Local-first | Function | Residual |
| :--- | :--- | :--- | :--- | :--- |
| (a) **Keep `wss://` entries (already a separate, explicit opt-in), refused on the host site by the sound three-valued rule** | The API is the same everywhere; the cookie that rides is the engine's third-party policy | yes | kept | a cross-site listed `wss` origin's own cookies: Firefox cb 4 and WebKit send None; Chromium none; Firefox TCP and Safari expected none (not measured for WS) |
| (b) Refuse WebSocket unless the embedder declares the origin cookie-free (a provisional name, e.g. `origins.sockets`; alternatives `cookieFreeSockets`, a `{origin, uncredentialed: true}` entry form) | yes | yes | kept, behind a claim | as (a) whenever the claim is wrong; the library cannot check it. Close to a rename of (a)'s `wss://` entry |
| (c) Remove WebSocket from strict mode | **yes, literally**: strict then has no request whose credentials the engine chooses | yes | lost in strict (use polling `fetch`, or cooperative mode) | none |
| (d1) WebTransport instead of WebSocket | **no** today (WebKit lacks it) | yes | new servers only | none |
| (d2) A socket opened by the host, or by the bridge frame | no | yes | kept | worse: the host page's context, or the same handshake |

**My recommendation is (a)**, with the owner choosing (c) if the stated goal must hold with no exception (D2). On (a):

- The residual arises only from an explicit `wss://` entry.
- It is exactly what any third-party frame on the host page can do to that origin. Cross-site WebSocket hijacking is the
  server's to refuse by checking `Origin`, and here the `Origin` is `null`.
- (b) adds a public name, and an unverifiable claim, to what `wss://` already says.

Revisit (d1) when WebKit ships WebTransport.

**Item 3.** That residual, a listed cross-site origin's own `SameSite=None` cookie on the handshake in Firefox and WebKit,
is acceptable as documented under (a). It is generated from `cookie-facts.ts` as the only strict-mode carrier. The one
thing that would make it unacceptable is a goal of "no listed origin's cookie ever, on any engine", and then (c) is the
construction.

**What (a) needs.** The verifier's sound rule, applied to `wss:` entries in strict:

- the host origin comes from `self.origin`;
- unknown refuses, as everything sharing the page's last two labels;
- no cached `null`.

**Structural tests:**

- the property test over jar behaviours × host and entry pairs from v3-iso;
- the srcdoc and wrapped-setter e2e variants of `host-site.spec.ts`;
- a source scan for no `location.origin` or `location.hostname` in host code.

#### 3.3 What the same-site machinery becomes after the peak

**Reduced, not removed.**

- **Strict:** the `sharesHostSite` / `limitHostReach` site drop applies to `wss:` entries only. An `https:` entry on the
  host site, of any kind including `connect`, is reached only with `omit`, by the gate (fetch, XHR) or the loader (view).
  - So it can be kept. This is owner decision D5. My pick: keep it, so a same-site anonymous asset host
    (`static.example.com`) becomes listable, and drop the cookie warning for those kinds.
  - The private-network rule is unrelated and stays.
- **Cooperative and worker modes:** unchanged. The drop applies to every kind, because the guest's document and its
  `importScripts` make engine-credentialed loads. So the sound rule (§6) is permanent there, not interim.
- **The probe (`host-site.ts`)** stays as the accuracy layer under the three-valued rule, and is used only where the rule
  runs. Defence in depth is the policy of step 1, not the site rule.

#### 3.4 Cooperative mode (item 4)

The guest owns a document, so everything in its table except the gate's rows is engine-credentialed, and nothing in-realm
can close it:

- a nested frame the guest creates has the natives (BD3:DOC-1 measured `framefetch` with a cookie on WebKit);
- the guest writes its own `<img>` and CSS.

Per-API patches would shrink the list without changing the property: refusing `sendBeacon`, or forcing `EventSource`
`withCredentials` false (~30 lines in the cooperative gate). That is the heuristic-patching the owner rules out.

**Recommendation: document it as the mode's limit, by construction of the docs.**

- Add a `COOKIE_CARRIERS` table to `cookie-facts.ts`: rows by mode × request kind, with engine facts and a test.
- The README, API.md and THREAT-MODEL sentences are generated from it, which closes **BD3:DOC-1**.
- `cookies.spec.ts` runs one request per cooperative row on every engine.
- The mode's neutralisation stays `credentialless` (Chromium) plus the sound same-site drop (all engines).

Worker mode inherits strict's worker rows. Its `importScripts` row joins the table.
