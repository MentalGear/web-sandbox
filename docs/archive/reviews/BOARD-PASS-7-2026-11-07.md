#### <a id="bd7-iso-1"></a>BD7:ISO-1: guest CSS keeps every URL that is not a network URL, so a `data:` URL makes the browser report to the host page's endpoint even when the page admits `blob:` as the docs say

- **Severity**: medium. A case can be made for high, because a documented security property does not hold. It is
  medium here because no field of a report carries guest bytes. The guest controls which directive is reported, how
  many reports are sent and when. That is the same content as the documented `blobLoads` residual. What fails is the
  docs' remedy, and the table's and the docs' claim that a guest style causes no report.
- **Effect**: data. The guest makes the browser POST reports to the host page's `report-uri`, often a third-party
  processor. It encodes data in which directive is reported, how many reports are sent and when.
- **Scope**: sealed, default configuration. Reports are sent on Chromium and Firefox. WebKit raises the violation in the
  view but sends no report from the view (ledger `view-report-delivery`).
- **Class**: A (`INHERITED_CONTEXT.cspReporting`, `SEALED_REACH` cells), through the chokepoint `cssUrlDrop`. It also has
  a class B side: the renderer predicts which CSS URLs reach a policy check ("network" ones), but the browser checks
  every URL it loads against the inherited list. A denylist of server schemes is used where markup uses an allowlist.
- **Where**:
  - `src/lib/css-references.ts:343-345` (`isNetwork`; the comment says "blob: and data: URLs name no server"): only
    http(s), ws(s), ftp, view-source, filesystem and jar are dropped.
  - `src/lib/in-sandbox-view.ts:1213` (`withoutNetwork`, style attributes and `<style>`), `:2484` (`cssInto`, `text()`
    into a style), `:2714` (`applyCss`, `set({ css })` `cursor` and `--*`).
  - `src/lib/files.ts:763` (`viewStylesheets`, registered stylesheets).
  - Markup is handled differently: `in-sandbox-view.ts:1034` (`urlAllowed`) keeps only http(s), minted `blob:` or
    relative URLs, and drops `data:`.
  - Claims that are now false:
    - `src/lib/sealed-reach.ts:633-634`: the `cspReporting` cells for `styleElement` and `styleAttribute` are
      `STYLE_*_CSSOM`, which say style-src only, "neutralised". #93 changed them from `remains`. The rendered table,
      THREAT-MODEL.md:215, lists `blobLoads` for cspReporting only from `loadKind`, `urlAttribute` and `viewApi`.
    - `src/lib/inherited-context.ts:147,151` ("none of a guest style"; "What the view still has checked … is the
      library's own loads of registered files").
    - docs/API.md:2319-2322 ("Admit `blob:` … or treat those reports as the guest's data").
- **Path**: the guest renders
  `<style>@font-face{font-family:pf;src:url("data:font/woff2;base64,…")} .pf{font-family:pf}</style><p class="pf">`, or
  `style="background-image:url(data:image/png;base64,…)"`, or calls `set(id,{css:{cursor:'url("data:…"),auto'}})`.
  1. The tokenizer keeps the URL, because it is not a network URL.
  2. The view's own policy (`img-src`/`font-src` `'none'` or `blob:`) refuses it.
  3. The host page's inherited policy is checked too. Its `font-src` falls back to `default-src 'self'`, and its
     `img-src 'self' blob:` follows the docs, so it refuses and POSTs `{"blocked-uri":"data","violated-directive":"font-src"|"img-src",…}`.
  4. The renders' timing and count are the guest's choice.
- **Reproduction**: `test/e2e/p7-iso-css-scheme.spec.ts`.
  - Test 1 uses the realistic host with secrets, and `img-src`, `font-src` and `media-src` set to `'self' blob:`. The
    guest makes 1 font load, 1 cursor, then bursts of 1, 3 and 2 images.
    - Chromium: **2 reports** (font-src and img-src). Chromium deduplicates identical report bodies per document.
    - Firefox: **9 reports** (2 font-src and 7 img-src: one per refusal, in the guest's bursts).
    - WebKit: 0 reports, 16 view violations.
  - Test 2 uses the realistic host exactly as the suite writes it, only `withPolicySecrets`, and one data: font.
    - Chromium: 1 report `{"violated-directive":"font-src","blocked-uri":"data","line-number":1123,"column-number":27,…}`.
    - Firefox: 2 reports.
- **Why the chokepoint and tests miss it**:
  - `cssReferences`' `network` scope is a denylist of server schemes, so `data:` (and a `blob:` the view did not mint)
    survive into the CSSOM.
  - `SEALED_MAKERS` and `STYLE_MAKERS` (test/e2e/sealed-makers.ts) aim only at http(s) URLs.
  - The realistic host's `img-src` admits `data:`, and no maker uses `@font-face` with a non-network URL.
  - `sealed-host-policy.spec.ts` therefore never sees a style that loads a non-network URL.
  - The structural test of `SEALED_REACH` checks only that cells name existing chokepoints and residuals, not that a
    `neutralised` cspReporting cell for styles covers the loads the CSS makes.
- **Suggested fix (by construction)**:
  - Make CSS like markup: an allowlist, not a denylist. Every `url()`, `image-set()` or `@import` string, and every
    string in network scope, is kept only when it is exactly a URL the view minted (`isMinted`) or a fragment-only
    `#id`. Everything else becomes `""`, in `withoutNetworkReferences` (rename it), `cssInto`/`applyCss` and
    `viewStylesheets`.
  - Restore the cspReporting `styleElement` and `styleAttribute` cells to `remains(['blobLoads'])`.
  - Structural test: a maker per URL scheme in every CSS carrier (style attribute, `<style>`, `text()`, `set({css})`,
    registered stylesheet; `@font-face`, `cursor`, `@import`). Schemes: data, unminted blob, about, javascript,
    filesystem, chrome-extension, moz-extension, resource, file, ftp, http(s) and ws(s).
  - Run it on the realistic host with every fetch directive `'self' blob:` and `'report-sample'`, expecting 0 reports on
    every engine.

#### <a id="bd7-iso-2"></a>BD7:ISO-2: the entry-import scan finds only `import(`; the phase forms `import.source(…)` and `import.defer(…)` pass it

- **Severity**: low. No data effect today; this is latent.
- **Scope**: sealed and strict.
- **Class**: A (`cspReporting` through the `entryImportRefusal` chokepoint). The construction enumerates one member of
  the dynamic-import family.
- **Where**: `src/lib/entry-imports.ts:48-53` (`dynamicImportAt` needs `(` right after `import` and trivia; the claim at :16) and
  `src/lib/sealed-reach.ts:247` (`DYNAMIC_IMPORT = 'import()'`, the only syntax name). The docs claim the scan "never
  miss[es] one it would [run]".
- **Path**: an entry holding `import.defer('https://x/<data>')` or `import.source('https://x/<data>')` builds. On an
  engine that parses it, this is a module fetch checked against the inherited `script-src`. That reproduces BD6:ISO-2:
  a report carrying the guest's URL, path and query.
- **Reproduction**: `test/e2e/p7-iso-import-phase.spec.ts`.
  - The scan returns -1 for both forms, and the build is ready.
  - No engine of the suite parses them yet. The entry fails with:
    - Chromium 145: "Unexpected identifier 'source'/'defer'";
    - Firefox: "did not parse";
    - WebKit: "\"import.\" can only be followed with meta".
  - 0 reports.
  - Both proposals are TC39 stage 3, and V8 has them behind flags.
- **Fix**: in a classic script, every `import` keyword is either `import(` or a phase form, since `import.meta` is a
  SyntaxError there. So the build should refuse every `import` that is not part of a longer name, not only one followed
  by `(`. `entry-imports.test.ts` should generate `import` followed by trivia, `.`, a name and `(` too.

#### <a id="bd7-iso-3"></a>BD7:ISO-3: the sealed view has picture-in-picture on Chromium; the `mediaControls` cell says no frame has it

- **Severity**: low. No data effect.
